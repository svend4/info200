# Вопросы к daten11

## 1. Разворачивалось ли демо на Render реально, и знаете ли вы, что веб-поиск в нём падает?

Аудит показал: /api/search и /api/facets гарантированно падают с NameError (отсутствует `import os` на уровне модуля в web/tools/search.py). README при этом обещает «работающее демо за 5 минут».

**Варианты ответов**
- А. Демо разворачивалось, поиском не пользовались (смотрели только навигацию) — баг не замечен.
- Б. Демо никогда не разворачивалось, конфиги написаны «на веру».
- В. Баг известен, проект сознательно заморожен.

**Варианты дальнейших действий**
- При А: применить быстрые улучшения 1–2 из recommendations.md (два однострочных исправления), передеплоить, убедиться в работе поиска.
- При Б: сначала прогнать локально (`DOCUMENTS_PATH=examples/sample_library python web/app.py`), исправить баги, и только потом оставлять в README обещания про демо.
- При В: добавить в README плашку «прототип, веб-поиск неисправен», чтобы репозиторий не вводил в заблуждение.

## 2. Какова целевая коллекция: для каких реальных файлов задумывалась система?

Демо содержит один txt-файл; методология же говорит о «тысячах файлов» и библиотеках PDF/DOCX.

**Варианты ответов**
- А. Личная библиотека документов/книг (PDF, DOCX).
- Б. Markdown-базы знаний (например, lorenzo с ~2815 md-файлов).
- В. Конкретной коллекции нет — это упражнение в методологии.

**Варианты дальнейших действий**
- При А: приоритет — извлечение текста из PDF/DOCX и AI-генерация метаданных (сценарий 3), иначе ручная разметка тысяч файлов нереальна.
- При Б: интегрировать с lorenzo как полигоном (идея сочетания 2), метаданные класть рядом с md-файлами, мерить производительность индексации.
- При В: выбрать сценарий 1 или 4 (честное демо либо перенос методологии в info200 как стандарта), код не развивать.

## 3. Почему поиск построен на полном обходе файловой системы при каждом запросе, а не на постоянном индексе?

MetadataSearch.build_index() вызывается в каждом запросе /api/search — на больших коллекциях это архитектурный тупик; при этом в профиле уже есть daten22 (SQLite FTS4) и в docs/SEARCH_INTEGRATION.md описаны Elasticsearch/Meilisearch.

**Варианты ответов**
- А. Осознанное упрощение для демо; постоянный индекс планировался.
- Б. Планировалась интеграция с Meilisearch (она даже закомментирована в render.yaml), но не дошли руки.
- В. Про проблему не думали.

**Варианты дальнейших действий**
- При А/В: минимальный шаг — кеш индекса в памяти процесса + инвалидация по mtime; полноценный — SQLite-индекс (можно переиспользовать наработки daten22).
- При Б: реализовать SEARCH_INTEGRATION.md хотя бы для Meilisearch в docker-compose для локального использования (на бесплатном плане Render его всё равно нет).
