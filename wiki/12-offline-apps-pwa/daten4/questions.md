# Вопросы к daten4

## 1. Где исходники HTML-планировщика (React/Vite-проект), из которого собраны четыре бандла?

В репозитории лежат только минифицированные сборки (~1,6 МБ), а среды сборки нет — значит, править и диффать версии невозможно.

**Варианты ответов:**
- А. Исходники есть локально/в другом репозитории, просто не опубликованы.
- Б. Исходники утеряны, остались только сборки.
- В. Файлы генерировались AI-инструментом (Claude Artifacts и т.п.) по промптам, «исходник» — это промпты.

**Варианты дальнейших действий:**
- При А: закоммитить исходники в `src/`, настроить сборку одним скриптом, старые бандлы перенести в `archive/`.
- При Б: выбрать лучшую версию (судя по всему, `(8)`/DEMO), декомпилировать/переписать её начисто как небольшой проект — UI-строки и логика восстановимы из бандла.
- При В: сохранить промпты/диалоги в `docs/provenance.md` и дальше развивать один канонический файл, зафиксировав процесс регенерации.

## 2. Какая из четырёх версий — актуальная, и в чём разница между `(1)`, `(8)`, `v2` и `DEMO`?

Сейчас понять это можно только сравнением мегабайтных бандлов; README не говорит ничего.

**Варианты ответов:**
- А. Актуальна `(8)`; `DEMO` — то же с демо-данными; остальные — история.
- Б. Ветки разные по функциям: `v2` — редактор условной логики, `(8)` — библиотека шаблонов; единой «актуальной» нет.
- В. Уже не помню / нужно самому сверять.

**Варианты дальнейших действий:**
- При А: переименовать в `index.html` (+ `demo.html`), остальное — в `archive/`, включить GitHub Pages.
- При Б: описать матрицу «версия × функции» в README и запланировать слияние веток в одну.
- При В: провести 30-минутную ревизию в браузере, зафиксировать выводы в README — иначе ценность файлов со временем обнулится.

## 3. Планируется ли доводить `ai-planner` до запускаемого состояния (frontend-каркас, Dockerfile, перенос workflow в корень)?

Сейчас MVP не запускается по собственной инструкции: нет `frontend/package.json`, нет `backend/Dockerfile`, CI-workflow лежит там, где GitHub его не видит.

**Варианты ответов:**
- А. Да, это основное направление — планировщик с ИИ.
- Б. Нет, это был эксперимент одной сессии; ценна только идея/код движков.
- В. Частично: интересен только chunking/RAG-движок, не сервис целиком.

**Варианты дальнейших действий:**
- При А: минимальный план — Dockerfile (10 строк), Vite-каркас фронта, перенос workflow, smoke-тест `docker compose up`; после этого честно назвать MVP.
- При Б: пометить `ai-planner` как experiment в README и вычистить из документации невыполнимые инструкции.
- При В: извлечь `chunking-engine.js` + `rag-engine.js` в отдельный пакет/репозиторий с тестами (см. сценарий 3 в рекомендациях).

## 4. Почему embeddings через OpenAI при генерации ответов через Claude — и приемлема ли зависимость сразу от двух платных API?

`rag-engine.js` требует и `ANTHROPIC_API_KEY`, и `OPENAI_API_KEY` (для `text-embedding-3-large`), что удваивает порог входа.

**Варианты ответов:**
- А. Так сложилось исторически, готов заменить.
- Б. Осознанный выбор: качество embeddings OpenAI устраивает.
- В. Хотелось бы вообще без внешних API (локально/офлайн).

**Варианты дальнейших действий:**
- При А: заменить на Voyage AI (рекомендованные для Claude embeddings) или локальную модель — правится один метод `getEmbedding()`.
- При Б: оставить, но добавить в README явное предупреждение о двух ключах и ориентировочной стоимости индексации.
- При В: связка с daten22/data20 — SQLite FTS или sql.js вместо векторной БД (см. рекомендации, сочетание 1).

## 5. Каков реальный статус «GitHub Integration — хранение и версионирование шаблонов», заявленной в README `ai-planner`?

В коде backend интеграции с GitHub не обнаружено (нет ни octokit, ни git-операций); есть только неактивный workflow авто-индексации.

**Варианты ответов:**
- А. Это план на будущее, не реализовано.
- Б. Под «интеграцией» имелось в виду просто хранение шаблонов в этом репозитории.
- В. Реализация есть в другом репозитории профиля (например, ingit).

**Варианты дальнейших действий:**
- При А: перенести пункт из «Возможности» в «Roadmap», чтобы README не обещал несуществующее.
- При Б: переформулировать в README («шаблоны версионируются самим git»), починить workflow — тогда заявление станет правдой.
- При В: сослаться на соответствующий репозиторий и описать протокол обмена; рассмотреть объединение с ingit (Integrated Git Platform).

## 6. Как daten4 соотносится с daten30 («динамический хаб, микросервисы») и daten6 («динамический каталог») — это одна линейка «динамических» приложений?

В профиле несколько «динамических» проектов; непонятно, конкурируют они или дополняют друг друга.

**Варианты ответов:**
- А. Да, одна линейка: планировщик / хаб / каталог — разные грани одного подхода «динамические блоки+шаблоны».
- Б. Независимые эксперименты на общую тему.
- В. daten4 — прототип, лучшие идеи которого уже перенесены в другой репозиторий.

**Варианты дальнейших действий:**
- При А: описать в вики профиля (info200) общую архитектуру линейки и выделить общий формат шаблона/блока как отдельную спецификацию.
- При Б: свести их в сравнительную таблицу в вики и решить, какой из экспериментов доводить до продукта.
- При В: пометить daten4 как superseded с ссылкой на преемника, оставив DEMO как витрину.
