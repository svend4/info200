# Рекомендации по daten4

## Быстрые улучшения

1. **Исправить корневой README**: описать реальный состав (4 версии HTML + подпроект `ai-planner`), указать, какой файл открывать как «актуальный», добавить скриншот.
2. **Переименовать HTML-файлы**: `dynamic-planner (1).html` → `dynamic-planner-v1.html` и т.п.; убрать пробелы и скобки из имён (ломают ссылки), а старые итерации перенести в папку `archive/`.
3. **Добавить LICENSE** (MIT уже заявлен в `backend/package.json` — оформить на весь репозиторий).
4. **Перенести workflow** из `ai-planner/.github/workflows/index-templates.yml` в корневой `.github/workflows/` и поправить в нём пути (`working-directory: ai-planner/backend`, `paths: ai-planner/templates/**`), иначе он никогда не запустится.
5. **Синхронизировать документацию с фактом**: убрать из `ai-planner/README.md` несуществующие `generate-embeddings.js` и `frontend/package.json`, исправить «5000+ строк» у примера (реально 412 строк), «14 файлов» в DEPLOYMENT.md (в списке 16).
6. **Включить GitHub Pages** и опубликовать `dynamic-planner-DEMO.html` как живую демонстрацию — это бесплатная витрина проекта.
7. **Добавить `backend/Dockerfile`** (10 строк), без него docker-compose из «рекомендуемого» варианта запуска не работает.

## Серьёзные доработки

1. **Опубликовать исходники HTML-планировщика.** Сейчас в репозитории только минифицированные сборки; проект React+Vite, из которого они собираются, не закоммичен. Без него невозможны ни дифф между версиями, ни доработки. Это главный долг репозитория.
2. **Достроить frontend `ai-planner`**: каркас Vite (package.json, index.html, App), интегрировать `AIAssistant.jsx` с самим планировщиком, чтобы «подключение ИИ» из описания репозитория стало правдой.
3. **Тесты**: jest уже в devDependencies — начать с unit-тестов `ChunkingEngine` (детерминированная логика, идеальна для тестирования: границы чанков, overlap, разбиение крупных секций) и supertest-тестов маршрутов с моками RAG.
4. **Снизить порог входа по API**: сделать embeddings подменяемыми (локальная модель / `@xenova/transformers` / отключаемый режим «поиск по подстроке»), чтобы систему можно было попробовать без ключей Anthropic и OpenAI одновременно.
5. **Объединить два слоя**: определить единый формат шаблона (сейчас формат HTML-версий и формат `templates/examples/api-documentation.json` совпадают лишь частично) и сделать экспорт/импорт между офлайн-планировщиком и AI-backend.

## Варианты продолжения

**Сценарий 1 — «Офлайн-продукт».** Отказаться от серверной части и довести до блеска однофайловый планировщик: опубликовать исходники, выпустить каноничную версию на GitHub Pages, добавить PWA-манифест и IndexedDB вместо localStorage (лимит 5 МБ), экспорт в Markdown/ICS. Это честное продолжение исходной идеи «в одном файле HTML»: нулевые зависимости, приватность, работа без сети. AI-слой при этом можно свести к опциональной вставке API-ключа пользователем прямо в браузере.

**Сценарий 2 — «AI-сервис шаблонов».** Наоборот, признать `ai-planner` главным: достроить frontend, Dockerfile и CI, добавить хранение шаблонов в git (GitHub Integration уже заявлена в README), автотесты chunking-движка — и позиционировать как «RAG поверх больших структурированных форм»: ниша, где обычные RAG-по-текстам работают плохо, а здесь есть схема полей, aiHints и условная логика. MVP-код backend уже покрывает ~70% этого пути.

**Сценарий 3 — «Библиотека, а не приложение».** Извлечь из backend два самостоятельных npm-пакета: `template-chunker` (разбиение больших JSON-схем/форм на чанки с overlap) и `form-rag` (индексация + автозаполнение полей через LLM). Планировщики (и любой другой проект профиля) становятся потребителями. Такой рефакторинг даёт переиспользование в daten30/data10 и делает код тестируемым.

**Сценарий 4 — «Заморозка с честной вывеской».** Если развивать не планируется: пометить репозиторий как experiment/archive, оставить рабочую DEMO-страницу на Pages и один абзац в README о том, что здесь исследовалось (итерации конструктора форм + RAG-прототип). Дешёво и снимает риск, что кто-то потратит время на невыполнимый GETTING_STARTED.

## Сочетания с другими репозиториями профиля

1. **daten4 + daten22 (Offline search app, SQLite FTS4) = офлайн-планировщик с полнотекстовым поиском без облака.** Заменить связку «OpenAI embeddings + ChromaDB» на встраиваемый SQLite FTS4/FTS5 (или sql.js в браузере): чанки шаблонов из `chunking-engine.js` индексируются локально, поиск по разделам и полям работает без API-ключей и без сети. Получается уникальная вещь — «RAG-подобный» помощник по большим шаблонам, целиком живущий в одном HTML-файле, чего нет ни в одной из двух исходных разработок.

2. **daten4 + data10 (Dynamic Content Blocks System) = конструктор «план-как-страница».** Поля и секции планировщика становятся динамическими контент-блоками data10: один шаблон порождает и форму для заполнения, и публикуемую страницу (отчёт, программу мероприятия, маршрут поездки). Инновация — двусторонняя связь: правишь блок на странице — меняются данные плана, и наоборот; из двух «обычных» конструкторов получается генератор живых документов.

3. **daten4 + lorenzo (docs-toolkit, ~2815 md-файлов) = chunking-конвейер для больших баз знаний.** `ChunkingEngine` и задуманный workflow auto-index из daten4 применить к корпусу Svyazi 2.0 через Python-пакет docs-toolkit: автоматическое разбиение и индексация тысяч md-файлов при push, а AIAssistant из daten4 — как единый интерфейс вопросов к корпусу. Уникальный результат — самообновляющаяся RAG-вики поверх крупнейшего репозитория профиля, где daten4 даёт механику, а lorenzo — контент.

4. **daten4 + info40 (AI Agent Orchestration Platform) = планировщик, который исполняет планы.** Endpoint `/api/autofill` расширить до «автовыполнения»: заполненный план (мероприятие, публикация, отчёт) передаётся оркестратору агентов info40, который раскладывает его на задачи агентам. Из «формы для записи плана» получается система «план → делегирование → исполнение» — качественно новый класс инструмента.
