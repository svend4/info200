**Варианты ответов:**
- А. Да, всё работало на телефоне: и бэкенд в Termux, и APK.
- Б. Бэкенд запускался, но APK так и не удалось стабильно собрать.
- В. Проверялось только частично / уже не помню.

**Варианты дальнейших действий:**
- При А: зафиксировать доказательство — скриншоты, релиз APK, короткое видео; пометить в README «проверено на устройстве X, Android Y».
- При Б: довести сборку через готовый CI (build-flutter-apk.yml уже собирает APK как artifact — достаточно скачать и проверить), задокументировать финальный рецепт вместо цепочки FIX-файлов.
- При В: провести один контрольный прогон по TERMUX_QUICK_START.md, все расхождения инструкции с реальностью исправить по горячим следам.

**Варианты ответов:**
- А. Hub Portal — остальное лишь ступени к нему.
- Б. Demo-app — это витрина стека, hub-portal был экспериментом.
- В. Все три равноценны как уровни обучающего курса.
- Г. Проект закрыт, иерархия уже не важна.

**Варианты дальнейших действий:**
- При А: заморозить demo-app (пометить как learning-архив), развитие сосредоточить на плагинах и реальных данных хаба.
- При Б: вынести demo-app в отдельный репозиторий «полигон стеков» с автоматическими бенчмарками; в daten30 оставить хаб.
- При В: реструктурировать README как курс с тремя главами и чекпойнтами, синхронизировать PROJECT_STRUCTURE.md с фактическим деревом.
- При Г: добавить в README статус «archived/учебный артефакт», исправить только фактические ошибки документации.

## 3. Почему документация описывает несуществующие файлы (backend-flask/, ARCHITECTURE.md, requirements.txt)?

**Варианты ответов:**
- А. Структура менялась в ходе спринта, документацию не успели обновить.
- Б. Документация писалась «на вырост» — файлы планировались, но не были созданы.
- В. Файлы были и потерялись при переносе/rebase.

**Варианты дальнейших действий:**
- При А или Б: пройтись по всем MD линк-чекером (например, lychee в CI), исправить или удалить битые пути; создать requirements.txt — это 3 строки.
- При В: поискать в истории коммитов (98 коммитов за 4 дня) удалённые файлы и восстановить нужные.
- В любом случае: добавить CI-проверку внутренних ссылок, чтобы расхождения не накапливались.

## 6. Нужен ли проекту тестовый контур, раз CI уже существует?

CI-матрица на Python 3.9–3.11 создана; в `test-backend.yml` есть четыре job-а — `py_compile`, non-blocking `lint` и даже `integration-test`, который поднимает стек и через curl проверяет саморегистрацию сервисов, — но собственно юнит-тестов (pytest) ноль: pytest ставится и лишь печатает свою версию, тестовых файлов нет.

**Варианты ответов:**
- А. Да, тесты нужны — хочется довести проект до уровня «можно показать».
- Б. Нет, это одноразовый учебный спринт, тесты избыточны.

**Варианты дальнейших действий:**
- При А: начать с 8–10 pytest-тестов Registry (Flask test_client + временная SQLite) и одного интеграционного теста «регистрация → discovery»; включить их в существующий test-backend.yml.
- При Б: упростить workflow до честного smoke-теста и убрать установку pytest, чтобы CI не изображал тестирование; зафиксировать статус «учебный, без поддержки» в README.
