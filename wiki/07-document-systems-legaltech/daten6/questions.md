# Вопросы к daten6

## 1. Планируется ли реализация backend/frontend, или проект остаётся концептом?

План IMPLEMENTATION_PLAN.md (8–12 недель, Express+MongoDB+React) не начат; вся активность уложилась в 28–29.12.2025, дальше — 6+ месяцев тишины. README при этом заявляет «Backend API разработка — в процессе».

**Варианты ответов:**
- А. Да, реализация планируется по исходному плану.
- Б. Реализация планируется, но в упрощённом виде (без MongoDB/React).
- В. Нет, репозиторий — законченный концепт/спецификация.
- Г. Ещё не решено.

**Варианты дальнейших действий:**
- При А: начать с вертикального среза (один endpoint + схема `catalog_items`), завести issues по этапам плана, добавить CI.
- При Б: перевести прототип на `fetch('data.json')` или SQLite (связка с daten22/data20), выбросить из README тяжёлый стек.
- При В: сменить статус в README на «концепт/архив», убрать «в процессе», выполнить быстрые исправления из recommendations.md — и репозиторий станет честным справочным материалом.
- При Г: сделать только Сценарий А («живое демо» на GitHub Pages) — он дёшев и не закрывает ни один путь.

## 2. Какая из двух систем — базовая или версионированная — является целевой?

BRANCHES.md и COMPARISON.md представляют их как альтернативы («выбор подхода»), но после мержа веток обе живут в одной `main` без выбранного победителя.

**Варианты ответов:**
- А. Базовая: нужен простой каталог (магазин, коллекция, меню).
- Б. Версионированная: цель — база знаний/энциклопедия с историей.
- В. Обе: базовая — ядро, версионирование — модуль сверху.
- Г. Ни одна: ценность репозитория — методология APPENDIX_3, а не каталог.

**Варианты дальнейших действий:**
- При А: развивать прототип до продукта (Сценарий Б), документы версионирования пометить как «исследование».
- При Б: следовать Сценарию В (движок версионированных знаний), прототип переделать под уровни детализации L0→L3.
- При В: составить единый roadmap с миграцией из COMPARISON.md, объединить дублирующиеся документы.
- При Г: выделить APPENDIX_3 в отдельный репозиторий/раздел хаба info200 (см. вопрос 3).

## 3. Не следует ли выделить методологию APPENDIX_3 в отдельный репозиторий?

Блок APPENDIX_3 (~13 тыс. строк, половина объёма docs/) — универсальная методология компиляции/чанкования/версионирования документов; её кейсы ссылаются на другие репозитории профиля (data1, юридический контент про персональный бюджет — тема data4/data2), а не на каталог.

**Варианты ответов:**
- А. Да, выделить в самостоятельный репозиторий-методологию.
- Б. Перенести в хаб info200 как общепрофильный стандарт.
- В. Оставить здесь: методология родилась из задач каталога.

**Варианты дальнейших действий:**
- При А: создать репо вида `compilation-methodology`, перенести 8 файлов APPENDIX_3* + CHUNKING_METHODOLOGY, в daten6 оставить ссылку; настроить перекрёстные ссылки из кейсов (data1, lorenzo).
- При Б: включить перенос в план наполнения wiki info200, здесь оставить краткую выжимку.
- При В: минимум — создать в `docs/` подпапку `methodology/` и отдельный индекс, чтобы каталог и методология не смешивались.

## 5. Лицензия MIT заявлена бейджем и разделом README — будет ли добавлен файл LICENSE?

Без файла LICENSE содержимое формально «all rights reserved», несмотря на заявление MIT; для документации это тем важнее, что методологию могут захотеть переиспользовать.

**Варианты ответов:**
- А. Да, MIT для всего репозитория.
- Б. Разделить: MIT для кода прототипа, CC BY(-SA) для документации.
- В. Лицензия не нужна, репозиторий личный.

**Варианты дальнейших действий:**
- При А: добавить стандартный LICENSE (MIT, копирайт svend4, 2025) — одна минута работы.
- При Б: LICENSE для кода + примечание о CC-лицензии в README и в шапках ключевых документов.
- При В: убрать бейдж MIT и раздел «Лицензия» из README, чтобы не вводить в заблуждение.
