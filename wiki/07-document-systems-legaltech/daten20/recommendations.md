# Рекомендации по daten20

## Быстрые улучшения

1. **Добавить файл LICENSE** (MIT, раз он уже заявлен бейджем) — сейчас проект юридически без лицензии.
2. **Привести README к правде**: убрать «zero dependencies» (в `requirements.txt` — Flask, PyYAML, openpyxl и др.), заменить «Production-Ready» на честный статус, синхронизировать цифры тестов/строк с одним источником истины.
3. **Свести самоотчёты к одному документу**: AUDIT_REPORT.md, docs/STATUS_OVERVIEW.md и README дают три несовместимых набора цифр (183/241/399 файлов; 127k/140k/214k строк; 172/284/2030 тестов) — оставить один автоматически генерируемый отчёт (`cloc` + `pytest --collect-only` в CI).
4. **Починить или удалить workflow Coverage Report** — он стабильно красный и создаёт шум.
5. **Разобрать dependabot-очередь**: ветки от 13.04.2026 (transformers, torch, spacy…) либо влить, либо отключить dependabot для замороженного проекта.
6. **Убрать дубли директорий**: `network6g`/`network_6g`, `explainable`/`explainable_ai`, `quantum`/`quantum_ml`/`qml`, `emotions`/`emotions_ai`, `federated`/`federated_learning` (проверено — все пары существуют одновременно); заодно разложить плоскую свалку из ~80 файлов `test_*.py` в `tests/` по поддиректориям, зеркалящим `src/`.
7. **Запустить в CI полный тестовый прогон** (сейчас `tests.yml` гоняет только 7 файлов `tests/test_doc_*.py` из ~80) хотя бы раз — и зафиксировать реальное число проходящих тестов, особенно по AI-модулям (`test_consciousness.py`, `test_quantum_ml.py` и др.), которые сейчас в CI не проверяются.

## Серьёзные доработки

1. **Разделить репозиторий на два продукта.** (а) `budget-planner` — предметное ядро: mSchablone, parser, financial_calculator, document_generator, web_app, соответствующие тесты; компактный, честный, потенциально полезный реальным соцслужбам. (б) `ai-modules-lab` — архив v11–v30 (federated, bci, consciousness, the_void…) как учебная коллекция Pure-Python-реализаций с явной пометкой «имитации/учебные». Смешение их в одном «production» репозитории — главный структурный дефект.
2. **Актуализация предметных данных**: ставки соцстрахования (KV 7.3 %, PV, умлаги U1/U2/U3) зашиты в код константами — вынести в конфиг с указанием года действия и источника, добавить тест «ставки не старше N месяцев».
3. **Довести до установки одной командой**: превратить `setup.py`-инсталлятор в нормальный python-пакет (pyproject.toml, extras: `[web]`, `[ocr]`, `[ml]`), опубликовать хотя бы в GitHub Releases.
4. **Проверить заявленные интеграции по-настоящему**: e2e-тест, который реально прогоняет PDF через OCR и перевод, а не мокает их; убрать из README то, что не проходит e2e.
5. **Пользовательская документация вместо самоотчётов**: из 150+ файлов docs/ собрать 5–7 руководств «как посчитать услугу», «как сгенерировать карточку», остальное — в `docs/archive/`.

## Варианты продолжения

**Сценарий 1: «Продуктизация ядра для соцсектора».** Выбросить (заархивировать) всё выше v10 и сфокусироваться на исходной задаче: инструмент для поставщиков социальных услуг в Германии — расчёт себестоимости часа услуги с учётом соцвзносов, умлаг, региональных коэффициентов и генерация комплекта документов из мега-шаблона. Это ниша с реальными пользователями (малые Träger, которым не по карману коммерческий софт). Дорожная карта: актуальные ставки 2026 → веб-форма → экспорт DOCX/PDF → пилот с одной организацией. Единственный сценарий, ведущий к настоящим пользователям.

**Сценарий 2: «Музей ИИ-разработки / учебный корпус».** Признать проект тем, чем он фактически стал — уникальным артефактом лавинообразной ИИ-ассистированной разработки (30 «версий» за месяц, от калькулятора до «Пустоты»). Оформить как исследовательский кейс: хронология коммитов, рост метрик, точки, где самоотчёты разошлись с реальностью, дисклеймеры в docstring против маркетинга в README. Такой разбор ценен для сообщества (как учиться контролировать агентскую генерацию) и напрямую полезен репозиториям info100 (лаборатория агентов) и info40 (оркестрация агентов) этого же профиля.

**Сценарий 3: «Карьер Pure-Python компонентов».** Не развивать монолит, а выкусывать из него самодостаточные модули с честной ценностью: dual-version реализации (FFT на cmath, метрики сходства текстов, анонимизатор PII, оценка читаемости) как маленькие независимые пакеты без зависимостей. Каждый — 1-2 тыс. строк, с уже написанными тестами. Портфель из 5–6 микропакетов полезнее и поддерживаемее, чем один 200-тысячестрочный монолит.

**Сценарий 4 (минимальный): «Честная консервация».** Один финальный коммит: LICENSE, правдивый README («экспериментальный проект, ядро работает, v21–30 — концептуальные»), отключение dependabot и лишних workflow, тег v30-final. Стоимость — час работы; выгода — репозиторий перестаёт вводить в заблуждение и жечь CI-ресурсы.

## Сочетания с другими репозиториями профиля

1. **daten20 + data4 («Soz соц апп — программ перс бюджет») = сквозная платформа персонального бюджета.** Это два конца одной и той же предметной цепочки: daten20 считает услугу со стороны *поставщика* (себестоимость часа, соцвзносы, карточка услуги из mSchablone), data4 ведёт персональный бюджет со стороны *получателя*. Объединение даёт уникальный продукт: получатель планирует бюджет → система подбирает услуги с прозрачной калькуляцией → автоматически генерируется пакет документов для согласования с плательщиком. Ни один из репозиториев поодиночке этой петли не замыкает.

2. **daten20 + infom (ГрафРАГ) = вопросно-ответная система по нормативке соцуслуг.** daten20 уже содержит NER, извлечение связей и KnowledgeGraphBuilder (`src/ml/knowledge_graph.py`) плюс корпус структурированных документов; infom даёт GraphRAG-подход. Скрестив их, получаем ассистента, который на вопрос «какая ставка умлаги U1 применима к услуге сопровождения в Саксонии?» отвечает по графу знаний, построенному из карточек услуг и нормативных документов, с трассировкой источника. Инновация — GraphRAG не по «интернету», а по локальному вертикальному корпусу с финансовой семантикой.

3. **daten20 + daten22 (offline-поиск на SQLite FTS4) / data20 (offline app) = полевой офлайн-DMS для соцработника.** Парсер, анонимизатор и оценка качества документов из daten20 (как раз Pure Python, без тяжёлых зависимостей) + офлайн-полнотекстовый индекс из daten22 = приложение, работающее на планшете без интернета при выезде к клиенту: поиск по карточкам услуг, анонимизированный просмотр, синхронизация при появлении сети. GDPR-анонимизатор здесь превращается из демо-фичи в ключевое преимущество.

4. **daten20 (v11–v30 модули) + info100 (лаборатория агентов) + info40 (оркестрация агентов) = стенд для аудита агентской генерации кода.** 70 сгенерированных модулей daten20 с известной историей (когда, какой сессией, с какими завышениями) — готовый размеченный датасет для экспериментов: научить оркестратор из info40 автоматически детектировать «версионную инфляцию», расхождение README↔docstring и дубли директорий. Уникальность — датасет не синтетический, а выращенный естественно в этом же профиле.
