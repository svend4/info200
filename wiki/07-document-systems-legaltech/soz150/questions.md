# Вопросы к soz150

## 1. Где полная кодовая база «Writing OS v50» (35 отсутствующих панелей и модули db/store/rag/security)?

`App.jsx` импортирует ~44 модуля, из которых в репозитории есть только 3 панели. Zip содержит те же 4 файла.

**Варианты ответов:**
- А. Полный исходник живёт локально / в артефактах claude.ai и никогда не загружался.
- Б. Полная версия лежит в другом репозитории профиля (например, data4 или один из daten*).
- В. Остальных панелей в готовом виде не существует — App.jsx писался «на вырост».

**Варианты дальнейших действий:**
- При А: загрузить полный исходник + `package.json` в soz150 (или новый репозиторий `writing-os`), убедиться, что `npm run build` проходит; это главный шаг к зрелости 4/5.
- При Б: в README обоих репозиториев указать перекрёстные ссылки и объявить один каноническим; дубликаты удалить.
- При В: пометить `wos-v14/` как «скелет/прототип», из App.jsx убрать импорты несуществующих панелей, чтобы фрагмент хотя бы собирался в демо.

Это два разных приложения без общего кода; непонятно, куда идут усилия.

**Варианты ответов:**
- А. PWA v50 — основной продукт, артефакт — экспериментальная AI-лаборатория при нём.
- Б. Артефакт — основная линия (работа идёт в чатах Claude), PWA заморожено.
- В. Планируется слияние: CAGE-пайплайн станет AI-ядром внутри PWA.

**Варианты дальнейших действий:**
- При А: см. вопрос 1; артефакт перенести в `experiments/`, из его наработок забрать Assertion Checker.
- При Б: оформить артефакт как самостоятельный проект: применить 3 патча безопасности из handoff, добавить README c инструкцией запуска в claude.ai.
- При В: начать с извлечения Assertion Checker и SKILLS[] в общие модули — они нужны обеим линиям (сценарий В из рекомендаций).

## 6. Почему семантический роутер остаётся на LLM-вызове (~800 мс, недетерминированно), хотя в roadmap описан переход на эмбеддинги (~20 мс, офлайн)?

**Варианты ответов:**
- А. Не дошли руки — план в силе.
- Б. Пробовал: качество маршрутизации e5-small на смеси RU/DE/EN оказалось хуже LLM.
- В. LLM-роутер нужен из-за поля `reasoning`/`task_type`, которых эмбеддинги не дают.

**Варианты дальнейших действий:**
- При А: реализовать по готовому фрагменту из handoff (3a), плюс LRU-кэш как быстрый промежуточный шаг.
- При Б: зафиксировать результаты эксперимента в handoff (какая модель, какие метрики) — ценное знание; попробовать гибрид: эмбеддинги как префильтр + LLM для спорных случаев.
- При В: гибридная схема: скоринг эмбеддингами, а `task_type` определять дешёвой эвристикой/регулярками; LLM оставить только для fallback.
