# Рекомендации по data10

## Быстрые улучшения

1. **Переписать README.md**: 10–15 строк — что это за методология, для кого, ссылка на оглавление документа, честный статус («концепт, реализации нет»).
2. **Убрать или пояснить галочки «✅» в разделе 12.1**: заменить на «план» либо добавить ссылку на репозиторий, где MVP реально реализован (если он существует).
3. **Добавить LICENSE** (например, CC-BY-4.0 для текста методологии) и указать AI-происхождение документа в шапке README.
4. **Разбить монолит**: вынести 13 разделов в `docs/01-intro.md … 13-appendix.md` с индексной страницей — 190-КБ файл плохо читается и плохо диффается.
5. **Извлечь код в файлы**: как минимум `examples/german_legal_parser.py` и `examples/smart_inserter.py` — оба класса почти самодостаточны и могут стать первым исполняемым артефактом.
6. **Проверить приложение D**: заменить неверифицируемые «академические статьи» без авторов на реальные ссылки; убрать мёртвые зависимости (pyknow) из requirements-списка.
7. **Добавить topics/теги на GitHub** (legal-tech, content-blocks, knowledge-management, german-law) — сейчас репозиторий не находится поиском.

## Серьёзные доработки

1. **Минимальный работающий прототип (урезанный стек)**: вместо Neo4j+MongoDB+Elasticsearch+Redis — SQLite + NetworkX + sentence-transformers в одном Python-пакете. Цель: парсинг одного закона (SGB IX) → блоки → 2–3 правила → сборка Widerspruch в DOCX. Это подтвердит или опровергнет ключевые допущения методологии за 1–2 недели работы.
2. **Тесты для парсеров**: набор реальных фрагментов немецких законов + pytest-кейсы; именно на парсерах (разделы 6 и 8) методология наиболее уязвима (одинаковые regex для Satz и Nummer, заголовки параграфов извлекаются эвристикой).
3. **Согласование с Akoma Ntoso / LegalDocML**: методология сама ссылается на эти стандарты, но собственная модель блоков с ними не сопоставлена. Маппинг схемы Block ↔ Akoma Ntoso резко повысил бы применимость.
4. **CI**: GitHub Actions с линтингом markdown (битые якоря оглавления) и, после извлечения кода, запуском тестов.
5. **Роль в профиле**: явно определить, что data10 — «спецификация», и связать её ссылками с репозиториями-реализациями (daten30, daten6, in4n), чтобы устранить дублирование «динамических» тем.

## Варианты продолжения

**Сценарий 1: Legal-tech прототип «Widerspruch-генератор».**
Самый прямой путь: реализовать разделы 6, 8 и 10 как небольшой пакет. Парсер SGB IX уже спроектирован, сквозной пример (§29, §17) написан. Продукт — CLI/веб-форма: пользователь отвечает на вопросы (стаж, степень инвалидности, полученный Bescheid), rule engine выбирает применимые параграфы, Jinja2-шаблон собирает Widerspruch в DOCX. Это нишевый, но реально востребованный инструмент в немецком социальном праве, и он сразу проверяет главную гипотезу методологии — условную сборку документов из блоков.

**Сценарий 2: Универсальный «блочный» движок для info-репозиториев профиля.**
Отвязать методологию от юриспруденции и реализовать ядро (Block, Topic, Rule, Assembly) как переиспользуемую библиотеку. У svend4 десятки «info»-репозиториев с перекрывающимся markdown-контентом — ровно та проблема дублирования, с которой начинается раздел 1.1. Движок, который разбивает markdown на атомарные блоки, находит дубликаты по эмбеддингам и пересобирает страницы по правилам, превратил бы data10 из бумаги в инфраструктуру всего профиля (в том числе для строящегося вики-хаба info200).

**Сценарий 3: Живой «самособирающийся» дайджест (Smart Inserter как продукт).**
Реализовать только раздел 7 — SmartContentInserter с эскалацией детализации — как отдельный сервис: на вход поток заметок/новостей, на выходе автоматически растущее дерево тем, где короткие заметки становятся заголовками развёрнутых разделов. Это самая оригинальная идея документа, ей не нужен юридический домен и тяжёлый стек (достаточно эмбеддингов + дерева в SQLite). Хорошо сочетается с темой information (новости) и data70 (экспорт чатов).

**Сценарий 4: Оставить как справочник.**
Если реализация не планируется — честно оформить репозиторий как reference: переписать README, разбить документ на главы, снять галочки roadmap, добавить лицензию. Тогда data10 займёт нишу «настольной книги» для других проектов профиля без ложных ожиданий.

## Сочетания с другими репозиториями профиля

1. **data10 + infom (ГрафРАГ) = юридический GraphRAG-ассистент.** infom посвящён GraphRAG, data10 даёт готовую доменную модель графа (Block, APPLIES_IF, CONFLICTS_WITH, REFERENCES) и парсеры немецких законов. Соединение даёт уникальный продукт: retrieval не по чанкам, а по юридически осмысленным блокам с условными рёбрами — LLM-ассистент, который отвечает на вопрос «имею ли я право на Persönliches Budget?» проходом по графу параграфов и собирает обоснование с точными ссылками (§29 Abs. 2 SGB IX). Обычный RAG таких гарантий структуры не даёт.

2. **data10 + lorenzo (docs-toolkit + ~2815 md-файлов) = самособирающаяся база знаний.** lorenzo содержит огромный корпус markdown и Python-пакет docs-toolkit для работы с документацией. Методология data10 (атомарные блоки, топик-идентификация по эмбеддингам, эскалация детализации) применённая к этому корпусу превращает статическую свалку из 2815 файлов в динамическую базу: дубликаты схлопываются в один блок, страницы пересобираются под запрос с нужным уровнем детализации. Инновация — вики, которая реорганизует саму себя при добавлении контента.

3. **data10 + daten22/data20 (offline-приложения с SQLite FTS) = офлайн-справочник законодательства.** daten22 и data20 отрабатывают паттерн «встроенный бэкенд + полнотекстовый поиск без сети». Замена тяжёлого стека data10 (Neo4j/Elasticsearch) на SQLite FTS + таблицу рёбер даёт карманный юридический справочник: блоки SGB IX, условная навигация («ваш случай → применимые параграфы») и сборка заявлений полностью офлайн — актуально для консультантов и получателей соцпомощи без постоянного доступа к интернету.

4. **data10 + daten4 (динамический планировщик) = процессуальный навигатор.** Правила data10 описывают, *какие* параграфы применимы, планировщик daten4 — *в каком порядке действовать*. Вместе: система, которая из фактов дела строит не только документ, но и план действий со сроками (подать Antrag → дождаться Bescheid → в течение месяца Widerspruch), где каждый шаг подкреплён блоком закона. Получается «GPS по административной процедуре» — класс продуктов, которого на рынке почти нет.
