# Вопросы к daten22

## Вопрос 1. Какая из четырёх частей репозитория главная — контент MBTI, RAG, PseudoRAG или Android-приложение?

Репозиторий содержит четыре слабо связанных подпроекта, а описание на GitHub выделяет только Android-часть («поисковой оффлайн апп c SQLite FTS4»). От ответа зависит вся стратегия развития.

**Варианты ответов:**
- А. Главное — контент MBTI, код был экспериментом вокруг него.
- Б. Главное — PseudoRAG/16 архетипов, MBTI был лишь исходной метафорой.
- В. Главное — Android-приложение офлайн-поиска, остальное — материалы для него.
- Г. Это сознательная «лаборатория поиска», все части равноценны.

**Варианты дальнейших действий:**
- При А: развивать корпус (заполнить тонкие документы 29–42, закрыть дыру 43–49), код заморозить или вынести.
- При Б: выделить pseudorag в отдельный репозиторий/пакет (см. вариант 2 в рекомендациях), docs/50–54 перенести туда.
- При В: интегрировать корпус в приложение как предустановленную базу и выпустить APK-релиз.
- При Г: переписать корневой README как «зонтичный» с картой всех четырёх частей и их взаимными связями.

## Вопрос 2. Запускались ли RAG-система и Android-приложение целиком, и собирается ли Android-проект?

В репозитории нет ни CI, ни скриншотов, ни релизов, ни закоммиченной векторной базы. Для pseudorag есть артефакт запуска (examples/города_европы.*), для rag и android — никаких свидетельств работоспособности.

**Варианты ответов:**
- А. Да, всё запускалось локально и работало.
- Б. RAG запускался, Android-приложение не собиралось ни разу.
- В. Ничего кроме pseudorag не запускалось — код написан «на веру».

**Варианты дальнейших действий:**
- При А: зафиксировать доказательства — скриншоты Streamlit и приложения в README, APK в Releases, GitHub Actions со сборкой.
- При Б: настроить `./gradlew assembleDebug` в CI — это выявит ошибки компиляции без устройства; исправить и выпустить debug-APK.
- При В: провести смоук-тест всех трёх подсистем; учесть, что rag/requirements.txt (langchain 0.1.0) уже устарел и установка может потребовать правок.

## Вопрос 3. Планируется ли реализация уровней 3–4 «пирамиды» PseudoRAG (автозаполнение вопросников ответами)?

Документы docs/52–54 описывают 4-уровневую архитектуру («вопрос → 850 вопросов → 850 ответов → миллионы документов»), но код реализует только переход 1→2 (генерацию вопросов). Самая амбициозная часть концепции существует лишь на бумаге.

**Варианты ответов:**
- А. Да, планируется — через LLM-заполнение (каждый вопрос отправляется модели).
- Б. Да, но через связку с RAG-поиском по реальным корпусам.
- В. Нет, PseudoRAG задуман только как генератор структурированных анкет/чек-листов.
- Г. Концепция пересматривается / отложена.

**Варианты дальнейших действий:**
- При А: добавить модуль answer_filler с батч-запросами к LLM и кешированием; оценить стоимость (сотни вопросов × запрос).
- При Б: соединить pseudorag с rag/: вопросы архетипов идут как запросы в ChromaDB — это первая реальная интеграция двух подсистем репозитория.
- При В: сузить README (убрать обещания уровней 3–4), позиционировать как «structured brainstorming tool» и добавить экспорт в форматы анкет.
- При Г: зафиксировать статус в README, чтобы читатель не искал недостающие уровни.

**Варианты ответов:**

- Б. Блок 50+ сознательно отделён как «другая серия» (архетипы ≠ MBTI), пропуск — визуальная граница.
- В. Случайность/без замысла.

**Варианты дальнейших действий:**

- При В: перенумеровать 50–54 в 43–47 либо тоже перенести в pseudorag/ — навести порядок.

**Варианты ответов:**
- А. Контент — личный конспект для самообразования, публичность вторична.
- Б. Контент планировался как публичная свободная энциклопедия.
- В. Контент — сырьё для продукта (приложение/бот), а не самоценность.

**Варианты дальнейших действий:**
- При А: добавить дисклеймер «личный конспект», лицензию CC-BY-NC; риски минимальны.
- При Б: проверить пересечения с 16personalities (их описания и названия защищены), переписать спорные фрагменты своими словами, выбрать CC-лицензию, добавить список источников к каждому документу.
- При В: то же юридическое упорядочение плюс структурирование контента под машинное потребление (front-matter с метаданными типа, JSON-версии таблиц совместимости).
