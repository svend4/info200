## Серьёзные доработки

1. **Публикация docs-toolkit на PyPI** с нормальным релизным циклом (v0.3.0 → tagged release, RELEASE.md уже есть). Это закроет milestone «Опубликован MVP» и даст пакету жизнь вне монорепо.
2. **Консолидация модулей.** Провести ревизию ~500 подпакетов: слить _v2/_v3-дубликаты (access_log/access_log_v2, circuit_breaker*, семейство doc_audit), пометить deprecated, вынести редко используемые в extras-неймспейс. Цель — сократить публичную поверхность API до поддерживаемого ядра (25 модулей из API.md) + плагины.
3. **Выполнить отправку контактов.** 32 контакт-файла готовы с апреля, «написано 0/16». Это единственный milestone, который не решается кодом — и именно он определяет судьбу Svyazi 2.0 как коллаборативного проекта.
4. **Отделить docs-toolkit в собственный репозиторий** (или git subtree/submodule): пакет «универсальный», но живёт внутри исследовательского монорепо, из-за чего его невозможно ставить/форкать независимо, а CI гоняет тесты пакета при изменении доков.
5. **Доказать универсальность на втором корпусе:** прогнать docs-toolkit на чужом markdown-репозитории (например, другом репо профиля) и опубликовать кейс — сейчас заявление «работает на любом корпусе» не подтверждено.
6. **Закрыть отложенные фазы** (NPP hosted federation, OpenAI-gateway в самом пакете, marketplace) либо явно вынести их из roadmap в «не планируется».

## Варианты продолжения

**Сценарий 1: Продукт «docs-toolkit» (открытый фреймворк).**
Сфокусироваться на пакете: LICENSE, PyPI, отдельный репозиторий, консолидация API до ядра, 2–3 внешних кейса, сравнительные бенчмарки с LangChain/LlamaIndex (MIGRATING.md уже даёт маппинг — превратить его в маркетинговый козырь «то же самое, но stdlib-first и офлайн»). Целевая ниша реально пустует: локальный RAG-фреймворк без зависимостей для приватных баз знаний. Это самый прямой путь к внешним пользователям и звёздам.

**Сценарий 2: Запуск Svyazi 2.0 как живого сообщества.**
Исследовательская часть завершена (SCORING: 96% GO), прототип Knowledge OS работает (итерации 0–15, gateway, MCP). Недостающее звено — люди: отправить 32 подготовленных контакта авторам Habr-проектов, собрать 3–5 заинтересованных, поднять общий инстанс gateway и начать реальную федерацию знаний по NPP. Репозиторий из «исследования о сообществе» становится инфраструктурой сообщества. Риск: зависимость от ответов внешних людей; митигируется тем, что вся техника уже готова.

**Сценарий 3: Карьерный/портфельный трек.**
В docs/ лежит анализ 436 вакансий Anthropic с profile-mapping. Использовать lorenzo как флагман портфолио: written case study («как я построил RAG-фреймворк на 500 модулей и 38 тыс. тестов с агентной разработкой»), демо-видео gateway + MCP, статья на Хабр про методику «спринтовой» разработки с Claude Code. Побочный эффект — статья сама привлечёт авторов проектов, которым не отправлены контакты.

**Сценарий 4 (гибрид): «Knowledge OS as a template».**
Упаковать связку docs/ + scripts/ + skills/ как переиспользуемый шаблон («создай свой Knowledge OS за час»): cookiecutter-шаблон + GitHub Action (action.yml уже существует) + туториал. Каждый из 60 info-репозиториев профиля — потенциальный полигон; внешние пользователи получают то, что LangChain не даёт: полный конвейер от MHTML-выгрузки до MCP-сервера.

## Сочетания с другими репозиториями профиля

1. **lorenzo + info200 (хаб вики) = самонаполняющаяся вики профиля.** info200 задуман как хаб вики по 61 репозиторию, но почти пуст. Скрипты lorenzo (improve_summary, improve_crosslink, improve_health, CARD_GRAPH с PageRank) — готовый конвейер: направить их на корпус вики-страниц info200 и получить автогенерируемые индексы, глоссарий, граф связей репозиториев, HEALTH-балл всего профиля и RSS-фид изменений. Инновация: вики, которая сама себя аудитирует и находит «сиротские» и устаревшие страницы (improve_decay_checker) по всему профилю.

2. **lorenzo + infom (ГрафРАГ) + in4n (динамический информационный граф) = гибридный Graph-RAG движок.** У lorenzo уже есть TripleStore на SQLite с мини-DSL (`"py" uses ?x`) и PageRank-граф карточек; infom исследует GraphRAG, in4n — динамические графы. Слияние даёт то, чего нет в mainstream: локальный (stdlib-first) GraphRAG с **эволюционирующим во времени** графом (timetravel/ в lorenzo уже умеет git-исторические запросы) — «как менялся ответ на вопрос X по мере роста базы». Ни LangChain, ни LlamaIndex такого из коробки не дают.

3. **lorenzo + info40 (AI Agent Orchestration Platform) = оркестрация с измеримым качеством.** info40 заявляет production-платформу оркестрации агентов; lorenzo даёт eval-слой (golden datasets P/R/F1, A/B-эксперименты, Wilson confidence, bandit_ask) и телеметрию (OTel + Prometheus). Комбинация — платформа оркестрации, где каждый агентный workflow автоматически прогоняется через golden-set и A/B, а маршрутизация между агентами делается multi-armed bandit'ом по фактическому качеству. Это ниша «LLMOps для локальных агентов», практически не занятая.

4. **lorenzo + daten22/data20 (офлайн-приложения с SQLite FTS) = офлайн-RAG для мобильных/embedded.** daten22 использует SQLite FTS4 для офлайн-поиска; lorenzo — «SQLite as backbone» (vectors, jobs, audit). Перенос облегчённого ядра docstoolkit (frontmatter + BM25 + TF-IDF, без FastAPI) поверх FTS-хранилища daten22 даёт полностью офлайн карманную базу знаний с RAG-ответами без единого сетевого запроса — уникальное сочетание для полевых/приватных сценариев.

5. **lorenzo + universal-file-storage-mcp = федерация MCP-знаний.** У lorenzo есть свой MCP-сервер по базе знаний, у universal-file-storage-mcp — универсальное файловое хранилище для Claude. Объединение: MCP-сервер, который не только отдаёт файлы, но и индексирует их конвейером lorenzo (карточки, promote, граф), превращая любое подключённое хранилище в самоорганизующуюся базу знаний Claude.
