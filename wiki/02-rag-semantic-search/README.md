# RAG и семантический поиск по базам знаний

## О теме

Тема объединяет пять репозиториев, которые с разных сторон подступаются к одной задаче: **надстроить поиск с извлечением (RAG) и семантический поиск над крупным корпусом русскоязычных документов**. Здесь собраны и зрелый рабочий фреймворк ([lorenzo](lorenzo/README.md) с его docs-toolkit), и «псевдо-RAG» движки на авторских онтологиях ([info3](info3/README.md) с 4-уровневыми «гуманитарными формулами», [daten22](daten22/README.md) с 16 «информационными архетипами» и MBTI-поиском), и FastAPI-шлюзы, дающие нейросетям HTTP-доступ к общему корпусу знаний ([info10](info10/README.md), [daten](daten/README.md)). Фактически это лаборатория одного автора вокруг собственной базы знаний Svyazi 2.0: одни репозитории поставляют корпус и движок, другие — обёртку и интерфейс.

Сквозная идея темы — **local-first / stdlib-first RAG**: работа офлайн, минимум внешних зависимостей, graceful degradation при отсутствии API-ключей и тяжёлых библиотек, честная маркировка спекулятивного кода. Всё это часть более широкого профиля svend4, где рядом лежат темы про ИИ-агентов, графы знаний и офлайн-приложения; RAG-тема служит для них «поисковым слоем» — способом достать нужный фрагмент из тысяч markdown-файлов. Обратная сторона зрелости неровная: только один репозиторий доведён до состояния настоящего работающего продукта, остальные — от честно завершённого эксперимента до неработоспособной из коробки заготовки.

## Лидеры и аутсайдеры

**Лидер — [lorenzo](lorenzo/README.md) (4/5).** Единственный в теме, где RAG — это не концепт, а работающий код: прочитанный `rag/pipeline.py` (582 строки), `mcp_server.py`, `gateway.py` — качественные, документированные, с fallback'ами. Есть настоящий CI (6 джобов + авто-PR метрик), исключительная документация (API, 5 ADR, COOKBOOK, гайд миграции с LangChain/LlamaIndex), дисциплина процесса с фазами и хешами коммитов. Это ядро всей темы: именно его docs-toolkit и корпус используют или хотят использовать остальные репозитории.

**Крепкий второй эшелон — [info3](info3/README.md) и [daten22](daten22/README.md) (обе 3/5).** Обе несут оригинальную авторскую концепцию (4 уровня абстракции у info3, 16 информационных архетипов PseudoRAG у daten22) и большой связный русскоязычный корпус, пригодный как готовый датасет для поисковых экспериментов. info3 даёт полный вертикальный срез (данные → поиск → API → real-time → UI) и честно помечает фантастику в докстрингах; daten22 предлагает сразу три подхода к поиску в одном репо (векторный RAG, онтологический PseudoRAG, классический SQLite FTS4). Планку им сбивают ноль тестов/CI и неподтверждённая работоспособность тяжёлого стека.

**Аутсайдеры — [daten](daten/README.md) (2/5) и [info10](info10/README.md) (1/5).** daten выглядит внушительно (современный React-фронтенд, проработанный деплой), но функциональное ядро — заглушки: `SearchService.search()` и `semantic_search()` возвращают `[]`, БД и граф не подключены, проект спит ~6,5 месяцев. info10 — самый сырой: код падает с `ModuleNotFoundError`, потому что ключевая зависимость `docstoolkit` не в репозитории и не в requirements; вдобавок дыры безопасности (`/api/git/write` без аутентификации, path traversal, токен в push-URL) и мусор вроде дубликата файла с пробелом в имени. Обе фактически заготовки-тупики, ценные скорее как замысел, чем как продукт.

## Общие сильные стороны темы

- **Готовые русскоязычные корпуса.** Почти в каждом репо лежит крупный связный markdown-корпус (Svyazi 2.0 у lorenzo, афоризмы/формулы у info3, ~1 МБ MBTI-контента у daten22), пригодный как датасет для RAG-экспериментов.
- **Local-first и graceful degradation.** Ставка на stdlib-first и офлайн-работу: базовая установка lorenzo без зависимостей, опциональные тяжёлые библиотеки в info3 и daten22, деградация RAG без API-ключа.
- **Честные самоаудиты и маркировка спекулятивного кода.** lorenzo с фазами и exit-критериями, info3 с пометками «Reality: 1–30%» в докстрингах, daten с AUDIT_ANALYSIS/STATUS, честно выявившими разрыв документация/код — редкая для пет-проектов дисциплина.
- **Оригинальные авторские концепции.** 4-уровневые «гуманитарные формулы» info3 и 16 «информационных архетипов» PseudoRAG daten22 — не копии LangChain/LlamaIndex, а собственные онтологии поиска.
- **Один по-настоящему рабочий фреймворк.** lorenzo с CI, тестами и обширной документацией задаёт теме реальный технический потолок и служит опорой для остальных.

## Общие слабые места и чего не хватает

- **Отсутствие LICENSE почти везде.** У lorenzo заявлен MIT (бейдж + pyproject), но файла нет; у info3, info10, daten, daten22 лицензии нет вовсе — блокер любого внешнего использования.
- **Слабые или нулевые тесты и CI.** У info3 — ноль тестов при ~24,7 тыс. строк; у info10 нет CI; у daten CI ссылается на переименованный каталог и нерабочий; у daten22 нет ни CI, ни релизов, ни закоммиченной векторной базы.
- **Документация опережает код и метрический дрейф.** Заявленные функции не подтверждаются кодом (MCP «13 серверов» у info10, «полностью готово»), расхождения цифр между README и самоаудитами (lorenzo, info3, daten22), устаревшие корневые README.
- **Ноль внешней валидации.** Ни PyPI, ни GitHub Releases, единичные звёзды, нет внешних пользователей и issues; универсальность движков не подтверждена ни одним чужим кейсом.
- **Неработоспособность из коробки и заглушки.** info10 падает без `docstoolkit`; ядро поиска daten — пустые заглушки; части daten22 не интегрированы (Android не ищет по базе MBTI, PseudoRAG не связан с RAG).
- **Дыры безопасности.** `/api/git/write` и `/api/download` без аутентификации + path traversal у info10; захардкоженные пароли `admin123`/`demo123` и дефолтный SECRET_KEY у daten.
- **Спячка.** daten не трогали ~6,5 месяцев, daten22 — ~6 месяцев после однонедельного спринта; активен только lorenzo.

## Дубли и пересечения

- **info10 — это буквально шлюз к lorenzo.** info10 импортирует `docstoolkit.rag` из lorenzo и оборачивает его в HTTP/Docker; без корпуса и пакета lorenzo он не запускается. Это не независимый проект, а недоделанная обёртка вокруг чужого ядра — логичнее втянуть его в lorenzo как модуль `gateway`, а не держать отдельным репозиторием.
- **Два FastAPI-шлюза над корпусом.** info10 и daten параллельно решают одну задачу — «дать HTTP/деплой-фасад над базой знаний» (FastAPI + Docker + конфиги деплоя). Различаются доменом и стадией, но архитектурно дублируют друг друга; стоило бы выбрать одну обёртку.
- **Два «псевдо-RAG» движка.** info3 (движок по 4-уровневым формулам) и daten22 (PseudoRAG по 16 архетипам) независимо изобретают онтологический поиск поверх русскоязычного markdown-корпуса. Разные предметные области (гуманитарные качества vs MBTI), но одна идея и один класс кода — кандидаты на единый движок с подключаемыми онтологиями.
- **Офлайн-поиск на SQLite FTS.** Рабочий FTS4 живёт в Android-части daten22, а в daten ровно эта функция — заглушка. Один и тот же кирпич реализован в одном репо и отсутствует в соседнем.

## Идеи сочетаний внутри темы

1. **lorenzo + info10 = завершённый DAF-шлюз.** Довести исходный замысел info10: lorenzo отдаёт пакет `docstoolkit` и корпус Svyazi 2.0, info10 — HTTP/Docker-обёртку с git-записью. Результат — самообновляющаяся база знаний с двусторонним API (чтение через OpenAI-совместимый `/v1/chat/completions`, запись через `/api/git/write`) для любых нейросетей. Обязательное условие — закрыть дыры безопасности info10 (аутентификация, защита от path traversal).

2. **daten + daten22 = офлайн информационная ОС.** Пересадить рабочий полнотекстовый поиск на SQLite FTS4 из daten22 в пустой `SearchService` из daten, взять готовый React-UI daten — и получить MVP «ОС знаний» без PostgreSQL/Redis, в один процесс и полностью офлайн. Каждый репо в одиночку до этого не дотягивает: у одного UI без ядра, у другого ядро без интерфейса.

3. **info3 + daten22 = единый онтологический псевдо-RAG.** Слить два авторских движка в один каркас с подключаемыми онтологиями: 4-уровневые формулы info3 и 16 архетипов daten22 становятся сменными «схемами разметки» над общим индексом, а корпуса афоризмов и MBTI — двумя первыми предметными областями. Плюс лёгкие эмбеддинги info3 и офлайн-FTS daten22 дают гибридный поиск «по смыслу + по точному совпадению» без интернета.

4. **lorenzo → облегчённое офлайн-ядро для daten22.** Вынести из docs-toolkit lorenzo минимальное ядро (frontmatter + BM25 + TF-IDF без FastAPI) и положить его поверх SQLite-хранилища daten22 — карманный RAG, дающий ответы без единого сетевого запроса, для полевых и приватных сценариев. Так зрелый код lorenzo получает реальный офлайн-кейс, а daten22 — проверенный движок вместо самописного.
