# Сочетания и инновации

> **Принцип страницы.** Когда обычное сочетается с обычным новым образом — получается уникальное. Ни один из 61 репозитория профиля [svend4](https://github.com/svend4) по отдельности не является прорывом: средняя зрелость 2.28, 32 репо помечены «экспериментальный», 8 — «почти пустой». Но профиль устроен как **набор взаимодополняющих полуфабрикатов**: сильные «движки» (Q6-геометрия, docs-toolkit, GraphRAG, оркестраторы, офлайн-FTS, каталоги IFOS) и множество «контентов» и «спецификаций» без движка под ними. Ценность рождается на стыках. Ниже — 20 лучших кросс-профильных сочетаний, собранных из полей `idei_sochetanij` всех репозиториев, отфильтрованных и объединённых.

Каждое сочетание: **что берём** (репозитории профиля), **что получается** (конкретный продукт), **почему инновационно** (что нового относительно каждого исходного репо), **сложность** и **первый шаг**. Ссылки ведут на страницы вики; на GitHub — `https://github.com/svend4/<repo>`.

## Флагманские сочетания (сигнатурные активы профиля)

### 1. Вычислимый И-Цзин: Q6-геометрия как ядро генеративной модели

**Что берём:** [pro2](03-q6-hypercube-knowledge-graphs/pro2/README.md) (трансформеры с геометрическим индуктивным смещением на 64 гексаграммах Q6, ~90 K строк, 1971 тест) + [meta](03-q6-hypercube-knowledge-graphs/meta/README.md) (строгая алгебра Q6: hexcore, hexsym, hexiching, марковские цепи hexstat, ~8,5 тыс. тестов) + [infon](10-systems-network-ai/infon/README.md) (у него уже есть адаптер `ai/adapters/yijing_brain.py` и байт-идентичный `SceneVector`).

**Что получается:** генеративная модель, у которой пространство состояний — не токены, а вершины гиперкуба Q6 со строгой проверяемой алгеброй. Единственный «цифровой И-Цзин» с математической подложкой и тысячами тестов. Подключив pro2 как живой `BRAIN_URL`-режиссёр infon, получаем первый генеративный метаверс, управляемый И-Цзин-трансформером: «гадание» буквально строит 3D-мир, по которому ходят терминалом.

**Почему инновационно:** pro2 в одиночку — исследовательский ML-каркас без строгой семантики состояний; meta — библиотека математики без применения к ML; infon — семантический кодек без «мозга». Вместе — вычислимая символьная система, которой нет ни у кого.

**Сложность:** высокая. **Первый шаг:** подставить `meta.hexcore`/`hexiching` как алгебру переходов состояний за `e2_inference` из pro2 и провалидировать на общем `SceneVector`.

### 2. Дискретный геометрический GraphRAG (retrieval прогулкой по гиперкубу)

**Что берём:** [infom](03-q6-hypercube-knowledge-graphs/infom/README.md) (GraphRAG на чистом Python с Q6-адресацией) + [pro2](03-q6-hypercube-knowledge-graphs/pro2/README.md) (модель, дающая каждому документу 6-битный Q6-адрес) + [lorenzo](02-rag-semantic-search/lorenzo/README.md) (корпус ~2,8 тыс. md-файлов + docs-toolkit).

**Что получается:** каждый документ lorenzo получает Q6-адрес (одну из 64 гексаграмм); узлы графа квантуются в 64 архетипа, рёбра типизируются по графу Бян-Гуа (флип одного бита = минимальная смысловая мутация), retrieval = walk по гиперкубу вместо ANN-поиска. Объяснимый офлайн-CPU-гибрид символьного и векторного поиска и одновременно первый **не синтетический** бенчмарк для Q6-эмбеддингов.

**Почему инновационно:** у lorenzo есть BM25/TF-IDF, но нет геометрического индекса; у infom граф с обычными узлами; у pro2 Q6-геометрия без реального корпуса. Вместе — навигационная карта огромного корпуса, которой нет ни в LangChain, ни в LlamaIndex.

**Сложность:** высокая. **Первый шаг:** прогнать `e2_inference` по корпусу lorenzo, предвычислить таблицу Хэмминг-соседей, подключить как retrieval-бэкенд infom.

### 3. Живой самоаудирующийся атлас профиля (61 репо)

**Что берём:** [nautilus](03-q6-hypercube-knowledge-graphs/nautilus/README.md) (мета-протокол федерации, `scan_repo.py`/`generate_passport.py`, sync-бот) + [info200](14-empty-placeholders/info200/README.md) (пустой хаб вики — эта самая энциклопедия) + [lorenzo](02-rag-semantic-search/lorenzo/README.md) (docs-toolkit: `improve_summary`, `crosslink`, `health`, `CARD_GRAPH` с PageRank, `decay_checker`) + [infom](03-q6-hypercube-knowledge-graphs/infom/README.md) (GraphRAG для ответов по вики).

**Что получается:** nautilus еженедельно сканирует профиль и генерирует страницы вики в info200, docs-toolkit lorenzo валидирует структуру, строит индексы, граф связей репозиториев и HEALTH-балл, `decay_checker` помечает устаревшие страницы, а infom отвечает на вопросы вида «какие репо про офлайн-поиск и с чем их скрестить» со ссылками. Q6-карта и D3-граф становятся интерактивным оглавлением. Вики, которая документирует и аудитирует себя сама.

**Почему инновационно:** info200 — пустой хаб; nautilus — протокол федерации без наполнения; lorenzo — инструментарий без внешних пользователей. Вместе — живой атлас вместо ручной документации, самоподдерживающийся.

**Сложность:** средняя (используются два самых зрелых репо профиля, оба зрелость 4). **Первый шаг:** направить `health`/`crosslink` docs-toolkit на страницы `wiki/_data`, собрать `CARD_GRAPH` по 61 репо.

### 4. Соцправовой комбайн для Persönliches Budget (Германия)

**Что берём:** [daten20](07-document-systems-legaltech/daten20/README.md) (DMS-калькулятор услуг персонального бюджета по правилам соцстрахования) + [soz150](07-document-systems-legaltech/soz150/README.md) (Writing OS с CAGE-пайплайном и генерацией Widerspruch) + [data4](14-empty-placeholders/data4/README.md) (заготовка приложения бюджета получателя) + [infom](03-q6-hypercube-knowledge-graphs/infom/README.md) + сырьё из [data70](04-knowledge-bases-wiki/data70/README.md) (шаблоны SGB IX/XII, медицинские письма, 300+ диалогов по соцправу).

**Что получается:** замкнутый цикл «расчёт бюджета (data4) → подбор услуг с прозрачной калькуляцией себестоимости часа (daten20) → заявление и отслеживание Bescheid → автоматический Widerspruch с аргументами из базы ошибок MDK (soz150)», а infom реализует юридический GraphRAG «нормы SGB ↔ жизненные ситуации ↔ шаблоны Widerspruch/Klage» с трассировкой источников (§29 Abs. 2 SGB IX).

**Почему инновационно:** daten20 считает только сторону поставщика, data4 — только бюджет получателя, soz150 — только правовую борьбу. Вместе замыкается петля, которую ни один репо не даёт поодиночке. Такого продукта для получателей ПБ в Германии нет, русскоязычных аналогов нет.

**Сложность:** высокая. **Первый шаг:** собрать в infom граф «норма ↔ ситуация ↔ шаблон» из roadmap soz150 и корпуса data70.

### 5. IFOS Live Registry: исполняемая B2B-OS (каталогизация → исполнение)

**Что берём:** [daten40](06-cataloguing-rationalization/daten40/README.md) (корпус IFOS: 210 OS_PACK-блоков с паспортами, OpenAPI-контрактами, уровнями доверия L0–L5, формат Recipe) + [daten14](06-cataloguing-rationalization/daten14/README.md) / [daten12](06-cataloguing-rationalization/daten12/README.md) (граф совместимости BIOS-I, словарь функций, YAML-макросы) + [info40](01-ai-agents-orchestration/info40/README.md) (оркестратор с DAG-исполнением) + [infom](03-q6-hypercube-knowledge-graphs/infom/README.md).

**Что получается:** оркестратор выбирает действия не из ad-hoc-списка инструментов, а из типизированного реестра с паспортами и уровнями доверия; исполняет декларативные YAML-макросы и кластеры («одна кнопка = развёрнутый бизнес-процесс»); infom превращает граф совместимости в объяснимый GraphRAG, отвечающий «какой стек собрать под задачу X» с доказательством-путём. Реализация Layer 1 + Layer 6 IFOS на готовой платформе.

**Почему инновационно:** daten40/daten14/daten12 — «бумажная архитектура» без рантайма; info40 — рантайм без предметной модели и без реестра доверия. Вместе — агенты собирают решения из проверенных комбинаций вместо свободной генерации кода.

**Сложность:** высокая. **Первый шаг:** превратить формат Recipe daten40 (`steps`/`secrets`/`evidence_plan`/`on_error`) в DSL, который исполняет info40; загрузить поле `Depends on` в infom.

## Оркестрация и надёжность агентов

### 6. Оркестратор с криптографически воспроизводимыми запусками

**Что берём:** [meta1](10-systems-network-ai/meta1/README.md) (Continuum — детерминированный рантайм для ИИ-кода, run-queue/checkpoint/replay) + [info40](01-ai-agents-orchestration/info40/README.md) (каркас оркестрации: Registry, DAG, метрики) + [info7](01-ai-agents-orchestration/info7/README.md) (enterprise-слой: multi-tenancy, RBAC, audit-log, 5-уровневая иерархия).

**Что получается:** каждый шаг агента — `ExecutionPlan` с sha256-хэшами артефактов, lineage и repair-cascade; аудируемый след решений ИИ с бит-в-бит replay любого прогона; сверху — мультиарендность и RBAC из коробки.

**Почему инновационно:** info40 и info7 — витрины на in-memory-заглушках, объявленные «production-ready»; meta1 — рантайм без агентного применения. Вместе — воспроизводимая мультиагентная оркестрация, которой нет ни у одного популярного фреймворка. Заодно исчезает дублирование двух оркестраторов профиля.

**Сложность:** высокая. **Первый шаг:** обернуть шаги DAG-исполнителя info40 в run-queue/checkpoint Continuum.

### 7. Оркестратор поверх каталога проверенных навыков (method DB + trust layer)

**Что берём:** [info4](05-claude-code-skills-mcp/info4/README.md) (~101 каталогизированный скилл/метод с иерархией уровней) + [data30](06-cataloguing-rationalization/data30/README.md) (система доверия: паспорта функций, verified-usage из логов, ранжирование `ranking_v1`) + [daten40](06-cataloguing-rationalization/daten40/README.md) (типизированный реестр с уровнями доверия) + [info40](01-ai-agents-orchestration/info40/README.md).

**Что получается:** перед декомпозицией задачи оркестратор запрашивает Method DB и получает готовые «рецепты», выбирая инструменты по подтверждённой практикой репутации, а не по промпту с нуля. «Рейтинг доверия для tool-calling» с воспроизводимыми планами и метриками реальной пользы каждого скилла.

**Почему инновационно:** info4/data30/daten40 — каталоги без исполнителя; ни один оркестратор не имеет репутационного реестра инструментов. Вместе — новая ниша skill-registry с доверием.

**Сложность:** средняя-высокая. **Первый шаг:** отдать Method DB info4 + ранжирование data30 как бэкенд подбора инструментов планировщику info40.

### 8. Бенчмарки агентов на реальных, а не синтетических артефактах

**Что берём:** [meta](03-q6-hypercube-knowledge-graphs/meta/README.md) (реестр q6ctl: 42 CLI-модуля с JSON-выводом и математически проверяемыми ответами) + [daten2](11-ecommerce-shops/daten2/README.md) (7 уровней одного магазина с общими API-тестами) + [meta4](11-ecommerce-shops/meta4/README.md) (олимпиадный солвер с брутфорс-верификатором) + [daten20](07-document-systems-legaltech/daten20/README.md) (72 ИИ-выращенных модуля с известными патологиями генерации).

**Что получается:** батарея измеримых бенчмарков агентов: многошаговый tool-use с проверяемым ответом (meta), «мигрируй магазин с уровня N на N+1 без изменения поведения» с проверкой одинаковыми тестами (daten2), самопроверяющийся задачник оптимизации (meta4), размеченный датасет патологий ИИ-генерации — версионная инфляция, расхождения README↔docstring (daten20).

**Почему инновационно:** агентные бенчмарки обычно синтетические; здесь у каждой задачи есть доказуемая истина на реальных артефактах, которые профиль уже построил (daten2 на 100% написан Claude через PR).

**Сложность:** средняя. **Первый шаг:** отдать реестр q6ctl как каталог инструментов + набор задач с математически проверяемыми ответами, оценить любого агента.

## Q6, графы знаний и офлайн-поиск

### 9. Семантический офлайн-поиск без сервера через 6-битный Q6-адрес

**Что берём:** [pro2](03-q6-hypercube-knowledge-graphs/pro2/README.md) (модель 19 МБ на CPU, выдающая гексаграмму 0–63) + [daten22](02-rag-semantic-search/daten22/README.md) (офлайн-поиск на SQLite FTS4) + [meta](03-q6-hypercube-knowledge-graphs/meta/README.md) (алгебра Хэмминг-соседства).

**Что получается:** к FTS-индексу добавляется колонка с 6-битной гексаграммой документа; семантические соседи находятся простым SQL по предвычисленной таблице Хэмминг-соседей. Семантический поиск по смыслу без сервера, без эмбеддинг-базы и без GPU — полностью офлайн, в одном SQLite-файле.

**Почему инновационно:** daten22 умеет только лексический FTS; pro2 обычно требует ML-инфраструктуры. Вместе — офлайн-поиск с символьным семантическим индексом, чего не даёт ни один продукт.

**Сложность:** средняя. **Первый шаг:** предвычислить Q6-адрес на документ, добавить колонку `q6` и таблицу Хэмминг-соседей в схему daten22.

### 10. Универсальный офлайн-конструктор справочников (контент × индекс × клиент)

**Что берём:** [daten22](02-rag-semantic-search/daten22/README.md) (Android-клиент с FTS4) + [data20](12-offline-apps-pwa/data20/README.md) (встраиваемый бэкенд + 57 инструментов индексации) + любой контент-корпус: [info](04-knowledge-bases-wiki/info/README.md) (символика/параллели), [info3](02-rag-semantic-search/info3/README.md) (афоризмы/формулы), [data2](13-robotics-motion/data2/README.md) (310 томов ЕТД).

**Что получается:** «выпекаемая» офлайн-энциклопедия — любой корпус профиля компилируется в один SQLite-файл с полнотекстовым поиском и работает на телефоне без Python-рантайма (снимает проблему 100 МБ APK с Chaquopy). Конструктор, куда подключается медицина, магазины, символика.

**Почему инновационно:** daten22 — единственный MBTI-корпус; data20 — гигантский движок при трёх статьях; контент-репо — мёртвый markdown. Вместе — мост «контент → продукт»; прямой ответ на главную боль MANIFEST data70 (архивы гибли при госпитализации и войне) — максимальная живучесть знаний офлайн.

**Сложность:** низкая-средняя (наименее трудоёмкое сочетание с наибольшим переиспользованием). **Первый шаг:** написать один адаптер «markdown-корпус → схема FTS4 daten22» и «выпечь» info (39 документов) первым продуктом.

### 11. Визуальный отладчик GraphRAG (наблюдаемость ретривала)

**Что берём:** [in4n](03-q6-hypercube-knowledge-graphs/in4n/README.md) (InfoAquarium — живой граф с физикой, ACO-феромонами и агентами-путешественниками) + [infom](03-q6-hypercube-knowledge-graphs/infom/README.md) (GraphRAG) + [data7](01-ai-agents-orchestration/data7/README.md) (честная TSP/ACO-механика).

**Что получается:** запрос = путешественник, обход графа при извлечении контекста = маршрут, частота попадания узла в ответы = яркость феромона. Видно, какие области знаний «протоптаны» запросами, а какие мертвы. Плюс готовый интерактивный тренажёр муравьиной оптимизации TSP.

**Почему инновационно:** визуального слоя наблюдаемости такого рода нет ни в одном популярном GraphRAG-стеке; in4n — арт-симуляция без прикладной задачи; infom — движок без визуализации. Вместе — редкий наглядный отладчик и демо графового RAG.

**Сложность:** средняя. **Первый шаг:** передавать трассы ретривала infom в in4n как обновления феромонов на общем graph JSON.

### 12. Второй мозг на реальном личном корпусе + воспроизводимый цифровой двойник

**Что берём:** [data70](04-knowledge-bases-wiki/data70/README.md) (1105 диалогов ChatGPT, ~78 МБ, готовый граф 197 нод / 576 рёбер) + [infom](03-q6-hypercube-knowledge-graphs/infom/README.md) (GraphRAG-движок) + [data50](04-knowledge-bases-wiki/data50/README.md) (разбор кейса ИИ-клона CTO с метриками совпадения стиля).

**Что получается:** полная индексация корпуса в персистентный граф с реальными эмбеддингами — личный архив становится запрашиваемым «вторым мозгом», а сообщества графа автоматически восстанавливают ручной тематический каталог. Поверх — воспроизводимый цифровой двойник с замерами совпадения стиля (как 50 %→85–90 % в исходной статье) и дневником репликации.

**Почему инновационно:** data70 даёт корпус без движка (пустые `embedding:[]`); infom — движок без корпуса; data50 — методология без данных. Вместе — открытый кейс «второго мозга» на реальном многолетнем корпусе с авторской разметкой тем, которого нет в публичных примерах.

**Сложность:** средняя. **Первый шаг:** довести пайплайн data70→infom до конца (реальные эмбеддинги вместо пустых, полнотекстовый гибрид-RAG).

### 13. Реконструкция документов на кодах коррекции ошибок + автономный архив
