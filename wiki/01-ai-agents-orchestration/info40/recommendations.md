# Рекомендации по info40

## Быстрые улучшения

1. **Честный README**: убрать «Production-ready» и «Проект готов к развертыванию в production!», добавить раздел «Текущий статус: прототип» с перечнем заглушек (in-memory storage, mock-auth, имитация агентов). Это дешевле всего и сразу снимает главную претензию аудита.
2. **Исправить цифры**: в README/PROJECT_SUMMARY/CHANGELOG заменить «40 000+ строк» на ~26–27 тыс., «15 000+ строк» концепт-дока на ~1 000, привести дерево каталогов PROJECT_SUMMARY в соответствие с реальным (`k8s/`, `docker/requirements/`, плоские Dockerfile, фактические имена тестов).
3. **Починить CI** (`.github/workflows/ci.yml`): заменить `mypy src/` и `--cov=src` на реальные пути (`api/`, `sdk/`, `workers/`, `cli/`), чтобы пайплайн стал зелёным; убрать несуществующие шаги.
4. **Синхронизировать тесты с API**: в `tests/unit/test_registry_service.py` перейти на вложенную модель `pricing`, ожидать 201 вместо 200, заменить `sys.path`-хак на нормальный пакетный импорт (`pip install -e`).
5. **Добавить недостающий `helm/agent-platform/values-production.yaml`** или убрать его упоминание.
6. **Пометить use-cases как вымышленные сценарии** (дисклеймер в начале каждого файла) — сейчас «метрики» читаются как отчёт о реальных внедрениях.
7. Вынести общие Pydantic-модели в пакет `common/` (или в SDK) и импортировать во всех сервисах — остановить расползание схем.

## Серьёзные доработки

1. **Подключить PostgreSQL по-настоящему**: schema.sql уже хороша — добавить слой репозиториев (asyncpg/SQLAlchemy) хотя бы в Registry Service и заменить `agents_db: Dict` на реальные запросы. Один сервис на реальной БД ценнее четырёх на словарях.
2. **Реализовать сквозной happy path**: задача через Gateway → декомпозиция в Orchestrator → публикация подзадач в RabbitMQ → получение воркером → выполнение (пусть даже простым LLM-вызовом) → агрегация результата. Один работающий E2E-сценарий превратит витрину в продукт.
3. **Настоящая аутентификация**: JWT + таблица api_keys уже есть в схеме — реализовать выдачу и проверку ключей.
4. **Реальный агент вместо `asyncio.sleep`**: подключить хотя бы один агент к Claude API (модель уже фигурирует в коде: `claude-sonnet-4.5`) для задач типа «сгенерируй код/суммаризуй текст».
5. **Интеграционные тесты в docker-compose**: поднять стек и гонять tests/integration против живых сервисов; включить в CI.
6. Сократить инфраструктурную избыточность: пока нет реальных пользователей, k8s+Helm+HPA на 100 подов — балласт; оставить docker-compose как основной путь запуска.

## Варианты продолжения

**1. Довести до работающего минимального продукта (MVP-путь).**
Сфокусироваться не на широте, а на глубине: выбросить marketplace и биллинг, оставить Registry + Orchestrator + один реальный агент на Claude API + PostgreSQL. Цель — «пользователь отправляет задачу, три агента параллельно её решают, результат агрегируется». Это 2–4 недели работы поверх готового каркаса, после чего проект перестаёт быть витриной. Marketplace возвращать только после того, как оркестрация реально работает.

**2. Переориентировать в открытый учебный курс «платформа с нуля».**
Репозиторий уже идеален как учебный материал: в нём есть все слои современного бэкенда (FastAPI → SQL → Docker → k8s → Helm → Prometheus → CI). Оформить как пошаговый курс/книгу: каждая глава — «оживление» одного слоя (глава 3: заменяем in-memory на PostgreSQL; глава 5: подключаем RabbitMQ). Честная маркировка «прототип» здесь становится достоинством, а не недостатком.

**3. Сузить до «оркестратора для Claude Code / локальных агентов».**
Вместо абстрактного глобального marketplace — конкретная ниша: локальная оркестрация нескольких Claude Code-сессий/субагентов на машине или в домашнем кластере разработчика. Декомпозиция задач и DAG из orchestrator_service переиспользуются напрямую; RabbitMQ заменяется на простую очередь; появляется реальный пользователь — сам автор профиля, у которого десятки репозиториев обслуживаются агентами.

**4. Заморозить как концепт-архив.**
Если развивать не планируется — привести документацию к честности (быстрые улучшения 1–2, 6), поставить статус «archived/concept» и ссылаться на репозиторий как на референс-архитектуру из хаба info200. Минимум усилий, максимум порядочности.

## Сочетания с другими репозиториями профиля

1. **info40 + info100 («лаборатория агентов») + info7 («оркестратор и бот») = действующий полигон мультиагентной оркестрации.** info40 даёт инженерный каркас (API, DAG-декомпозиция, метрики, деплой), info100 — экспериментальную площадку и сценарии агентов, info7 — уже существующий оркестратор с ботом как первый «реальный агент» платформы. Вместо трёх разрозненных прототипов — один стек: боты из info7 регистрируются в Registry info40, эксперименты info100 становятся его use-cases. Уникальность: у профиля появляется первая end-to-end работающая агентная система, а не набор описаний.

2. **info40 + daten4 («динамический планировщик») = оркестратор с умным планированием вместо эвристик.** Слабейшее место info40 — примитивная декомпозиция «подзадача на capability». Планировщик daten4 может стать мозгом Orchestrator Service: строить план с учётом зависимостей, сроков и бюджета, а DAG-исполнитель info40 — его runtime. Получается редкая связка «planner + executor» — то, чего нет в большинстве open-source агентных фреймворков, где планирование и исполнение смешаны.

3. **info40 + in4 («домашние AI-кластеры») = волонтёрский пул агентов на домашнем железе.** Самая оригинальная идея info40 — волонтёрский пул простаивающих агентов (BOINC для ИИ) — сейчас существует только на бумаге. in4 описывает домашние AI-кластеры; соединение даёт конкретную инкарнацию: домашние узлы поднимают AgentWorker из info40, регистрируются в Registry со `pricing.mode = volunteer`, и k8s-манифесты info40 впервые получают целевую площадку. Инновация: распределённая любительская сеть AI-агентов для общественных задач.

4. **info40 + universal-file-storage-mcp = обмен артефактами между агентами через MCP.** У info40 не решён вопрос передачи результатов между подзадачами (сейчас — JSON в памяти). MCP-сервер файлового хранилища из universal-file-storage-mcp становится стандартным «контекст-стором» платформы: агенты пишут и читают артефакты через MCP, что напрямую реализует блок «Context Sharing» из архитектурной диаграммы info40 современным протоколом.
