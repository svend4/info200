# ИИ-агенты и мультиагентная оркестрация

## О теме

Пять репозиториев этой темы объединены одной сквозной идеей: построить платформу, которая координирует множество ИИ-агентов — принимает цель, декомпозирует её на подзадачи, строит граф зависимостей (DAG), назначает исполнителей по рейтингу и гоняет всё это через канбан-доску, workflow-движок или REST API. Поверх ядра почти всегда навешивается «обвязка платформы»: marketplace скиллов, метрики, мониторинг, SDK/CLI, а в двух случаях — амбиция «эволюционной лаборатории», которая сама синтезирует и отбирает агентов по fitness. Это одна из центральных, наиболее проработанных линий всего профиля svend4: сюда стянуты самые крупные инженерные репозитории и самые громкие заявки на «production-ready».

Одновременно это тема с самым большим разрывом между вывеской и начинкой. Почти каждый репозиторий заявляет промышленную готовность, но при проверке ядро «интеллекта» оказывается симуляцией: агенты — это if/else, таблицы и `asyncio.sleep`, персистентность держится в памяти процесса, а настоящий LLM-вызов встречается редко. Реально работающее ядро есть лишь у части репозиториев, и именно по этому признаку тема резко делится на «живые» и «витринные» проекты. Тема тесно смыкается с [RAG и семантическим поиском](../02-rag-semantic-search/README.md) (граф знаний как «активная память» агентов) и с [скиллами и MCP](../05-claude-code-skills-mcp/README.md) (marketplace и синтез скиллов).

## Лидеры и аутсайдеры

**Лидеры.**

- **data15** — единственный репозиторий темы со статусом «активный» и, пожалуй, самое честное ядро. Здесь работают паттерны надёжности (CircuitBreaker, RateLimiter, EventBus, retry) на чистом stdlib, а коннекторы агентов имеют реальные fallback-цепочки (`hermes CLI → MiniMax API → заглушка`), а не только стабы. Выделяются выдающаяся русская документация (`docs/DOCUMENTATION.md`, 1510 строк, сверена с кодом) и честный самоанализ `PERFORMANCE_ANALYSIS.md` с реальными метриками и найденной гонкой. Проект живёт: открыт PR с v6 (SQLite WAL, мульти-LLM, JWT). Минус — монолит на 6,5 тыс. строк и закоммиченное runtime-состояние (в т.ч. `users.json` с паролем `admin`).
- **data7** — крупнейший инженерный репозиторий не только темы, но и профиля: реальный объёмный код (TSP-библиотека на 1494 строки, 8+ алгоритмов, слоистая FastAPI-архитектура с DI и Repository pattern), полный DevOps-контур (CI, docker-compose, Prometheus+Grafana) и, что редкость для профиля, реально существующие тесты (pytest, Vitest, Playwright). Оригинальна сквозная идея «TSP как оптимизатор когнитивных маршрутов», проведённая через 6 доменов. Портит картину хаос из ~90 отчётов в корне и противоречивые самоотчёты («95% Production Ready» против честного «production code 0%»).

**Аутсайдеры и заготовки.**

- **info40** — образцовая «витрина»: полный инженерный контур (код + SQL-схема + Docker + k8s + Helm + мониторинг + CI) собран за один день, но сервисы работают на in-memory словарях, авторизация замокана (`user-123`), а агенты имитируют работу `sleep`'ами. Тесты не соответствуют коду и упадут при запуске; развития после генерации нет.
- **info7** — самый содержательный по коду из «витрин» (реальный граф знаний на 1034 строки, TF.js-сети), но с ложным статусом «Production Ready / 100% complete» при нуле тестов, отсутствии CI и сборке, сломанной в двух местах. «Интеллект» симулируется (эмбеддинги из char-кодов), security-пакет построен на прекращённом из-за уязвимостей `vm2`; брошен в день объявления «100% Complete».
- **info100** — самая явная заготовка-тупик: сквозной цикл (ingest → synthesize → validate → report) реально прошёл ровно один раз, после чего автоматизация мертва ~2,5 месяца (последние запуски workflow упали). Генерируемые скиллы тривиальны (шаблонный класс с fitness 1.0 за «компилируется»), а в коде подтверждены баги (строка `"default"` вместо bool, `string.Template` поверх `{{ }}`-плейсхолдеров).

## Общие сильные стороны темы

- **Реальное ядро оркестрации есть у нескольких репо**: паттерны надёжности на stdlib (data15), TSP-библиотека и слоистая FastAPI-архитектура (data7), граф знаний и 5-уровневая иерархия агентов (info7), реально прошедший 4-стадийный CI-пайплайн (info100).
- **Повторяющиеся зрелые архитектурные концепции**: декомпозиция задач, DAG с уровнями исполнения, назначение агентов по рейтингу, marketplace скиллов, fitness-отбор — тема оперирует правильным словарём мультиагентных систем.
- **Полнота инженерного контура**: Docker/compose почти везде, а info40 и data7 доводят его до k8s/Helm, мониторинга Prometheus/Grafana и CI.
- **Сильная русскоязычная документация**: `DOCUMENTATION.md` на 1510 строк (data15), 40+ КБ математической теории TSP (data7), двуязычные гайды (info7).
- **Точки честности**: `PERFORMANCE_ANALYSIS.md` с реальными метриками и найденной гонкой (data15), внутренние статусы, признающие «production code 0%» (data7), закоммиченные промежуточные данные, делающие состояние проверяемым (info100).

## Общие слабые места и чего не хватает

- **Разрыв «production-ready» и заглушек**: info40 работает на in-memory словарях, info7 объявляет «100% complete» при нуле тестов и сломанной сборке, data7 обещает «95% Production Ready» при честном «production code 0%».
- **Симуляция интеллекта вместо LLM**: агенты — это if/else, таблицы и `sleep`; эмбеддинги считаются из char-кодов (info7); настоящий вызов модели встречается лишь эпизодически (реальнее всего — fallback-цепочка на MiniMax в data15).
- **Систематически завышенные и противоречивые самоотчёты**: объёмы кода завышены кратно (info40, info7), проценты готовности скачут (40%→48%→91%→100% в data7; три разных статуса в документах info7).
- **Нет настоящих тестов и зелёного CI**: 0 тестов в info7, падающие тесты и CI по несуществующему `src/` в info40, print-скрипты вместо pytest в data15.
- **Заброшенность и одномоментность**: info7 мёртв с февраля, info100 — с апреля 2026; несколько репо целиком сгенерированы за 1–3 дня и далее не развиваются.
- **Проблемы безопасности и гигиены**: закоммиченные хэши паролей и, вероятно, ключ в git-истории (data15), устаревший `vm2` (info7), захламлённые корни (data15, data7).
- **Отсутствие лицензий и упаковки**: нет LICENSE у info100, data7, фактически у info7; нет `pyproject.toml`/`setup.py` в большинстве репо; персистентности (БД) нет у info40 и info7.

## Дубли и пересечения

- **Четыре оркестратора об одном и том же.** data15, info40, info7 и Meta-Orchestrator внутри data7 независимо реализуют один и тот же контур: декомпозиция задач → граф зависимостей → назначение агентов → REST API. Это прямое дублирование внутри профиля; логично свести их в один живой оркестратор, взяв проверенное ядро (data15) и производственную обвязку (info40/data7).
- **Граф знаний в двух местах.** info7 строит граф знаний (9 типов узлов, обход, центральность), info100 держит свой мини-граф концепций (5 узлов, 4 ребра) — оба по факту заглушки без настоящей семантики; их стоит объединить в одну графовую память (пересечение с темой RAG).
- **TSP-алгоритмы задвоены внутри data7**: корневой `dissertation_optimizer.py` и backend `tsp_algorithms.py` реализуют одно и то же без общей библиотеки.
- **«Marketplace/синтез скиллов»** заявлен и в info40 (marketplace-сервис), и в info100 (synthesize → test) — две половины одной идеи, которые просятся в единый каталог проверенных скиллов.

## Идеи сочетаний внутри темы

1. **data15 + info40 = один зрелый оркестратор вместо двух полупроектов.** Проверенное ядро data15 (доска с flock, workflow-движок, md-скиллы, реальные метрики) кладётся на производственную обвязку info40 (PostgreSQL-схема, k8s/Helm, мониторинг, SDK/CLI). Итог — один живой оркестратор профиля, а не два дублирующих друг друга.
2. **info7 + info40 = оркестратор с мультиарендностью из коробки.** У info7 есть уникальный для профиля enterprise-слой (multi-tenancy, RBAC с декораторами, аудит-лог), но нет рабочей инфраструктуры; у info40 наоборот. Их сложение даёт редкую для OSS комбинацию — оркестратор агентов с изоляцией арендаторов на реальном рантайме.
3. **info100 + (data15 или info40) = самооптимизирующаяся платформа.** info100 приносит петлю отбора по fitness, рабочий оркестратор — исполнение. Оркестратор автоматически заменяет слабых агентов «потомками» с лучшими метриками — то, чего ни один репозиторий темы не умеет в одиночку. Предварительно у info100 надо починить синтез (сейчас скиллы тривиальны).
4. **data7 (TSP-планировщик) + оркестратор = порядок задач вместо FIFO.** Задачи агентов как «города», стоимость переключения контекста как «дистанция» — TSP-библиотека data7 оптимизирует порядок исполнения вместо наивной FIFO-очереди. Это редкий планировщик, которого нет в большинстве open-source фреймворков.
5. **Единая графовая память для всех четырёх оркестраторов (своя идея).** Вместо четырёх плоских in-memory состояний — один граф знаний (каркас из info7 + настоящий retrieval из темы RAG), куда каждый workflow пишет результаты, а декомпозиция новых целей опирается на прошлый опыт: какие подзадачи и агенты срабатывали. Система, обучающаяся на собственной истории выполнения.
