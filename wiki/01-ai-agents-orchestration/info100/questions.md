# Вопросы к info100

## 1. Почему остановилась «ежедневная эволюция» — это осознанное завершение эксперимента или поломка?

Последние два запуска `evolve.yml` (17 и 21.04.2026) упали, cron с тех пор не срабатывал, коммитов нет ~2,5 месяца — при этом README позиционирует репозиторий как живую лабораторию.

**Варианты ответов:**
- А. Эксперимент «Variant C» был разовой целью, она достигнута — продолжение не планировалось.
- Б. Workflow сломался (конфликты push между job'ами / истёкший PAT), руки не дошли починить.
- В. GitHub отключил расписание из-за неактивности, я об этом не знал.
- Г. Проект заморожен в пользу других репо (info40, info20/30).

**Варианты дальнейших действий:**
- При А: зафиксировать в README статус «завершённый эксперимент», отключить cron, добавить итоговый отчёт — репо станет честным архивным кейсом.
- При Б: разобрать логи упавших запусков, применить исправления из recommendations.md (single-commit-стратегия уже начата), перезапустить вручную.
- При В: сделать любой коммит и заново включить workflow во вкладке Actions; рассмотреть keep-alive-механизм.
- При Г: перенести работающие части (tester, reporter) в активный репозиторий и заархивировать info100.

## 2. Что должен производить синтез на самом деле: сейчас сгенерированные «скиллы» — шаблонные классы-заглушки, возвращающие словарь?

Fitness 1.0 у `test-agent-v1` означает лишь «компилируется, импортируется, возвращает dict» — методология присутствует в коде только как строки-комментарии.

**Варианты ответов:**
- А. Это осознанный каркас: сначала конвейер, содержимое — потом (через LLM-генерацию).
- Б. Целевой артефакт — скиллы/плагины Claude Code, а не Python-классы.
- В. Целевой артефакт — записи в базу методов (info4), исполняемость вторична.

**Варианты дальнейших действий:**
- При А: добавить стадию LLM-синтеза (Claude API) в `skill-synthesizer.py` и ужесточить fitness реальными задачами из `benchmarks/tasks/`.
- При Б: сменить формат вывода на SKILL.md + скрипты, валидировать структуру скилла — и связать с info20/info30.
- При В: убрать генерацию .py, оставить YAML-манифесты и наладить экспорт/импорт с info4.

## 3. Планируется ли расширение сбора с 2 захардкоженных репозиториев (info1, data70) на весь профиль?

`base-collector.yaml` описывает универсального параметризуемого агента, но реализованы два отдельных скрипта с зашитыми именами и разными эвристиками.

**Варианты ответов:**
- А. Да, универсальный сборщик — следующий логичный шаг.
- Б. Нет, info1 и data70 выбраны намеренно как «эталонные» источники методологий.
- В. Сбор всего профиля — задача другого репо (nautilus/info200), здесь не нужен.

**Варианты дальнейших действий:**
- При А: слить два коллектора в один `collector.py --repo <owner/name>`, список целей — в конфиг; учесть rate-limit GitHub API.
- При Б: задокументировать критерий выбора источников в README; вычистить обобщающие обещания.
- При В: выделить ingest-код в переиспользуемый модуль и подключить его к репо-хабу, чтобы не дублировать логику.

## 4. В чём смысл дублирования: `skill-generator.py` (нерабочая подстановка шаблона) и `skill-synthesizer.py` делают одно и то же, оба с классом `SkillSynthesizer`?

README при этом ссылается именно на устаревший `skill-generator.py`.

**Варианты ответов:**
- А. generator — черновик, забыл удалить после написания synthesizer.
- Б. Задумывались как два режима: лёгкий (по шаблону) и полный (с графом).
- В. Не знал, что подстановка `{{ }}` через `string.Template` не работает.

**Варианты дальнейших действий:**
- При А: удалить `skill-generator.py`, поправить README и быстрый старт.
- При Б: починить шаблонизацию (Jinja2 или `$`-синтаксис), переименовать классы (`TemplateGenerator` vs `SkillSynthesizer`), описать оба режима.
- При В: добавить простейший тест на выход генератора (проверка отсутствия `{{` в результате) — он бы поймал этот баг сразу.

## 5. Замечен ли баг `passed: "default"` в результатах тестов, и насколько можно доверять fitness 1.0?

В `skills/tested/test-agent-v1.yaml` и `benchmarks/results/test-run-*.json` поле `functional.passed` содержит строку `"default"` вместо булева значения — `validate()` возвращает имя конфигурации, и оно протекает в отчёт (а строка всегда truthy, т.е. функциональный тест не может провалиться по валидации).

**Варианты ответов:**
- А. Не замечен — спасибо, надо исправить.
- Б. Замечен, но не критично: тест всё равно смысловой нагрузки пока не несёт.
- В. Это ожидаемое поведение (truthiness достаточно).

**Варианты дальнейших действий:**
- При А/Б: однострочный фикс (`bool(...)`) в `skill-tester.py` + перегенерация `test-agent-v1.yaml`; добавить схему-валидацию результатов (pydantic/jsonschema).
- При В: как минимум привести тип к bool при сериализации, иначе любые потребители JSON-отчётов получат неоднородные типы.

## 6. Какова связь info100 с info40 (AI Agent Orchestration Platform) и другими агентными репо — конкуренция, этапы одного замысла или независимые эксперименты?

В профиле несколько репозиториев про агентов (info40, info7, daten4, info4), и непонятно, где «центр тяжести» агентной темы.

**Варианты ответов:**
- А. info100 — исследовательская песочница, info40 — производственная платформа; результаты первого должны питать второе.
- Б. Независимые эксперименты разных периодов, объединять не планирую.
- В. Всё это черновики одного будущего проекта, который ещё не начат.

**Варианты дальнейших действий:**
- При А: определить формат передачи (протестированные скиллы как артефакты для info40), описать в обоих README.
- При Б: в вики-хабе (info200) зафиксировать статус каждого агентного репо, чтобы избежать путаницы.
- При В: составить сводную концепцию в info200/nautilus и решить, какой репозиторий станет основным, а какие — архивом.
