# Рекомендации по info2

## Быстрые улучшения

1. **Добавить файл LICENSE** (MIT) — README на него уже ссылается; сейчас ссылка битая.
2. **Закоммитить `prototype/package-lock.json` и `frontend/package-lock.json`** (`npm install --package-lock-only`) — без этого CI (`npm ci`) не может пройти в принципе.
3. **Починить `package.json`**: поле `"main": "index.js"` указывает на несуществующий файл — либо создать `prototype/index.js`, экспортирующий DeduplicationEngine/DependencyResolver/репозитории, либо указать реальный вход.
4. **Один раз запустить весь стек** (`docker-compose up`) и прогнать `npm test` — зафиксировать результат в README (badge CI, раздел «Проверено»); это главный шаг от «написано» к «работает».
5. **Вычистить вымышленное**: контакты thub.io/team@thub.io/@thub_io, ссылку на github.com/thub-io/thub, даты roadmap 2024–2025 — заменить на реальные или пометить как «гипотетический сценарий».
6. **Обновить PROJECT-SUMMARY.md** под фактическую структуру (сейчас не отражает db/, cache/, search/, realtime/, monitoring/, frontend/, k8s/, CI).
7. **Слить README-COMPLETE.md с README.md** или явно разграничить их назначение — сейчас это два пересекающихся документа на 1 000+ строк суммарно.
8. **Переименовать репозиторий или дополнить описание** (например, «thub — content-addressed component registry (prototype)») — имя info2 не находимо поиском.

## Серьёзные доработки

- **Верификация запуском (первоочередное)**: поднять PostgreSQL, прогнать миграции и сиды, запустить API и все 8 команд CLI, выполнить оба тестовых файла. По опыту AI-сгенерированных однопроходных проектов, вскроется ещё 5–15 ошибок интеграции — их исправление и есть превращение муляжа в прототип.
- **Настоящая семантическая дедупликация**: заменить Jaccard-по-токенам на AST-нормализацию (парсинг через @babel/parser или tree-sitter, альфа-переименование идентификаторов, хеш нормализованного AST) + шинглы/MinHash для масштабируемого поиска похожих. Текущий O(n)-перебор всей категории не переживёт и тысячи компонентов.
- **Убрать несоответствие обещаний и охвата фронтенда**: либо достроить (страница компонента, публикация, логин, дашборд дедупликации), либо честно убрать frontend/ и заявить «API-first».
- **Безопасность**: JWT_SECRET с дефолтом «your-secret-key…» в .env.example допустим, но код должен отказываться стартовать в production без секрета; в `db/index.js` `process.exit(-1)` на любой ошибке idle-клиента — грубо; добавить graceful shutdown.
- **Сузить скоуп MVP**: реестр + дедупликация + CLI на локальном PostgreSQL, без Elasticsearch/MinIO/K8s/Grafana. Половина инфраструктуры сейчас — балласт, увеличивающий поверхность отказа.

## Варианты продолжения

**Сценарий 1 — «Честный локальный инструмент дедупликации».**
Отбросить платформенные амбиции и превратить ядро (deduplication.js + dependency-resolver.js + CLI) в npm-пакет-утилиту: `thub scan ./src` находит дубликаты и почти-дубликаты кода внутри монорепозитория или между репозиториями одного владельца. Это реализуемо в одиночку за недели, не требует серверов, и у svend4 есть идеальный полигон — собственный 61 репозиторий с заведомо повторяющимся кодом. Результат сразу полезен и проверяем.

**Сценарий 2 — «Внутренний реестр компонентов профиля».**
Довести серверную часть до реального запуска (Postgres + API + CLI, без ES/MinIO) и наполнить реестр реальными переиспользуемыми модулями из репозиториев профиля (валидаторы, rate-limiter'ы, query-builder'ы и т.п. встречаются в data*/daten*-проектах многократно). T-Hub становится «внутренним npm» экосистемы svend4: измеримая метрика успеха — сколько дублей реально удалось схлопнуть. Это одновременно проверка центрального тезиса проекта (80–90% дублирования) на собственных данных.

**Сценарий 3 — «Исследовательская статья + бенчмарк».**
Использовать сильную концептуальную документацию (04-THUB-CONCEPT.md, 02-COMMON-FUNCTIONS.md) как основу публикации/лонгрида о content-addressed подходе к коду: взять корпус (например, топ-1000 npm-пакетов), прогнать через 3 уровня дедупликации и опубликовать реальные цифры дублирования вместо декларируемых «80–90%». Код прототипа становится измерительным инструментом; проект получает то, чего ему больше всего не хватает — эмпирическую опору.

**Сценарий 4 — «Архивировать как концепт-документ».**
Если продолжения не планируется: пометить в README статус «concept + unverified prototype, 2026, AI-assisted», убрать фиктивные контакты, добавить LICENSE — и оставить как справочный документ по теме для других проектов профиля. Минимальные усилия, честный статус.

## Сочетания с другими репозиториями профиля

1. **info2 + meta10 (grep-ast → ast-grep) = настоящий семантический дедупликатор.**
   Слабейшее место T-Hub — «семантический» уровень на Jaccard-схожести. meta10 посвящён AST-инструментам (ast-grep). Скрестив их, получаем дедупликацию на структурных AST-паттернах: ast-grep находит структурно эквивалентный код независимо от имён переменных и форматирования, а T-Hub даёт реестр, хеширование и CLI-обвязку. Это уникальный инструмент, которого в open-source в готовом виде почти нет: «content-addressed реестр с AST-канонизацией».

2. **info2 + lorenzo (docs-toolkit, ~2815 md-файлов Svyazi 2.0) = тезаурус-хаб для документов, а не кода.**
   Механика T-Hub (content-hash, нормализация, поиск почти-дубликатов, граф зависимостей) один-в-один применима к markdown-базам знаний. В lorenzo — тысячи md-файлов с заведомыми повторами; движок дедупликации info2 после замены нормализатора кода на нормализатор markdown станет инструментом аудита дублей и построения графа связей документации. Инновация: «CAS-вики», где каждый смысловой блок существует в одном экземпляре — прямое воплощение идеи T-Hub на реальных данных профиля.

3. **info2 + info40 (AI Agent Orchestration Platform) = реестр переиспользуемых навыков/инструментов агентов.**
   Агентские платформы страдают тем же дублированием: одинаковые tool-функции и промпты копируются между агентами. T-Hub-реестр с дедупликацией + оркестратор info40 = «пакетный менеджер способностей агентов»: агент декларирует зависимости в манифесте (аналог sample-app.thub.yaml), платформа резолвит их через dependency-resolver и собирает агента из уникальных компонентов. Это свежая ниша (skill-registry для агентов), где content-addressed подход даёт ещё и воспроизводимость поведения.

4. **info2 + info200 (хаб вики профиля) = страница-витрина «повторное использование в экосистеме».**
   Минимальное сочетание: прогнать дедупликатор info2 по всем 61 репозиториям и опубликовать в вики info200 карту реальных дублей кода между проектами — и как демонстрацию работоспособности T-Hub, и как практический план консолидации профиля.
