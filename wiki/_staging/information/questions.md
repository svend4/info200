# Вопросы к information

## 1. Каков замысел: это личный новостной инбокс, будущий публичный дайджест или разовый эксперимент с «issues-как-закладки»?

Описание («info новости ньюз») и три issue-ссылки допускают все три трактовки, а README ничего не уточняет.

**Варианты ответов**
- А. Личный инбокс «прочитать позже».
- Б. Заготовка публичного новостного дайджеста.
- В. Разовый эксперимент, продолжать не планировалось.

**Варианты дальнейших действий**
- При А: оформить процесс (README с правилами, labels, шаблон закладки, дисциплина open=в очереди/closed=прочитано) — см. Вариант A в рекомендациях.
- При Б: строить автоматизацию дайджеста (Action + Pages) — Вариант B; начать с еженедельной выгрузки issues в markdown.
- При В: перенести 3 закладки в info200/data70 и заархивировать репозиторий (Вариант D).

## 2. Почему хранилище — именно GitHub Issues, а не markdown-файлы в самом репозитории?

В профиле десятки репозиториев хранят информацию файлами; здесь выбран противоположный паттерн, но нигде не объяснён.

**Варианты ответов**
- А. Осознанно: issues удобнее с телефона, есть поиск, метки и API.
- Б. Случайно: так было быстрее в тот день.
- В. Хотелось попробовать паттерн, решение не принято.

**Варианты дальнейших действий**
- При А: закрепить паттерн — шаблон issue, автолейблинг, периодическая выгрузка issues в файлы для резервной копии (issues не версионируются git).
- При Б: перенести закладки в `bookmarks.md`/`news/` внутри репозитория и вести их файлами — проще для grep и офлайна.
- При В: месяц пожить с issues, месяц с файлами, сравнить трение; выбранный вариант задокументировать в README.

## 3. Что делать с пересечением ролей: в профиле уже есть info200 (хаб), data70 («много тем»), daten8 (мониторинг объявлений) — зачем отдельный «information»?

61 репозиторий — это уже проблема навигации; каждый новый «info»-контейнер её усугубляет.

**Варианты ответов**
- А. «information» — единственный официальный новостной инбокс, остальные — про другое.
- Б. Роли пересекаются, надо консолидировать.
- В. Пусть живут параллельно, это не мешает.

**Варианты дальнейших действий**
- При А: зафиксировать роль в README и в вики-хабе info200 («новости — только сюда»), настроить перекрёстные ссылки.
- При Б: выбрать один репозиторий-приёмник, перенести закладки, лишние заархивировать с указателем.
- При В: как минимум описать в хабе info200 разграничение, чтобы будущие закладки не расползались случайным образом.

## 4. Нужен ли захват содержимого статей, или достаточно голых ссылок?

Сейчас каждая закладка — только URL; Хабр-статьи и продуктовые страницы со временем меняются или исчезают.

**Варианты ответов**
- А. Достаточно ссылок — важен факт «я это видел».
- Б. Нужны аннотации (1–3 фразы) — зачем сохранено и что главное.
- В. Нужен полный архив текста статьи.

**Варианты дальнейших действий**
- При А: ничего не менять, но принять риск link rot осознанно (пометить в README).
- При Б: добавить в шаблон issue обязательное поле «почему интересно»; дописать аннотации к трём существующим закладкам.
- При В: сделать Action/скрипт, который по новому issue извлекает текст (trafilatura/readability) и коммитит в `archive/`; учесть авторские права — хранить приватно или выдержками.

**Варианты ответов**

- Б. Эпизодически, когда попадается важное.
- В. Нет, наполнять не планирую.

**Варианты дальнейших действий**

- При Б: настроить хотя бы автолейблинг и шаблон, чтобы редкие закладки были самодостаточными (аннотация обязательна).
- При В: перенести существующее и заархивировать репозиторий (Вариант D) — пустой «живой» репозиторий хуже честно закрытого.
