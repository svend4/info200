# Рекомендации по daten40

## Быстрые улучшения

1. **Добавить лицензию** (например, CC BY-SA для спецификаций + MIT для кода-заглушек) — сейчас переиспользование корпуса юридически не определено.
2. **Починить README**: убрать несуществующую папку `releases/` из таблицы структуры (или создать её), исправить диапазон нумерации («14241 → 88800» → «1 → 88800»), привести имя `master-index/` в `README_IFOS_20260113.md` к фактическому `master_index/`.
3. **Создать README слоёв 00–06** (`blocks/00_GENESIS/README.md` … `06_FINANCE_LEGAL/README.md`) — на них уже ссылается мастер-индекс, ссылки битые. Шаблон уже есть в репозитории: `blocks/07_DOMAIN_PACKS/README.md` (заголовок + таблица блоков), его формат можно сгенерировать для остальных слоёв из `_block_index.json`.
4. **Включить GitHub Pages** для `blocks/index.html` — задача уже стоит в очереди (MEDIUM), эффект мгновенный: корпус получает публичную витрину.
5. **Убрать/изолировать январский тестовый слой**: перенести `chatgpt-tests/`, `make_test/`, `test/`, `test-notes/`, `data/`, `config/`, `database/`, `web/`, `generated_code.txt` в одну папку `legacy_make_tests/` (append-only это позволяет — переносом новых копий) и удалить файл-опечатку `docs/.md`.
6. **Добавить `tools/build_pack.py`** — скрипт сборки ZIP из `pack_files_*`, который предписан собственной политикой `BINARY_POLICY_APPEND_ONLY_20260113.md`, но так и не создан.
7. **Закрыть CRITICAL из очереди и дополнить её**: регенерировать битый `IFOS_14241_14440_function_wikipedia_pack.zip` и 5 потерянных блоков (21201–21600, 21601–22000, 26001–26400, 30401–30800, 31201–31600), а также внести в очередь **3 незадокументированные дыры**, выявленные пересчётом индекса при аудите (49201–49600, 80001–80100, 81301–82000), и **30 задублированных диапазонов** — сейчас в «известных проблемах» признан только дубль 35601–36000.

## Серьёзные доработки

1. **Валидатор целостности корпуса + CI**: GitHub Action, который на каждый push (а) валидирует все `*_schema_v1.json` как JSON Schema, (б) прогоняет OpenAPI-линтер по `*_api_v1.yaml`, (в) сверяет `_block_index.json` с фактическим деревом (дыры, дубли, число файлов), (г) проверяет внутренние ссылки md-файлов. Это превратит «известные проблемы» из ручного списка в автоматический отчёт. Необходимость доказана самим аудитом: тривиальный скрипт пересчёта индекса сразу нашёл 30 дублей диапазонов и 3 дыры, о которых ручной учёт проекта не знает.
2. **Единый пайплайн генерации мастер-индекса**: сейчас индексы (v26, v31, 20260618) созданы разными способами; нужен скрипт, генерирующий Master Index (md+json+csv) и `index.html` из `_block_index.json` детерминированно.
3. **Исполняемый вертикальный срез**: выбрать один блок (логичный кандидат — Recipe-OS 14441–14680, там уже есть схема, компилятор-скелет и примеры) и довести до работающего MVP: recipe JSON → валидация → реальный экспорт в n8n workflow JSON, с тестами. Это переведёт проект из «бумажной архитектуры» в стадию прототипа и проверит жизнеспособность формата паспортов.
4. **Дедупликация и вычитка контента**: убрать citation-артефакты («citeturn…» с невидимыми Unicode-разделителями) из Genesis, разрешить все **30 задублированных диапазонов** (переприсвоить номера одному блоку из каждой пары; в «известных проблемах» признан только 35601–36000), ввести отметку человеческой вычитки в паспорт блока (реально применить собственную Quality Ladder L0–L5 к своим же блокам — сейчас уровни описаны, но блокам не присвоены).
5. **Слить IFOS-хвосты из data70**: мастер-индекс ссылается на «856 файлов из _CANONICAL» и chat_export в svend4/data70 — стоит либо перенести канонический источник в daten40, либо явно задокументировать распределение ролей между двумя репозиториями.

## Варианты продолжения

**Сценарий 1 — «IFOS как публичная база знаний».** Не писать платформу, а оформить корпус как открытую вики/справочник по стандартизации интернет-функций: GitHub Pages поверх `index.html`, README слоёв, поиск, присвоенные уровни качества, лицензия CC. Ценность — 165+ доменов структурированных спецификаций уже сегодня полезны как референс для проектировщиков автоматизаций (Make/n8n). Трудозатраты минимальны, поскольку 90% контента готово; главное — навигация и вычитка.

**Сценарий 2 — «Recipe-OS MVP» (исполняемый срез).** Сфокусироваться на одном слое: рецепты-микромакросы. Довести `IFOS_recipe_schema_v1.json` до стабильной версии, написать настоящий компилятор recipe → n8n/Make (скелет уже есть), собрать каталог из 20–30 реальных рецептов с evidence-планами и прогонять их в CI. Это самый короткий путь от «бумаги» к продукту, который можно показывать: «одна идея → одна кнопка → работает в разных платформах», как и заявлено в блоке 14441–14680.

**Сценарий 3 — «Машиночитаемый корпус для ИИ-агентов».** Превратить 1466 JSON-схем и 139 OpenAPI-спек в датасет/инструментальную библиотеку для LLM-агентов: MCP-сервер «IFOS Registry», который отдаёт агенту паспорт функции, схему и заглушку по запросу. IFOS задумывался как «AI Layer» — здесь корпус становится не описанием платформы, а её первым реальным компонентом: реестром, к которому агенты обращаются при построении автоматизаций.

**Сценарий 4 — «Заморозка с достоинством».** Если продолжение не планируется: закрыть CRITICAL-дыры индексов, зафиксировать финальный Master Index, включить Pages, поставить лицензию и пометить репозиторий как архив-справочник. Даже в таком виде это самый крупный целостный артефакт концепции IFOS в профиле.

## Сочетания с другими репозиториями профиля

1. **daten40 + info40 (AI Agent Orchestration Platform, Production) = «IFOS Live Registry»**. daten40 даёт то, чего обычно нет у оркестраторов агентов, — стандартизованный каталог функций с паспортами, схемами и OpenAPI-контрактами; info40 даёт исполняемую платформу. Скрестив их, получаем оркестратор, где агенты выбирают действия не из ad-hoc списка инструментов, а из типизированного реестра IFOS с уровнями доверия L0–L5 и evidence-планами — уникальная связка «каталог стандартов + рантайм», фактически реализация Layer 1 + Layer 6 IFOS на готовой платформе.

2. **daten40 + data70 (чат-экспорты, источник IFOS) + meta2 (восстановление разорванных документов) = «конвейер канонизации знаний из чатов»**. Мастер-индекс daten40 прямо указывает источником chat_export из data70. Инструментарий meta2 по восстановлению/склейке фрагментированных документов можно применить к чат-экспортам data70, чтобы автоматически регенерировать потерянные блоки (21201–22000, 26001–26400 и др.) и вычищать citation-артефакты. Получается воспроизводимый пайплайн «сырой диалог → канонический OS_PACK-блок» — инновация в том, что корпус перестаёт зависеть от ручной пересборки.

3. **daten40 + infom (ГрафРАГ) = «граф зависимостей интернет-функций с RAG-поиском»**. Master Index v31 уже содержит поле «Depends on» между блоками, а блоки — 1466 схем сущностей. Загрузив это в граф знаний infom, получаем GraphRAG-систему, отвечающую на вопросы вида «какие функции нужны для запуска marketplace billing и какие у них PII-риски» с трассировкой по слоям IFOS — готовый демонстратор Trust Layer, которого нет ни в одном из репозиториев по отдельности.

4. **daten40 + daten4 (динамический планировщик) = «планировщик, говорящий на языке рецептов»**. Формат Recipe (steps, secrets, evidence_plan, targets) из блока 14441–14680 — готовый DSL для динамического планировщика daten4: планировщик строит план как последовательность IFOS-шагов с контрактами `on_error/retry`, а корпус daten40 служит библиотекой допустимых действий. Новое качество — планирование с проверяемыми (evidence) и идемпотентными шагами.
