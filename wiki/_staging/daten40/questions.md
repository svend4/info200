# Вопросы к daten40

## 1. Какова целевая судьба IFOS: продукт, стандарт или исследовательский корпус?

Мастер-индекс честно называет проект «Design Specification (paper architecture) — no production code yet», но README позиционирует IFOS как «B2B-платформу». Это разные траектории с разными следующими шагами.

**Варианты ответов:**
- А. Это будущий продукт — планируется реализация хотя бы одного слоя.
- Б. Это стандарт/справочник — код не планируется, ценность в спецификациях.
- В. Это исследовательский/личный корпус идей без обязательств.

**Варианты дальнейших действий:**
- При А: начать с исполняемого среза Recipe-OS (схема+компилятор уже есть), поставить CI-валидацию схем, выбрать целевую платформу (n8n — самая открытая).
- При Б: включить GitHub Pages, добавить лицензию CC, вычитать блоки, присвоить им уровни Quality Ladder — и продвигать как открытый каталог.
- При В: закрыть CRITICAL-дыры, зафиксировать финальный индекс и оформить архивный статус, чтобы корпус не деградировал.

## 2. Кто источник истины по IFOS: daten40 или data70 (_CANONICAL)?

`IFOS_MASTER_INDEX_20260618.md` указывает «Источник: … + 856 файлов из _CANONICAL, GitHub: svend4/data70». Непонятно, где каноническая копия корпуса и что делать при расхождениях.

**Варианты ответов:**
- А. daten40 — рабочая витрина, канон в data70/_CANONICAL.
- Б. daten40 и есть канон, data70 — только сырые чат-экспорты.
- В. Чёткого разделения нет, копии разъехались.

**Варианты дальнейших действий:**
- При А: добавить в README daten40 явное указание на канон и процедуру синхронизации; в идеале — скрипт сверки контрольных сумм.
- При Б: перенести недостающие 370 standalone-файлов из _CANONICAL в daten40 и пометить data70 как источник сырья.
- При В: провести одноразовую сверку (по `_block_index.json` и checksums), выбрать канон и задокументировать это в обоих репозиториях.

## 3. Планируется ли регенерация потерянных блоков и битого ZIP (CRITICAL в очереди)?

`tools/NEXT_QUEUE_v1_20260618.md` числит CRITICAL: битый `IFOS_14241_14440_function_wikipedia_pack.zip` и 5 потерянных диапазонов. Дыры подтверждены пересчётом `_block_index.json`.

**Варианты ответов:**
- А. Да, исходники есть (чат-экспорты), регенерация возможна.
- Б. Исходники утрачены, блоки придётся создавать заново.
- В. Дыры признаются допустимыми, нумерация останется с пропусками.

**Варианты дальнейших действий:**
- При А: настроить конвейер регенерации (в связке с data70 и, возможно, meta2 — восстановление разорванных документов) и закрыть все 6 пунктов разом.
- При Б: сгенерировать блоки заново по соседним по смыслу темам и пометить их в паспорте как «reconstructed», понизив уровень качества.
- При В: зафиксировать пропуски в мастер-индексе как норму («reserved ranges») и снять задачи из CRITICAL, чтобы очередь отражала реальные планы.

## 4. Почему заявленная в README папка `releases/` не существует и где должны жить ZIP-бандлы?

README и стратегия ссылаются на `releases/`, но папки нет (404); ZIP лежат в `blocks/` и `archives/`. Политика бинарников при этом рекомендует ZIP как опциональные, с checksums.

**Варианты ответов:**
- А. `releases/` — планировалась, но не дошли руки; ZIP в `blocks/` — временно.
- Б. От ZIP решено отказаться (текст — источник истины), README устарел.
- В. Бандлы предполагается публиковать через GitHub Releases, а не папку.

**Варианты дальнейших действий:**
- При А: создать `releases/`, перенести туда бандлы новыми копиями (append-only), добавить sha256 в checksums.
- При Б: удалить упоминание `releases/` из README, пометить существующие ZIP как legacy.
- При В: завести GitHub Releases с тегами по версиям Master Index и написать `tools/build_pack.py`, который предписан собственной политикой.

## 5. Будет ли применена собственная Quality Ladder (L0–L5) к самим блокам?

README описывает уровни качества от Draft до Enterprise/Gov, но ни в `_block_index.json`, ни в мастер-индексе у блоков нет присвоенных уровней — метрика существует, но не используется.

**Варианты ответов:**
- А. Да, планируется паспортизация блоков с уровнями.
- Б. Уровни — часть концепции IFOS для внешних функций, к своим блокам не применяются.
- В. Об этом не думали.

**Варианты дальнейших действий:**
- При А: добавить поле `quality_level` в `_block_index.json`, начать с автоматических критериев (есть ли схема/API/примеры/вычитка) и отразить уровни в навигаторе.
- При Б: явно оговорить это в README, чтобы читатель не искал уровни у блоков.
- При В: провести пилот на одном слое (например, 01_FOUNDATION) — это одновременно проверит применимость собственной методики.

## 6. Какой смысл сохраняется у январского слоя Make.com-тестов — это часть проекта или мусор?

Треть корневых папок (`chatgpt-tests/`, `make_test/`, `config/`, `data/`, `database/`, `web/`, `test*`) и три корневых отчёта относятся к январскому эксперименту с тремя Make.com-инструментами, не связанному с содержанием IFOS напрямую.

**Варианты ответов:**
- А. Это рабочая инфраструктура доставки файлов — инструменты Make.com до сих пор используются для пополнения репозитория.
- Б. Это исторический эксперимент, ценный как документация метода.
- В. Это мусор, оставшийся от тестов.

**Варианты дальнейших действий:**
- При А: вынести описание инструментов в `docs/` как актуальную инструкцию пополнения и связать с политикой бинарников.
- При Б: переместить всё в `legacy_make_tests/` одной папкой с коротким README «как это было».
- При В: удалить тестовые папки (append-only можно не нарушать — зафиксировать удаление в очередном NEXT_QUEUE), оставив только отчёты.
