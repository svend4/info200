# Рекомендации по daten8

## Быстрые улучшения

Даже без написания кода репозиторий можно за час привести в осмысленное состояние:

1. **Наполнить README.md**: заменить «prog» на 5–10 предложений — что мониторим (какие площадки: eBay Kleinanzeigen/Kleinanzeigen.de, Avito, willhaben и т.п.), по каким критериям, как должны приходить уведомления, какой планируется стек.
2. **Добавить LICENSE** (MIT/Apache-2.0), чтобы будущий код был переиспользуем.
3. **Добавить .gitignore** под выбранный стек (Python/Node).
4. **Завести 3–5 issues** с декомпозицией MVP: «выбрать источники», «схема данных объявления», «скрипт опроса одного источника», «фильтр + дедупликация», «уведомления (Telegram/email)».
5. **Записать спецификацию** (`docs/spec.md`): схема записи объявления (id, заголовок, цена, регион, url, дата, хэш), периодичность опроса, правила дедупликации.
6. **Указать место в серии daten\***: одной строкой в README пояснить, чем daten8 отличается от соседних репо (daten6 — каталог, daten22 — офлайн-поиск и т.д.), чтобы слоты не смешивались.

## Серьёзные доработки

1. **MVP-скрапер одного источника**: Python (requests/httpx + BeautifulSoup или Playwright для JS-страниц), сохранение объявлений в SQLite, запуск по cron/GitHub Actions schedule. Это превращает репозиторий из идеи в работающий инструмент.
2. **Модуль уведомлений**: Telegram-бот или email при появлении объявления, подходящего под сохранённый фильтр («квартира до X», «велосипед до Y»).
3. **История цен и изменения объявлений**: хранить снапшоты, детектировать снижение цены/повторную публикацию — главная «добавленная стоимость» мониторинга по сравнению с ручным просмотром площадки.
4. **Абстракция «источник»**: интерфейс-адаптер (fetch → parse → normalize), чтобы «(versch.)» — «различные площадки» — реально поддерживались подключаемыми модулями, а не форками кода.
5. **Юридическая гигиена**: зафиксировать в доках ограничения (robots.txt, rate limiting, персональные данные в объявлениях) — для скраперов это критично.
6. **Тесты и CI**: юнит-тесты парсеров на сохранённых HTML-фикстурах + GitHub Actions.

## Варианты продолжения

**Сценарий 1 — «Личный вахтёр объявлений» (минимальный, рекомендуемый).**
Довести до личного инструмента: один Python-скрипт, 1–2 площадки, фильтры в YAML-конфиге, SQLite для дедупликации, уведомления в Telegram. Запуск — GitHub Actions по расписанию (каждые 30–60 минут), без собственного сервера. Ценность появляется через 1–2 дня работы; репозиторий из пустого слота становится самым «полезным в быту» проектом профиля.

**Сценарий 2 — «Платформа мониторинга с историей цен» (амбициозный).**
Развить в сервис: подключаемые адаптеры площадок, нормализованная схема объявления, накопление истории цен, веб-дашборд с графиками (падения цен, длительность экспозиции объявления), многопользовательские подписки на фильтры. Это уже продукт уровня «Flipping-assistant»: поиск недооценённых лотов для перепродажи. Требует недель работы и аккуратности с правилами площадок.

**Сценарий 3 — «Слияние со смежным репо и закрытие слота» (консервативный).**
Признать, что отдельный репозиторий для нереализованной идеи создаёт шум в профиле из 61 репо. Перенести идею как раздел/issue в более живой смежный проект (например, `information` — мониторинг новостных лент, или `daten6` — динамический каталог), а daten8 заархивировать с README-указателем «идея переехала в …». Профиль станет чище, идея не потеряется.

**Сценарий 4 — «Спецификация без кода» (документный).**
Если писать код сейчас не хочется — оформить daten8 как качественную спецификацию в духе инфо-репозиториев профиля: сравнение существующих готовых решений (Kleinanzeigen-alerts, RSS-мосты, Huginn, Changedetection.io), вывод «строить своё или взять готовое», схема данных и план. Такой документ сам по себе полезен и совместим с вики-хабом info200.

## Сочетания с другими репозиториями профиля

Минимум две идеи «обычное + обычное = новое уникальное»:

1. **daten8 + daten22 (offline search app, SQLite FTS4) = офлайн-архив объявлений с полнотекстовым поиском.** Скраперы daten8 складывают объявления в SQLite, а движок daten22 даёт мгновенный офлайн-поиск по накопленному архиву (FTS4). Уникальность: площадки удаляют старые объявления, а здесь возникает личная «машина времени» рынка — поиск по исчезнувшим лотам, история цен на конкретную модель товара, оценка «нормальной» цены перед покупкой. Ни одна площадка такого не даёт.

2. **daten8 + info40 (AI Agent Orchestration Platform) = агентный мониторинг с пониманием текста объявлений.** Оркестратор info40 управляет пайплайном агентов: агент-сборщик (daten8) → агент-классификатор (LLM определяет состояние товара, скрытые дефекты из текста, адекватность цены) → агент-переговорщик (черновик сообщения продавцу). Уникальность: вместо фильтра по ключевым словам — семантический отбор («ищи неубитые велосипеды с честным описанием до 200 €»), чего нет в стандартных «сохранённых поисках» площадок.

3. **daten8 + data4 (персональный бюджет) = покупки по бюджету.** Личный бюджет из data4 знает, сколько выделено на категорию («мебель: 300 €»); монитор daten8 автоматически ищет подходящие лоты в этих пределах и присылает только то, что «по карману» именно сейчас. Уникальность: связка «финансовый план → автоматический поиск предложений» — рынок объявлений подстраивается под личный бюджет, а не наоборот.

4. **daten8 + daten4 (динамический планировщик) = мониторинг как триггер планов.** События монитора (появился нужный лот, цена упала) становятся входами динамического планировщика: он перестраивает план («забрать в субботу», «отложить покупку Y»). Получается реактивная система «рынок → личное расписание».
