# Рекомендации по data20

## Быстрые улучшения

1. **Починить CI**: добавить корневой `requirements.txt` (или заменить в `.github/workflows/tests.yml` шаг на `pip install -r backend/requirements.txt -r requirements-test.txt`); отключить или починить падающий `sync-versions.yml`; закрыть/смёржить ветку `claude/fix-apk-builds-fdMiG`.
2. **Починить повреждённый frontmatter**: найти инструмент, который записывает метаданные как Python-repr (`{'title': ..., datetime.date(...)}`) вместо YAML (виновник — конвейер обогащения pagerank/quality/reading_time), исправить сериализацию на `yaml.safe_dump` и прогнать восстановление по всем статьям; добавить в `validate.py` проверку «frontmatter парсится как YAML» как critical.
3. **Добавить LICENSE** (MIT или CC-BY для контента + MIT для кода).
4. **Разгрести корень**: перенести 60+ авто-сгенерированных индексов и релизных инструкций в `docs/` и `generated/`, добавить `.gitignore` для кэшей (`.index_cache.json`, `.reading_progress.json`) и `backups/`, `exports/`.
5. **Опубликовать APK**: сборка в Actions уже проходит — добавить upload-artifact → release asset, чтобы заявление «100MB APK» стало проверяемым фактом.
6. **Обновить README-статистику** или убрать «обновляется автоматически» — даты застыли на 02.01.2026.

## Серьёзные доработки

1. **Наполнить базу знаний** — главный дефицит. Без хотя бы 100–300 реальных статей невозможно ни проверить масштабируемость инструментов, ни получить пользу. Источник контента есть в самом профиле (см. сочетания ниже).
2. **Свести 8+ фронтендов к одному-двум**: выбрать целевую платформу (реалистично: mobile-app-lite + browser-extension как самые дешёвые в поддержке), остальные варианты заархивировать в отдельную ветку/папку `attic/`.
3. **Выделить общее ядро инструментов**: 57 скриптов дублируют парсинг frontmatter и обход `knowledge/` — вынести в пакет `data20_core` (это заодно решит проблему битого YAML в одном месте), покрыть ядро тестами.
4. **Интеграционные тесты конвейера данных**: тест «создать статью → прогнать все инструменты обогащения → frontmatter остаётся валидным YAML» предотвратил бы найденную порчу данных.
5. **Реально проверить embedded-сценарий на устройстве**: Chaquopy + FastAPI + 57 инструментов — амбициозная связка; нужен smoke-тест на эмуляторе в CI (сейчас проверяется только сборка, не работа).

## Варианты продолжения

**Сценарий A. «Личная офлайн-энциклопедия» (минимальный, рекомендуемый).** Отказаться от production-обвязки (Celery, Redis, JWT, Prometheus — для личной базы это лишнее), оставить knowledge/ + tools/ + static_site/ + browser-extension. Сфокусироваться на наполнении: 20–30 статей в месяц через inbox-конвейер с AI-обработкой (промпты уже написаны в README). Через полгода получится то, что заявлено: работающая личная база знаний с офлайн-поиском. Трудозатраты минимальны, ценность — реальная и личная.

**Сценарий B. «Offline KB Engine» как продукт-шаблон.** Довести до конца именно инженерную часть: одна кнопка «Use this template» → пользователь получает пустую KB с 57 инструментами, CI, мобильным приложением и расширением. Для этого нужно: опубликовать APK, вычистить личные артефакты, написать quickstart на английском, оформить лицензию. Ниша реальная (Obsidian/Zettelkasten-аудитория, которой нужен git-native подход без проприетарных приложений), и 90% работы уже сделано — осталось «последняя миля» дистрибуции.

**Сценарий C. «Бэкенд-как-платформа для роя инструментов».** Самая ценная и переносимая часть data20 — связка `tool_registry.py` (AST-автообнаружение CLI-инструментов) + `tool_runner.py` (асинхронный запуск с job-статусами и WebSocket-прогрессом) + Flutter/Electron-клиенты. Извлечь её в отдельный универсальный проект «любая папка Python-скриптов → мгновенный API + UI + мобильный клиент». Это пригодилось бы почти всем репозиториям профиля (у svend4 десятки папок со скриптами) и было бы самостоятельно интересным open-source-продуктом.

**Сценарий D. «Заморозка с честным статусом».** Если возврата к проекту нет: прибить README-баннер «экспериментальный спринт, январь 2026, не поддерживается», зафиксировать выводы (что сработало: registry/runner, lite-подход; что нет: расползание фронтендов), извлечь уроки в info200-вики. Дёшево и предотвращает гниение репутации репозитория.

## Сочетания с другими репозиториями профиля

1. **data20 + lorenzo (Svyazi 2.0: ~2815 md-файлов + docs-toolkit) = стресс-тест и живая мега-база.** У data20 — 57 инструментов и пустая база; у lorenzo — огромный корпус markdown и свой Python-тулкит. Импортировать корпус lorenzo в `knowledge/` data20 и прогнать весь конвейер (PageRank, конкорданс, глоссарий, граф знаний, поиск) — впервые проверить заявление «работает с 10 000 документами» на реальных данных. Уникальный результат: навигируемый офлайн-атлас корпуса Svyazi 2.0 (в т.ч. в мобильном приложении), плюс честный бенчмарк инструментов на порядке величины, для которого они писались.

2. **data20 + daten22 (Offline search app, SQLite FTS4) = единый офлайн-поисковый движок знаний.** daten22 решает ровно ту задачу, которая у data20 самая слабая на мобильном — быстрый полнотекстовый поиск без сервера. Заменить в mobile-app-lite самодельный поиск на FTS4/FTS5-индекс из daten22, а индексатор data20 научить наполнять эту SQLite-базу при сборке APK. Получится инновационная связка: git-native база знаний, компилируемая в один SQLite-файл с полнотекстовым поиском — «выпекаемая» офлайн-энциклопедия, работающая на телефоне без Python-рантайма вообще (что снимает главную боль — 100МБ APK с Chaquopy).

3. **data20 + info40 (AI Agent Orchestration Platform) = самонаполняющаяся база знаний.** Конвейер `inbox/raw → processing → processed` в data20 спроектирован под AI-обработку, но запускается вручную. Оркестратор агентов из info40 может закрыть цикл: агент-сборщик кладёт материалы в inbox, агент-редактор структурирует по шаблонам из docs/TEMPLATES.md, агент-валидатор гоняет validate.py и чинит замечания, агент-индексатор обновляет индексы. Уникальность: полностью автономная KMS, где человек только читает и задаёт темы — редкий работающий пример «agentic knowledge gardening».

4. **data20 + infom (ГрафРАГ) = офлайн GraphRAG-ассистент.** data20 уже строит граф знаний (build_graph, knowledge_graph_builder, backlinks, pagerank), infom занимается GraphRAG. Скормить граф и статьи data20 в GraphRAG-пайплайн infom и подключить локальную LLM — получится карманный вопрос-ответный ассистент по личной базе знаний, работающий офлайн на десктопе (Electron-клиент уже есть). Это превращает data20 из «хранилища» в «собеседника».

## Приоритет

Сначала быстрые пункты 1–2 (CI и порча YAML — это дефекты, а не улучшения), затем решение по сценарию: A — если проект личный, B/C — если хочется продукта, D — если возврата нет. Сочетание №2 (daten22) — самое дешёвое и с максимальным техническим выигрышем.
