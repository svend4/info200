# Характеристика и оценка data20

## Что есть

- **57 CLI-инструментов** в `tools/` — проверено пофайлово по листингу: ровно 57 .py-скриптов; прочитанные (`update_indexes.py`, `validate.py`) — зрелые, по ~700 строк, с argparse, инкрементальностью, multiprocessing, несколькими форматами отчётов.
- **Полноценный production-бэкенд** (`backend/`): FastAPI + JWT-аутентификация с ролями, SQLAlchemy + Alembic-миграции, Celery + Redis с graceful fallback, Prometheus-метрики, structured logging, WebSocket-прогресс задач. Ядро — автообнаружение инструментов через AST (`tool_registry.py`) и асинхронный запуск subprocess-ами (`tool_runner.py`).
- **Тесты и CI**: `tests/` с conftest (in-memory SQLite, TestClient, фикстуры пользователей), unit-тесты (test_auth, test_tool_registry, test_tools_core), папки integration/performance/fixtures; 12 GitHub-workflow, 477 запусков, pytest с coverage и Codecov на матрице Python 3.10/3.11.
- **Мобильное приложение** (Flutter + Chaquopy): экраны логина/инструментов/задач, embedded Python 3.9 + FastAPI + SQLite на устройстве; отдельная lite-версия на stdlib (ThreadingHTTPServer + sqlite3); сборочные скрипты и 8 доков по сборке/подписи/оптимизации. CI-сборки APK на main проходили (по странице Actions).
- **Другие фронтенды**: Electron-десктоп, браузерное расширение на Pyodide (WASM, полностью клиентское), static site generator, Dockerfile (multi-stage).
- **Обширная документация**: подробный README (RU), METHODOLOGY, TEMPLATES, ARCHITECTURE_ANALYSIS, DEPLOYMENT_GUIDE, целая серия инструкций по созданию GitHub-релизов.
- **Релиз v1.0.0** (04.01.2026) с 3 ассетами (без APK).

## Чего нет

- **Контента**: база знаний содержит ~4–5 статей (в `programming/` — ровно 1 файл, cooking — пусто). Система на 10 000 документов работает с пятью. README это честно признаёт («Статей: 5+, начальная структура»).
- **Опубликованного APK**: главная фича («~100MB APK, 100% offline») не доведена до артефакта — RELEASE_NOTES.md прямо говорит, что APK в релиз не включён, собирайте сами.
- **Лицензии**: файла LICENSE нет; в README — неформальное «для личного использования, структуру можно свободно адаптировать».
- **`requirements.txt` в корне**: отсутствует (404 на main), при этом `.github/workflows/tests.yml` выполняет `pip install -r requirements.txt` — в текущем HEAD этот шаг должен падать (зависимости разбросаны по `backend/requirements.txt` и `requirements-test.txt`). Как проходили последние зелёные прогоны — не проверено (возможно, файл был удалён после них).
- **Общего пакета/упаковки**: нет pyproject/setup, инструменты не устанавливаются, общий код между 57 скриптами дублируется.
- **Активности**: с 2026-01-08 — тишина (~6 месяцев), незакрытая ветка `claude/fix-apk-builds-fdMiG`, стабильно падающий `sync-versions.yml`.

## Плюсы

- Редкая для профиля полнота инженерного стека: от CLI до мобильного приложения с embedded-бэкендом, с тестами, CI, Docker и метриками.
- Идея embedded Python-бэкенда на Android (Chaquopy) и её WASM-вариант (Pyodide в расширении) — технически интересные и нетривиальные решения; lite-версия на чистой stdlib показывает осознанную работу над размером APK.
- Осмысленная архитектурная рефлексия: ARCHITECTURE_ANALYSIS.md честно разбирает «55 инструментов: поодиночке или группами, какой фронтенд», решения аргументированы.
- Инструменты не игрушечные: инкрементальная индексация с fingerprinting, PageRank, конкорданс, фасетный поиск, валидация с severity-уровнями.
- Хорошая воспроизводимость истории: авто-changelog, релизные инструкции, фазовые коммиты.

## Минусы

- **Дисбаланс «инструменты vs данные»**: 87% Python-кода обслуживают ~5 markdown-статей; ценность системы управления знаниями без знаний нулевая.
- **Повреждённые данные**: frontmatter реальной статьи `knowledge/computers/articles/ai/llm-overview-2026.md` — это не YAML, а срепрезентированный Python-dict (`{'title': ..., 'date': datetime.date(2026, 1, 2), ...}`) — какой-то из инструментов обогащения (pagerank/quality_score/reading_time) перезаписал метаданные через `str(dict)` и сломал их для всех YAML-парсеров. Конвейер, ради которого всё строилось, портит собственные данные.
- **Расползание вариантов**: 8+ фронтендов (mobile full/lite/versions/sandboxes, desktop, 2 webapp, extension) вместо одного доведённого до конца; ни один не имеет опубликованного дистрибутива.
- **Мусор в git**: кэши (`.index_cache.json`, `.reading_progress.json`), backups/, exports/, сгенерированные индексы закоммичены; корень репозитория — свалка из 60+ md-файлов, включая полдюжины дублирующих инструкций «как нажать кнопку Release».
- **Битый CI в HEAD** (см. «Чего нет» про requirements.txt) и падающий sync-versions.
- **Обрыв на полуслове**: последние коммиты — починка сборки APK, работа не завершена.

## Качество кода и документации

Код (по прочитанным файлам) — выше среднего для профиля: докстринги, тайпхинты, dataclass-ы, enum-ы, аккуратная обработка ошибок, осмысленные абстракции (ToolRegistry/ToolRunner). Однако видна типичная сигнатура AI-генерации в спринте: каждый инструмент раздувался «в 2–3 раза» по плану Tier-ов (коммиты фиксируют «241→722 строки, x3.0»), фичи добавлялись ради фич (SEO-валидация в личной базе), а интеграционное качество (корректность YAML после перезаписи, согласованность requirements) не контролировалось. Документация обильная и в основном честная (RELEASE_NOTES не скрывает отсутствие APK), но избыточная и захламляющая корень.
