# Вопросы к info200

Вопросы владельцу (svend4) по пустому репозиторию, назначенному хабом вики-энциклопедии профиля.

## 1. В каком виде публиковать вики: папка `wiki/` в main, GitHub Wiki или сайт (GitHub Pages/MkDocs)?

Сейчас страницы копятся в `wiki/_staging/`, финальный носитель не выбран, а от него зависит навигация, поиск и процесс правок.

**Варианты ответов**
- А. Папка `wiki/` в main — всё версионируется git, правки через PR.
- Б. GitHub Wiki — проще редактировать, но отдельный git-механизм и слабее ревью.
- В. Статический сайт (MkDocs Material + Pages) поверх папки в main — читабельность и поиск.
- Г. Пока не решено / неважно.

**Варианты дальнейших действий**
- При А: слить staging в `wiki/`, добавить `index.md` и CI-проверку ссылок; закрыть вопрос.
- При Б: написать скрипт синхронизации staging → GitHub Wiki; учесть, что ревью станет слабее.
- При В: добавить `mkdocs.yml`, workflow публикации Pages; staging остаётся источником истины.
- При Г: временно принять вариант А как самый обратимый (обычные файлы в git) и зафиксировать это в README как «решение по умолчанию».

## 2. Кто аудитория вики — человек, ИИ-агенты или обе?

От ответа зависит формат: людям нужны связные тексты и навигация, агентам — машиночитаемые метаданные (yaml/json) с полями «темы, статус, зрелость».

**Варианты ответов**
- А. В первую очередь сам владелец (навигация по своим 61 репо).
- Б. ИИ-агенты (оркестрация из info40/info100, программные запросы к базе знаний).
- В. Обе аудитории равнозначно.

**Варианты дальнейших действий**
- При А: приоритет — индекс, рубрики, короткие обзоры; front-matter не обязателен.
- При Б: добавить в каждую страницу yaml front-matter и/или собрать сводный `catalog.json`; интегрировать с infom (ГрафРАГ).
- При В: двухслойный формат — человекочитаемые страницы + генерируемый из них машинный каталог (сценарий 3 из recommendations.md).

## 3. Как поддерживать актуальность: разовый снимок или регулярная переаудитация?

Профиль активен, страницы вики устареют. Без решения вики за полгода станет вводить в заблуждение.

**Варианты ответов**
- А. Разовый снимок с датой аудита на каждой странице; обновления вручную по мере надобности.
- Б. Периодический роевой переаудит (раз в квартал/полгода) — как текущий, но инкрементально.
- В. Автоматика: CI сверяет метаданные (последний коммит, число файлов) и помечает устаревшие страницы.

**Варианты дальнейших действий**
- При А: добавить в шаблон страницы обязательное поле «дата аудита»; больше ничего не делать.
- При Б: описать процедуру переаудита в `wiki/_staging/CONVENTIONS.md`, завести повторяющийся issue-чек-лист.
- При В: написать workflow (в CI GitHub API доступен штатно), который строит отчёт свежести; страницы старше порога получают плашку «требует перепроверки».

## 4. Что делать с почти пустыми репозиториями-заглушками, которые вики выявляет (data50, information, meta4, свежесозданный info201 и др.)?

По первым 44 аудитам роя статус «почти пустой» получили data50, information, meta4 и сам info200; 2026-07-03 в профиле появился ещё один однострочный info201 (62-й репозиторий). Среди 17 недоаудированных, вероятно, найдутся ещё. Вики может стать инструментом расчистки профиля.

**Варианты ответов**
- А. Оставить как есть — заглушки зарезервированы под будущие идеи.
- Б. Архивировать пустые репо, зафиксировав в вики их «завещание» (что планировалось).
- В. Слить родственные заглушки в несколько тематических монорепо.

**Варианты дальнейших действий**
- При А: в индексе вики ввести статус «резерв», чтобы заглушки не путались с активными проектами.
- При Б: по каждой заглушке — страница-эпитафия в вики, затем archive на GitHub; профиль станет читабельнее.
- При В: спланировать слияния по тематическим осям вики (инфо-ОС, магазины, офлайн); info200 фиксирует карту миграции.

## 5. Нужна ли лицензия на тексты вики, и какая?

Публичный репозиторий без LICENSE: юридический статус текстов не определён, переиспользование (в т.ч. вашими же агентами в других репо) формально ограничено.

**Варианты ответов**
- А. CC-BY-4.0 — свободное переиспользование текстов с указанием авторства.
- Б. MIT — привычная «кодовая» лицензия, годится и для доков.
- В. Без лицензии — контент личный, переиспользование не предполагается.

**Варианты дальнейших действий**
- При А или Б: добавить файл `LICENSE` и строку в README; вопрос закрыт за 5 минут.
- При В: явно написать в README «All rights reserved», чтобы отсутствие лицензии выглядело решением, а не забывчивостью.

## 6. Почему именно info200, а не lorenzo, где уже есть ~2,5–2,8 тыс. md-файлов и docs-toolkit?

Выбор пустого репо под хаб — решение с последствиями: отдельная площадка чище, но инструментарий работы с markdown уже существует в lorenzo.

**Варианты ответов**
- А. Осознанно: вики должна быть отдельной и лёгкой, lorenzo перегружен.
- Б. Случайно/временно: место ещё может поменяться.
- В. Планируется гибрид: вики в info200, но с использованием docs-toolkit из lorenzo.

**Варианты дальнейших действий**
- При А: зафиксировать решение в README info200 и добавить перекрёстные ссылки между репо.
- При Б: отложить серьёзные вложения в структуру (CI, сайт) до финального решения; staging-страницы переносимы.
- При В: подключить docs-toolkit как внешний инструмент сборки/валидации (идея 1 из recommendations.md) — это лучший из вариантов по переиспользованию.
