# Структура info200

## Фактическое дерево (ветка main, коммит 5cffd3b)

```
info200/
└── README.md        # 2 строки: "# info200" и "info" — весь контент репозитория
```

Это не сокращение и не выборка: перечислено всё содержимое репозитория. Скрытых каталогов (кроме `.git`), конфигураций, workflow, `.gitignore`, лицензии — нет. Проверено локальным листингом клона и страницей GitHub.

## Формируемое дерево (staging вики, создаётся текущим аудитом, ещё не влит в main)

```
info200/
├── README.md                     # существующая заглушка
└── wiki/
    └── _staging/                 # черновики страниц вики по каждому репо профиля
        └── <имя-репо>/           # по папке на каждый из 61 репозиториев svend4
            ├── README.md         # обзор: суть, назначение, архитектура, статус, факты
            ├── structure.md      # аннотированное дерево и таблица ключевых файлов
            ├── assessment.md     # что есть/чего нет, плюсы/минусы, зрелость N/5
            ├── recommendations.md# улучшения, сценарии развития, сочетания репо
            └── questions.md      # вопросы владельцу с вариантами ответов/действий
```

## Ключевые файлы

| Файл | Что делает | Состояние |
|---|---|---|
| `README.md` | Заголовок `# info200` и слово `info`; не объясняет ни назначение, ни планы | 2 строки, единственный файл в main |
| `wiki/_staging/info200/*` | Страницы аудита самого info200 (этот комплект) | создаются, не в main |

Точек входа, модулей, конфигов, тестов нет — таблица исчерпана одним файлом.

## Особенности организации

1. **Организации кода нет** — нет кода. Репозиторий на стадии «создан, ничего не добавлено»: один коммит в день создания.
2. **README неинформативен даже как заглушка**: слово «info» повторяет шаблон описаний десятков репозиториев профиля (data15, info10, information и др.) и не отличает будущий хаб вики от остальных «info»-репо. Роль хаба зафиксирована только вне репозитория.
3. **Пустота как преимущество для новой роли**: отсутствие унаследованной структуры позволяет сразу задать чистую схему вики (`wiki/_staging/` → после ревью в корень или в GitHub Wiki) без миграций и конфликтов.
4. **Схема staging** («сначала в `_staging/`, после проверки — публикация») — единственное принятое на данный момент архитектурное решение; финальный вид вики (папка `wiki/` в main, GitHub Wiki, GitHub Pages/MkDocs) ещё не выбран.
