# Рекомендации по info200

Контекст: репозиторий пуст (1 файл), но выбран площадкой вики-энциклопедии профиля svend4 (61 репозиторий). Рекомендации исходят из этой роли.

## Быстрые улучшения

1. **Переписать `README.md`**: заявить роль («Хаб вики-энциклопедии профиля svend4: каталог и аудит 61 репозитория»), описать структуру `wiki/`, добавить ссылку на индекс страниц. Сейчас README («info») не отличает хаб от десятков однотипных репо профиля.
2. **Добавить лицензию** (например, CC-BY-4.0 для текстов вики или MIT) — файл `LICENSE`.
3. **Создать `wiki/index.md`** — главную страницу-каталог: таблица всех 61 репозиториев (имя, одна строка сути, тема, статус, зрелость, ссылка на страницу вики).
4. **Зафиксировать конвенцию страниц** в `wiki/_staging/CONVENTIONS.md`: 5 файлов на репо (README/structure/assessment/recommendations/questions), язык русский, обязательные разделы — чтобы страницы от разных агентов роя были единообразны.
5. **Добавить CI-проверку ссылок** (GitHub Actions + markdown-link-check или lychee) — для вики это аналог тестов; ловит битые перекрёстные ссылки между страницами.
6. **Завести Issues/roadmap**: хотя бы один issue «Наполнение вики: чек-лист 61 репозиториев» с отметками, какие страницы готовы.

## Серьёзные доработки

1. **Процесс публикации staging → main**: определить, как черновики из `wiki/_staging/` после ревью попадают в `wiki/` (PR на каждый репозиторий или пакетные слияния), кто/что делает ревью, как помечается версия аудита и дата актуальности каждой страницы.
2. **Навигация и тематические оси**: сквозные страницы-рубрики («ИИ-агенты», «интернет-магазины», «офлайн-приложения», «инфо-ОС», «базы знаний»), связывающие однотипные репозитории; без них 61×5 = 300+ страниц быстро станут нечитабельными.
3. **Автоматизация актуализации**: скрипт/агент, который периодически сверяет данные страниц (дата последнего коммита, число файлов, статус) с реальностью и помечает устаревшие страницы. Вики об активном профиле без этого протухнет за месяцы.
4. **Публикация как сайт**: MkDocs (Material) или GitHub Pages поверх `wiki/` — поиск, дерево навигации, читабельность; либо перенос в GitHub Wiki, если важна простота правок.
5. **Единый словарь метаданных**: машиночитаемый front-matter (yaml) в каждой странице — язык, статус, зрелость, темы; это позволит генерировать индекс и рубрики автоматически, а не вручную.

## Варианты продолжения

**Сценарий 1 — «Вики-энциклопедия профиля» (базовый, уже запущен).** Довести текущее роевое наполнение до конца: 61 папка в `wiki/_staging/`, ревью, слияние в `wiki/`, главный индекс, рубрики, CI-проверка ссылок. Результат — единый справочник: любой человек или агент за минуты понимает, что есть в профиле, что живо, что заброшено, что с чем сочетать. Это минимальный сценарий, который оправдывает существование info200; трудозатраты в основном уже понесены роем, остаётся редактура и публикация.

**Сценарий 2 — «Живой портал профиля».** Надстроить над вики автоматику: GitHub Actions по расписанию собирает свежие метаданные о репозиториях профиля, обновляет таблицы статусов, строит дашборд («сколько активных, сколько заброшенных, распределение по темам») и публикует статический сайт (MkDocs/Pages). Вики превращается из разового снимка в постоянно актуальный портал. Требует решить вопрос доступа к метаданным GitHub из CI (в самом CI GitHub API доступен штатно) и дисциплины поддержки.

**Сценарий 3 — «Машиночитаемая база знаний для агентов».** Дополнить страницы структурированным слоем: yaml/json с полями (темы, технологии, зрелость, идеи сочетаний) по каждому репо. Тогда вики становится источником данных для ИИ-агентов профиля: оркестратор из info40 или «лаборатория агентов» info100 могут программно спрашивать «какие репо профиля про офлайн-поиск?» и планировать работу. Это переводит info200 из документации в инфраструктуру мультиагентных сценариев, которыми профиль явно интересуется.

**Сценарий 4 — «Слияние с существующим доком-монорепо».** Альтернатива: не растить отдельный хаб, а перенести вики в lorenzo (там уже ~2815 md-файлов и Python-пакет docs-toolkit), а info200 закрыть или оставить редиректом. Плюс — один инструментарий и одно место для всей документации; минус — вики профиля утонет в чужом массиве документов, а lorenzo и так перегружен. Сценарий стоит рассмотреть и осознанно отвергнуть или принять.

## Сочетания с другими репозиториями профиля

1. **info200 + lorenzo (docs-toolkit) = конвейер публикации вики.** В lorenzo уже есть Python-пакет для работы с большими массивами markdown (~2815 файлов). Применить его к `wiki/` info200: валидация структуры страниц, генерация индексов и рубрик, сборка в сайт. Уникальность: инструмент, обкатанный на монорепо документов, получает вторую жизнь как «движок» энциклопедии профиля — вместо двух независимых доков-свалок появляется общий toolchain документации.

2. **info200 + infom (ГрафРАГ) + in4n (динамический информационный граф) = граф знаний профиля с семантическим поиском.** Страницы вики — узлы; темы, технологии и «идеи сочетаний» — рёбра. ГрафРАГ поверх этого корпуса отвечает на вопросы вида «какие репо реализуют офлайн-поиск и с чем их скрестить?» с указанием конкретных страниц. Уникальность: вики перестаёт быть плоским каталогом и становится запрашиваемым графом знаний — редкий случай, когда учебные ГрафРАГ-наработки получают реальный, постоянно нужный корпус.

3. **info200 + info40 (AI Agent Orchestration Platform) + info30 (Claude Code Knowledge System) = самообновляющаяся энциклопедия.** Оркестратор info40 по расписанию запускает агентов-аудиторов (как текущий рой), те перепроверяют страницы устаревших репо и открывают PR с обновлениями; конвенции и знания о Claude Code берутся из info30. Уникальность: вики, которая аудитирует себя сама — профиль из 61 репозитория получает механизм самоописания, а платформа оркестрации — постоянную боевую задачу вместо демо.

4. **info200 + daten22 (offline search, SQLite FTS4) = офлайн-справочник профиля.** Упаковать страницы вики в SQLite с полнотекстовым индексом по схеме daten22 — получить локальный, работающий без сети поиск по всей энциклопедии. Уникальность: сочетание «интерес профиля к офлайн-приложениям» с собственным контентом профиля; удобно и для локальных агентов, которым нельзя в веб.
