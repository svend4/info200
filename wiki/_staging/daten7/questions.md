# Вопросы к daten7

## Вопрос 1. Планируется ли реализация, или daten7 — законченный «бумажный» проект?

Репозиторий содержит только документацию v1.0 (28.12.2025), после merge PR #1 (03.01.2026) активности нет. При этом документы описывают систему вплоть до горячей замены плагинов.

**Варианты ответов:**
- А. Да, реализация планируется, документация — подготовленное ТЗ.
- Б. Нет, это концепт/упражнение в проектировании, реализация не предполагалась.
- В. Реализация планируется, но в другом репозитории/проекте (например, на базе data10 или daten6).

**Варианты дальнейших действий:**
- При А: начать со Сценария 1 из рекомендаций (MVP из 7 модулей по CONFIG_MINIMAL.md), завести issues по одному на модуль, добавить дисклеймер о статусе до готовности прототипа.
- При Б: пометить репозиторий как «спецификация, архив» в описании и README; включить его страницы в вики-хаб info200 как справочник по модульной обработке данных.
- При В: добавить в README ссылку на целевой репозиторий и зафиксировать, какие части спецификации (BaseModule, module.json, паттерны) считаются обязательными для той реализации.

## Вопрос 2. Какая конфигурация является целевой — 7, 20 или 52 модуля?

Документация даёт три уровня с оценками 2–3 недели / 6–8 недель / 6–12 месяцев, но не фиксирует, что именно нужно владельцу.

**Варианты ответов:**
- А. Минимальная (7) — нужен рабочий инструмент быстро.
- Б. Стандартная (20) — целевой уровень «бизнес/ETL».
- В. Максимальная (52) — стратегическая цель, идти поэтапно.

**Варианты дальнейших действий:**
- При А: вычеркнуть из активной документации всё, что не относится к модулям 1–7 (перенести в раздел «будущее»), реализовать MVP, проверить UI-гипотезу аккордеона.
- При Б: составить дорожную карту 7 → 20 с контрольной точкой после MVP; заранее выбрать библиотеки для PDF/Excel/визуализации (они диктуют стек).
- При В: сначала реализовать ядро plug-in системы (APPENDIX_A/B), потому что при 52 модулях без динамической загрузки проект не выживет; модули добавлять волнами по категориям.

## Вопрос 3. Какой технологический стек предполагается для UI и бэкенда?

Примеры кода — Python (pandas, scikit-learn, asyncio), но фронтенд-аккордеон никак технически не специфицирован; не решено даже, серверное это приложение или офлайн.

**Варианты ответов:**
- А. Python-бэкенд (FastAPI/Flask) + лёгкий JS-фронтенд.
- Б. Полностью браузерное офлайн-приложение (JS/WASM, как daten22/data20 в профиле).
- В. Стек не выбран — нужна проработка.

**Варианты дальнейших действий:**
- При А: добавить в архитектурный документ раздел «Стек и деплой», зафиксировать API между аккордеоном и модулями (REST/WebSocket для прогресса).
- При Б: пересмотреть CONFIG-файлы — часть модулей (OCR, БД, email) в офлайн-браузере нереализуема или требует WASM; честно разметить модули по признаку «офлайн-совместим».
- При В: сделать два одностраничных прототипа (серверный и офлайн) на 2–3 модулях и выбрать по результатам.
