## Серьёзные доработки

1. **Реализовать минимальный бэкенд по уже готовому контракту.** Всё для этого есть: `docs/api/openapi.yaml` (18 путей), SQL-миграции, эталонные данные `data/mvp.json`. FastAPI + SQLite/PostgreSQL, генерация моделей из OpenAPI — и репозиторий превращается из «папки спецификаций» в работающий сервис. Начать с `/health`, CRUD функций и `/search` с подключением `ranking.py`.
2. **Оживить прототип**: добавить в `prototype/` немного JS, который грузит `data/mvp.json` + `templates/macros.yaml` (или ходит в новый API) и ранжирует карточки реальным алгоритмом (портировать формулу `ranking_v1` на JS или дергать бэкенд). Тогда UX-концепция «почему рекомендовано» станет демонстрируемой.
3. **Довести словарь функций до заявленного объёма**: functional_spec.md обещает 50 функций / 20 сценариев / 20 приложений; фактический каталог фрагментарен и частично побит. Сгенерировать паспорта по единой схеме и валидировать их в CI.
4. **Нормализовать процесс слияний**: вместо архива README и скриптов-костылей — запрет прямых правок README из веток (CODEOWNERS), линтер конфликт-маркеров в CI, squash-merge.
5. **Свести двуязычие к правилу**: например, спецификации — на русском, контракты и код-комментарии — на английском; вычистить смешанные файлы (docs/architecture/overview.md содержит два параллельных текста).

## Варианты продолжения

**Сценарий А. «Каталог макросов как работающий продукт» (рекомендуемый).**
Сфокусироваться на самой зрелой части — макросах: JSON Schema уже есть, 14 шаблонов есть, спецификация формата есть. Сделать маленький сервис/CLI: валидация макросов по схеме, каталог с поиском и ранжированием (`ranking.py`), простая витрина на базе `prototype/`. Это даёт демонстрируемый MVP за недели, не требуя реализации всей платформы «метаслоя». Критерий успеха — можно открыть страницу, найти макрос «SLA-эскалация», увидеть его рейтинг и параметры.

**Сценарий Б. «Библиотека ранжирования доверия» (извлечение ядра).**
Признать, что платформа целиком не будет построена, и выделить действительно ценное ядро — систему доверия (раздельные рейтинги, verified-использование, анти-спам, сценарное ранжирование) — в отдельный переиспользуемый Python-пакет `trust-ranking`: `ranking.py` + SQL-схемы + спецификация как документация пакета. Опубликовать с pyproject.toml, CI и примерами. Такой пакет применим к любому каталогу (плагины, промпты, датасеты, магазины) и станет «кирпичом» для других репозиториев профиля.

**Сценарий В. «Заморозка с приведением в порядок».**
Если развитие не планируется: выполнить только «быстрые улучшения» (маркеры, apps.yaml, README-оглавление, LICENSE), пометить статус «архив / design-документация» и оформить репозиторий как справочник паттернов проектной документации (паспорта функций, реестр рисков, спецификация системы доверия) — в этом качестве он уже полезен как донор шаблонов для остальных ~60 репозиториев профиля.

**Сценарий Г. «Каталог для ИИ-агентов».**
Переориентировать метаслой с «бизнес-приложений» на инструменты/скиллы ИИ-агентов: паспорт функции ≈ описание инструмента (tool), макрос ≈ workflow агента, verified-использование ≈ телеметрия запусков. Формат MCP-инструментов почти дословно ложится на схему паспорта (входы/выходы/ошибки/ограничения). Это придаёт проекту актуальный рынок и связывает его с агентной линией профиля.

## Сочетания с другими репозиториями профиля

1. **data30 + info40 (AI Agent Orchestration Platform) = маркетплейс проверенных агентных навыков.** info40 оркестрирует агентов, но не решает задачу выбора «какой навык/инструмент взять». data30 даёт готовую систему доверия: паспорта функций, уровни зрелости, verified-usage (лог запусков агента — идеальный источник подтверждения!) и сценарное ранжирование `ranking_v1`. Получается уникальная вещь: оркестратор, который выбирает инструменты не по имени, а по подтверждённой практикой репутации в конкретном сценарии — «рейтинг доверия для tool-calling».

2. **data30 + daten22 / data20 (offline-поиск на SQLite FTS) = офлайн-каталог решений с умным ранжированием.** daten22/data20 умеют полнотекстовый офлайн-поиск (FTS4, embedded backend), data30 — схемы каталога, 14 макросов и алгоритм ранжирования. Комбинация: однофайловое офлайн-приложение «каталог функций и макросов» — FTS ищет, `ranking.py` сортирует по качеству/зрелости/свежести. Инновация — офлайн-инструмент выбора решений для закрытых контуров (без облака), чего нет ни в одном из репо по отдельности.

3. **data30 + meta10 (grep-ast/ast-grep) = автогенерация паспортов функций из реального кода.** Главная слабость data30 — словарь функций заполняется вручную и не дотянут до 50 позиций. ast-grep умеет структурно разбирать код; связка даёт конвейер: сканируем любой репозиторий → извлекаем сигнатуры/докстринги → автоматически формируем паспорта по схеме FUNCTION_PASSPORT.md → загружаем в каталог. «Живой» Function Dictionary, который сам синхронизируется с кодовой базой, — это уже продукт уровня внутренней devtools-платформы.

4. **data30 + infom (ГрафРАГ) или in4n (динамический информационный граф) = граф знаний решений с RAG-поиском.** ADR-0001 в data30 прямо обсуждает графовое хранилище для транзитивных связей Function→Module→UseCase, но не реализует его. ГрафРАГ-механика infom поверх модели данных data30 даёт вопрос-ответный интерфейс: «какие сценарии сломаются, если функция X изменит контракт?» — навигация по графу зависимостей + LLM-объяснения на основе паспортов.
