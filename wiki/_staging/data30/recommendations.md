## Серьёзные доработки

1. **Реализовать минимальный бэкенд по уже готовому контракту.** Всё для этого есть: `docs/api/openapi.yaml` (18 путей), SQL-миграции, эталонные данные `data/mvp.json`. FastAPI + SQLite/PostgreSQL — и репозиторий превращается из «папки спецификаций» в работающий сервис. Начать с `/health`, CRUD функций и поиска с подключением `ranking.py`.
2. **Оживить прототип**: добавить в `prototype/` JS, который грузит `data/mvp.json` + `templates/macros.yaml` (или ходит в новый API) и ранжирует карточки реальным алгоритмом (портировать формулу `ranking_v1` на JS или дёргать бэкенд). Тогда UX-концепция «почему рекомендовано» станет демонстрируемой.
3. **Довести словарь функций и каталог до заявленного объёма и единственной канонической версии**: functional_spec.md обещает 50–61 функцию / 20 приложений; фактические перечни фрагментарны и задвоены. Сгенерировать паспорта по единой схеме и валидировать их в CI.
4. **Нормализовать процесс слияний**: вместо архива README и скриптов-костылей — запрет прямых правок README из веток, линтер конфликт-маркеров в CI, squash-merge, мелкие файлы вместо одного гигантского README.
5. **Свести двуязычие к правилу**: спецификации — на русском, контракты и код — на английском; расклеить смешанные файлы (`docs/architecture/overview.md` содержит два параллельных текста).

## Варианты продолжения

**Сценарий А. «Каталог макросов как работающий продукт» (рекомендуемый).**
Сфокусироваться на самой зрелой части — макросах: JSON Schema уже есть, 14 шаблонов есть, спецификация формата есть. Сделать маленький сервис/CLI: валидация макросов по схеме, каталог с поиском и ранжированием (`ranking.py`), витрина на базе `prototype/`. Это даёт демонстрируемый MVP за недели, не требуя всей платформы «метаслоя». Критерий успеха: открыть страницу, найти макрос «триаж тикетов», увидеть его рейтинг, зрелость и параметры.

**Сценарий Б. «Библиотека ранжирования доверия» (извлечение ядра).**
Признать, что платформа целиком строиться не будет, и выделить действительно ценное ядро — систему доверия (раздельные рейтинги качество/полезность, verified-использование, анти-спам, сценарное ранжирование) — в отдельный переиспользуемый Python-пакет `trust-ranking`: `ranking.py` + SQL-схемы + спецификация как документация пакета. Опубликовать с pyproject.toml, CI и примерами. Такой пакет применим к любому каталогу (плагины, промпты, датасеты, магазины) и станет «кирпичом» для других репозиториев профиля.

**Сценарий В. «Каталог для ИИ-агентов» (переориентация).**
Перенацелить метаслой с «бизнес-приложений» на инструменты/скиллы ИИ-агентов: паспорт функции ≈ описание инструмента (tool), макрос ≈ workflow агента, verified-использование ≈ телеметрия запусков. Схема паспорта (входы/выходы/ошибки/ограничения) почти дословно ложится на формат MCP-инструментов. Это придаёт проекту актуальный рынок и связывает его с агентной линией профиля (info40, info100, info4).

**Сценарий Г. «Заморозка с приведением в порядок».**
Если развитие не планируется: выполнить только «быстрые улучшения» (маркеры, apps.yaml, README-оглавление, LICENSE, разбор PR), пометить статус «архив / design-документация» и оформить репозиторий как справочник паттернов проектной документации (паспорта функций, реестр рисков, спецификация системы доверия, ADR) — в этом качестве он уже полезен как донор шаблонов для остальных ~60 репозиториев профиля.

## Сочетания с другими репозиториями профиля

1. **data30 + info40 (AI Agent Orchestration Platform) = маркетплейс проверенных агентных навыков.** info40 оркестрирует агентов, но не решает задачу выбора «какой навык/инструмент взять». data30 даёт готовую систему доверия: паспорта функций, уровни зрелости, verified-usage (лог запусков агента — идеальный источник подтверждения использования!) и сценарное ранжирование `ranking_v1`. Получается уникальная вещь: оркестратор, который выбирает инструменты не по имени, а по подтверждённой практикой репутации в конкретном сценарии — «рейтинг доверия для tool-calling».

2. **data30 + daten22 / data20 (offline-поиск на SQLite FTS, embedded backend) = офлайн-каталог решений с умным ранжированием.** daten22/data20 умеют полнотекстовый офлайн-поиск, data30 — схемы каталога, 14 макросов и алгоритм ранжирования. Комбинация: однофайловое офлайн-приложение «каталог функций и макросов» — FTS ищет, `ranking.py` сортирует по качеству/зрелости/свежести, UI берётся из `prototype/`. Инновация — инструмент выбора решений для закрытых контуров (без облака), которого нет ни в одном из репозиториев по отдельности.

3. **data30 + meta10 (grep-ast → ast-grep) = автогенерация паспортов функций из реального кода.** Главная слабость data30 — словарь функций заполняется вручную и задвоен. ast-grep умеет структурно разбирать код; связка даёт конвейер: сканируем любой репозиторий → извлекаем сигнатуры/докстринги → автоматически формируем паспорта по схеме `FUNCTION_PASSPORT.md` → загружаем в каталог. «Живой» Function Dictionary, который сам синхронизируется с кодовой базой, — продукт уровня внутренней devtools-платформы.

4. **data30 + infom (ГрафРАГ) или in4n (динамический информационный граф) = граф знаний решений с RAG-интерфейсом.** ADR-0001 в data30 прямо обсуждает графовое хранилище для транзитивных связей Function → Module → UseCase, но откладывает его. ГрафРАГ-механика infom поверх модели данных data30 даёт вопрос-ответный интерфейс: «какие сценарии сломаются, если функция X изменит контракт?» — навигация по графу зависимостей + LLM-объяснения на основе паспортов.

5. **data30 + lorenzo (docs-toolkit) = санация документации как продукт.** Боль data30 — дубли разделов и конфликт-маркеры после агентных слияний — типична для всего профиля. Python-пакет docs-toolkit из lorenzo можно расширить детектором дублей/маркеров и «нормализатором» markdown-корпусов, отладив его на data30 как на эталонном «пациенте». Получается инструмент пост-обработки документации, сгенерированной параллельными ИИ-агентами, — ниша, которой пока нет на рынке.
