# data30 — «метаслой решений»: каталог переиспользуемых функций, сценариев и макросов бизнес-автоматизации

## Обзор

**data30** — это документо-центричный проект по проектированию «метаслоя решений» (solution meta-layer): единого каталога, в котором атомарные **функции**, **модули**, **сценарии (use cases)** и **макросы** бизнес-автоматизации описываются по стандартизированным «паспортам», связываются между собой, оцениваются пользователями (раздельно «качество» и «полезность», с подтверждённым использованием) и ранжируются по сценариям применения.

Описание репозитория на GitHub — «info ос рационал программ» — отражает общую линию профиля svend4 («рациональные информационные программы»), но реальное содержимое гораздо конкретнее: это полный пакет продуктовой и технической документации для платформы каталога решений плюс небольшие исполняемые артефакты:

- **алгоритм ранжирования** `src/ranking.py` (Python, чистая stdlib) с 4 юнит-тестами — тесты реально проходят (проверено локально);
- **HTML/CSS-прототип** экрана поиска сценариев (`prototype/index.html`, ~405 строк);
- **OpenAPI 3.0.3-спецификация** API с 18 путями (`docs/api/openapi.yaml`, валидный YAML);
- **JSON Schema макроса** и **14 готовых шаблонов макросов** (`schemas/macro.schema.json`, `templates/macros.yaml`);
- **SQL-миграции** для журнала аудита и системы отзывов/рейтингов (`migrations/*.sql`).

Основной объём (десятки markdown-файлов) — спецификации: функциональная спецификация (целевой объём: 50 функций, 20 сценариев, 10 макросов, 20 приложений каталога), модель данных, спецификация системы рекомендаций и модерации, реестр рисков, план безопасности, дорожная карта до H2 2026, RACI-планы, QA-отчёты.

## Назначение и идея

Идея проекта — превратить разрозненные решения по автоматизации в управляемый каталог с единым языком описания:

1. **Function Dictionary / паспорта функций** — каждая функция описывается по фиксированной схеме (ID, имя в snake_case, категория, входы/выходы, ошибки, ограничения, пример).
2. **Макросы** — шаблоны автоматизации со структурой «триггер → шаги → условия → ошибки → результат», хранятся в JSON/YAML и валидируются JSON Schema; параметризуются без кода (для no-code пользователей).
3. **Система доверия** — раздельные оценки качества (`quality_rating`) и полезности (`usefulness_rating`), отзывы только при подтверждённом использовании за последние 90 дней (`verified_usage`), уровни зрелости «прототип → стабильное → рекомендовано», анти-спам и модерация.
4. **Ранжирование по сценариям** — реализованный в `src/ranking.py` алгоритм `ranking_v1`: взвешенная сумма качества/полезности/зрелости/подтверждённых отзывов/новизны, множитель свежести (штраф 0.7 при отзывах старше 12 месяцев), штраф за спам-риск, порог минимум 3 подтверждённых отзыва.

Целевая аудитория (по `system_framework.md`): B2B-команды, разработчики, интеграторы и no-code пользователи. Шесть бизнес-вертикалей: маркетинг, продажи, HR, документооборот, поддержка клиентов, финансы.

## Как устроено (архитектура)

Репозиторий организован как «проектный офис» платформы, где код — лишь малая часть:

- **Корень** — 8 ключевых спецификаций: `system_framework.md` (миссия, сущности, глоссарий), `functional_spec.md`, `data_model.md`, `FUNCTION_PASSPORT.md`, `recommendation-system-spec.md`, `integration_inventory.md` (20 внешних систем: SendGrid, Twilio, Okta, S3, Slack, Jira, Salesforce и др. — все контакты и SLA пока `TBD`), `risk-register.md` (10 рисков с планами смягчения).
- **`docs/`** — 18 файлов + 8 подпапок: OpenAPI-контракт, архитектурный обзор (Web UI → API Gateway → Auth → Core Service → PostgreSQL + Cache + Message Broker), ADR-0001 по выбору хранилища (граф vs реляционка), roadmap (MVP H2 2025 → Beta H1 2026 → Scale H2 2026), план безопасности, KPI и метрики.
- **`data/`** — эталонные JSON-примеры модели (mvp.json: функции/модули/юзкейсы с версионированием; recommendations.json). Оба файла — валидный JSON (проверено).
- **Целевая архитектура сервиса** (из документации): REST API v1 c Bearer-аутентификацией, CRUD сущностей, история изменений и rollback (audit_log + change_set в SQL-миграциях), курсорная пагинация.
- **Особенность процесса**: репозиторий собирался автоматизированными агентами (ветки вида `053jns-codex/check-repository`, 106+ pull request'ов, 225 коммитов преимущественно за 9 января 2026). Из-за конвейера мелких веток возникла хроническая проблема конфликтов слияния — под неё созданы отдельные скрипты (`scripts/resolve-readme-conflicts.sh`, `scripts/merge-branch.sh`), инструкции (`docs/merge/`) и архив 12 исторических версий README (`readmes/`). Тем не менее в README.md на main остались **неразрешённые конфликт-маркеры** (`<<<<<<<`/`>>>>>>>`), а `catalog/apps.yaml` — синтаксически битый YAML.

## Статус и активность

- **225 коммитов**, практически все — 9 января 2026 года (один интенсивный «спринт» агентной генерации); последнее обновление репозитория — 18 января 2026. С тех пор (на дату аудита 2026-07-02) активности нет ≈ 5,5 месяцев.
- Ветки: видна только `main`; PR-ов было ≥106 (все слиты/закрыты).
- README фиксирует «Версия: 0.1.0, дата обновления 2026-01-09» — совпадает с историей коммитов.
- Собственные QA-отчёты (`qa/test-results.md` от 2025-09-23) честно фиксируют: тест-раны приложения не выполнялись, QA sign-off **отклонён** — приложения как такового нет. Юнит-тесты ранжирования (`tests/test_ranking.py`, 4 теста) при этом реально проходят — перепроверено в ходе аудита.
- Roadmap обещал Beta-релиз к H1 2026 — по состоянию репозитория этот рубеж не достигнут (кода сервиса нет).
