# Характеристика и оценка data30

Аудит-перепроверка от 03.07.2026. Все ключевые машиночитаемые артефакты скачаны и провалидированы парсерами; юнит-тесты запущены локально.

## Что есть (реально сделано и работает)

- **Работающий модуль ранжирования**: `src/ranking.py` (195 строк) — детерминированный алгоритм `ranking_v1` со сценарными конфигурациями весов, валидацией входных полей и версионированием. **4 юнит-теста в `tests/test_ranking.py` проходят** — перепроверено запуском `python3 -m unittest discover -s tests` (результат: `Ran 4 tests… OK`).
- **Валидные машиночитаемые контракты** (все проверены парсерами при аудите):
  - `docs/api/openapi.yaml` — корректный OpenAPI 3.0.3, ровно 18 путей (CRUD шести сущностей + `/{id}/history`);
  - `schemas/macro.schema.json` — корректный JSON Schema;
  - `templates/macros.yaml` — корректный YAML, 14 шаблонов макросов;
  - `data/mvp.json`, `data/recommendations.json` — валидный JSON;
  - `migrations/001…sql`, `002…sql` — осмысленный PostgreSQL DDL (аудит-лог с before/after JSONB, отзывы с раздельными рейтингами, индексы).
- **Объёмная и местами качественная проектная документация**: спецификация системы доверия (verified-отзывы за 90 дней, анти-фрод, модерация, объяснимость), модель данных с версионированием (SemVer + revision), ADR-0001 с разбором графовой vs реляционной БД (принят PostgreSQL), реестр из 10 рисков с триггерами и буферами, обоснованный выбор приоритетной вертикали (Маркетинг, скоринг 18/20), KPI с формулами (Precision@5 ≥ 55 % на MVP), roadmap с mermaid-Gantt.
- **HTML/CSS-прототип** экрана поиска сценариев (`prototype/`) — статический, но целостно отражающий UX-концепцию («почему это рекомендовано», фильтры по зрелости/совместимости, отзывы с verified-бейджами).
- **Уникальная инфраструктура работы со слияниями**: скрипты `merge-branch.sh` и `resolve-readme-conflicts.sh`, инструкции `docs/merge/`, архив 12 версий README — инженерная реакция на реальную боль конвейера параллельных агентных веток.
- **Честные самоотчёты QA** (`qa/`): тест-раны «Not Run», sign-off отклонён, причины названы прямо.

## Чего нет

- **Нет бэкенда.** REST API описан в OpenAPI и README, но ни одного серверного файла нет: ни фреймворка, ни обработчиков, ни подключения к БД. SQL-миграции не к чему применять.
- **Нет CI** — `.github/workflows` отсутствует; даже имеющиеся 4 теста не запускаются автоматически, YAML/JSON не валидируются (что и позволило битому `apps.yaml` и конфликт-маркерам попасть в main).
- **Нет лицензии** — файла LICENSE нет; правовой статус использования не определён.
- **Нет упаковки/установки** — ни `requirements.txt`, ни `pyproject.toml`; нет инструкции запуска тестов (тест добавляет `src` в `sys.path` вручную).
- **Нет интерактивности в прототипе** — `prototype/index.html` не содержит JS; поиск, фильтры и рейтинги не работают, с `src/ranking.py` прототип никак не связан.
- **Нет связи «данные → код»**: `data/mvp.json` не используется ни ranking.py, ни прототипом; для карточек приложений (`catalog/apps.yaml`) схемы валидации нет вовсе (есть только для макросов).
- **Нет issues и досок** — задачи существовали только как ветки/PR агентов; 27 PR так и остались открытыми.

## Плюсы

1. **Продуманная предметная модель.** Разделение «качество vs полезность», привязка отзывов к подтверждённому использованию, уровни зрелости и сценарное ранжирование — цельная, нетривиальная концепция системы доверия, доведённая до SQL-схем и работающего алгоритма.
2. **Код соответствует спецификации.** Веса, порог 3 verified-отзывов, коэффициент свежести 0.7 после 12 месяцев в `ranking.py` совпадают с текстом `recommendation-system-spec.md` и README — редкая для документо-центричных репозиториев синхронность (сверено при аудите).
3. **Машиночитаемые контракты** (OpenAPI, JSON Schema, SQL DDL) вместо чисто прозаических описаний — готовая база для кодогенерации.
4. **Самокритичность**: QA-папка и реестр рисков не имитируют успех.
5. **Аккуратный Python**: типизация, frozen dataclass, чистые функции, версионирование алгоритма — код читается легко.

## Минусы

1. **Битые артефакты прямо на main.** `README.md` содержит неразрешённые конфликт-маркеры `<<<<<<< 053jns-codex/check-repository … >>>>>>> main` (строки 792–796 и 1182–1193 — проверено); `catalog/apps.yaml` (1165 строк, 31 карточка) не парсится YAML-парсером (ошибка на строке 133, дублированные ключи в карточке Slack); в `prototype/index.html` задвоены секции (нумерация заголовков «1, 3, 2, 4, 3, 4, 5, 6, 7»). Ирония: репозиторий содержит специальные скрипты и инструкции по борьбе именно с этой проблемой.
2. **README-агрегат на 1245 строк** — склейка разнородных документов без оглавления, дублирующая `docs/`; в начале — англоязычная API-документация с плейсхолдером `api.example.com`.
3. **Разрыв «дизайн — реализация» ≈ 95/5.** Roadmap обещал MVP к концу 2025 и Beta к H1 2026; на дату аудита (03.07.2026) сервис не начат, активности нет с 18.01.2026, 27 PR не разобраны.
4. **Шаблонность части документов**: `integration_inventory.md` — 20 систем, но все контакты/SLA «TBD»; RACI и планы — универсальные заготовки без привязки к людям и датам; `docs/registry.md` устарел (помечает как «не созданные» документы, которые уже существуют, например архитектурный обзор).
5. **Дубли внутри документов** — `system_framework.md` содержит миссию/глоссарий трижды, `functional_spec.md` — три версии перечня функций (50/58/61), `FUNCTION_PASSPORT.md` — словарь дважды. Читателю не понятно, какая версия каноническая.
6. **Языковая мешанина** (англ./рус. вперемешку в одном файле) усложняет чтение.

## Качество кода и документации

- **Код** (`ranking.py`): 4/5 — чистый, типизированный, тестируемый. Замечания: `SCENARIO_CONFIGS` инициализируется значениями `None` с последующим `_build_configs()` (хрупкий паттерн); четыре сценарные конфигурации различаются двумя числами — просятся в параметризацию; тест манипулирует `sys.path`.
- **Документация**: содержательно 3.5/5 (глубокая предметная проработка, сквозная модель), редакционно 2/5 (дубли, конфликт-маркеры, битый YAML, устаревший реестр, нет сквозной навигации).
