# Характеристика и оценка data7

## Ограничение покрытия аудита

Репозиторий очень большой (~200+ файлов, десятки тысяч строк). Аудит выполнен без полного клона: прочитаны корневой README, 2 самоаудита, CHANGELOG, README_MASTER, SUMMARY_ru, COMPLETION_SUMMARY, ~10 ключевых файлов кода (точки входа, TSP-библиотека, механики MMO), конфиги (Makefile, docker-compose, CI-workflow, package.json, requirements.txt) и листинги ~15 каталогов. Запуск кода и тестов **не производился** — все утверждения о работоспособности являются проверкой по исходникам, а не исполнением. Статус прогонов GitHub Actions не проверен (страница Actions недоступна через использованные каналы).

## Что есть

- **Реальный, объёмный код**, а не только документы: ~9 корневых Python-прототипов (~5 700 строк суммарно), FastAPI-бэкенд с 15 API-модулями и 9 сервисами (включая `tsp_algorithms.py` на 1494 строки с 8+ алгоритмами TSP), 5 доменных симуляторов (healthcare — 1000 строк), React/TS-фронтенд.
- **Тесты существуют**: `backend/tests/` с разделами unit (7 файлов, в т.ч. `test_tsp_algorithms.py` на 497 строк), integration, load, websocket; `pytest.ini`, `conftest.py`; во фронтенде — Vitest и Playwright e2e-конфигурация.
- **CI/CD настроен**: `.github/workflows/ci-cd.yml` — postgres-сервис, линтеры (black, isort, flake8, mypy), security-сканы (bandit, safety), unit+integration тесты с coverage и загрузкой в Codecov, отдельная фронтенд-джоба.
- **Инфраструктура**: docker-compose (postgres+backend+frontend), Dockerfile для backend/frontend/mmo_ai_bridge_web, Makefile с 20+ целями, monitoring (Prometheus+Grafana), скрипты бэкапа с cron.
- **Обширная документация**: ~90 md-файлов — 68 КБ математической теории TSP для диссертаций (с формулами и теоремами), 45 КБ теории геймдизайна, 8-частные техспецификации, гайды на русском (`SALESMAN_GUIDE_RU.md`, `practical_guide_ru.md`, `case_studies_ru.md`), 9 файлов примеров API в `backend/examples/`.
- **Симуляционная валидация**: скрипты `extended_economy_analysis.py` (10 прогонов, масштаб 50–500 игроков, 365 дней) и `simple_tsp_benchmark.py` реально существуют и соответствуют заявленной методике (сами цифры не перепроверялись запуском).
- **Самоаудиты**: `PROJECT_STATUS_v8.0.md`, `PROJECT_STATUS_CURRENT.md`, `MMO_AI_BRIDGE_COMPREHENSIVE_AUDIT.md`, `COMPLETE_LEVELS_AND_VERSIONS_AUDIT.md` — проект рефлексирует над собственным состоянием (хотя и противоречиво, см. ниже).

## Чего нет

- **Лицензии** — файла LICENSE нет; README ограничивается фразой «Research project — contact for licensing». Для 6 подпроектов с амбициями публикации это блокер повторного использования.
- **Релизов и тегов** — ни одного GitHub Release при версиях «v4.5», «v8.0», «v1.1» в документах.
- **Подтверждённого прохождения тестов/CI** — статус Actions не проверен; учитывая, что workflow гоняет mypy и flake8 по большому AI-сгенерированному коду, «зелёный» статус не гарантирован (не проверено).
- **Единого корневого README о монорепо** — корневой README описывает только MMO RPG-подпроект; о Meta-Orchestrator, симуляторах и трансформаторе знаний новый читатель узнаёт случайно.
- **Упаковки** — нет pyproject.toml/setup.py для корневых прототипов; они не устанавливаются как пакет, импортируются только из текущего каталога.
- **Реальных данных и интеграций** — «валидация» целиком симуляционная: нет ни одной реальной MMO, ни одного реального корпуса диссертаций, на которых проверены алгоритмы; заявленные эффекты («-60% выгорания», «+36% retention») — теоретические экстраполяции.
- **Тестов для корневых прототипов** — pytest покрывает только backend; `dissertation_optimizer.py`, `knowledge_transformer.py`, `mmo_rpg_mechanics.py` тестов не имеют.
- **Issues/процесса** — активность двумя всплесками (4–5 февраля и 14 марта 2026), задачного трекинга не видно.

## Перепроверка самозаявлений (аудит-перепроверка)

Репозиторий содержит десятки статус-отчётов; их заявления **противоречат друг другу**:

| Источник | Дата | Заявление |
|---|---|---|
| `README.md` (корень) | 04.02.2026 | «95% Complete, Production Ready», код 1 598+ строк, качество 4.9/5 |
| `PROJECT_STATUS_v8.0.md` | 04.02.2026 | «Concept & Design Phase», **«код пока не реализован»**, production code 0% по всем 4 компонентам, общая зрелость 40% |
| `PROJECT_STATUS_CURRENT.md` | 05.02.2026 | Meta-Orchestrator «48% Complete (Week 4–5 из 32)», TRL 4.0 |
| Коммит 05.02.2026 | 05.02.2026 | «Comprehensive Project Status Report — DATA7 (91% Complete)» |
| Коммит 05.02.2026 (позже) | 05.02.2026 | «Complete Remaining Features — Project 100% Ready!» |

Выводы перепроверки:

1. **Проценты готовности ненадёжны**: 40% → 48% → 91% → 100% за двое суток — это инфляция отчётности, а не реальный прогресс по 32-недельному плану из `TECHNICAL_SPEC_PART8_ROADMAP.md`.
2. **README устарел и занижает масштаб**: заявленные «1 598+ строк кода» не соответствуют действительности — только корневые прототипы дают ~5 700 строк, а backend — ещё десятки тысяч. При этом «Production Ready» **завышает** зрелость: продукт нигде не развёрнут, реальных пользователей нет.
3. **Честный документ существует**: `PROJECT_STATUS_v8.0.md` — самый адекватный самоаудит («прототипы, не production»), но он датирован до основного спринта и тоже устарел.
4. **Цифры валидации правдоподобны, но не воспроизведены**: скрипты симуляций и бенчмарков в наличии и по коду соответствуют описанной методике; сами значения (0.153 мс, 100% попадание в ±20%) помечаем «не проверено запуском».
5. **Сравнения с WoW/FFXIV/EVE и «Best-in-class»** — маркетинговые утверждения без внешней проверки.

## Плюсы

- Редкое для профиля сочетание: теория (математика с теоремами) + прототипы + production-стиль сервис + инфраструктура в одном репозитории.
- Оригинальная сквозная идея (TSP как универсальный оптимизатор «когнитивных маршрутов») последовательно проведена через 6 доменов, включая взаимные импорты в коде.
- Грамотная слоистая архитектура backend (api/services/domain/infrastructure, DI, Alembic, Repository pattern — подтверждено `PROJECT_STATUS_CURRENT.md` и структурой каталогов).
- Полный DevOps-контур «на бумаге»: CI со security-сканами, мониторинг, бэкапы, Makefile.
- Богатая русскоязычная методическая документация по TSP для диссертаций — самостоятельная ценность.

## Минусы

- Хаос в корне: ~90 отчётов/спецификаций перемешаны с кодом; 7+ «финальных» отчётов только по MMO RPG.
- Систематическое завышение статусов в отчётах (см. таблицу выше) — типичный артефакт AI-генерации «отчётов об успехе».
- Нет ни одного внешнего подтверждения работоспособности: релизов, демо, скриншотов развёрнутой системы, «зелёных» бейджей CI (бейджи в README — статические картинки shields.io, не привязанные к реальному CI).
- Монорепо объединяет слабо совместимые по зрелости вещи — исследовательские эссе (Diffusion VFX) и production-код — без модульных границ.
- Redis и Celery заявлены в требованиях и main.py (Phase 9), но в docker-compose закомментированы — рассинхронизация конфигурации.
- Прототипы в корне не покрыты тестами и не упакованы.

## Качество кода и документации

- **Код** (по прочитанным фрагментам): аккуратный, с докстрингами, типизацией (typing, Pydantic), dataclass-структурами, разумной декомпозицией; в `main.py` — корректный lifespan с graceful shutdown и деградацией без Redis. Стиль однородный, «клодовский». Уровень — хороший прототипный/ранний production.
- **Документация**: очень объёмная и местами качественная (теория TSP, техспецификации), но избыточная, дублирующаяся и противоречивая в статусах; отсутствие единой навигации по монорепо снижает её полезность.

## Зрелость: 3/5

Обоснование: это существенно больше, чем эксперимент выходного дня — есть архитектурный backend с тестами, CI, Docker, миграциями и примерами (заслуженные 3 балла). До 4/5 не дотягивает из-за: отсутствия лицензии и релизов, неподтверждённого прохождения тестов/CI, чисто симуляционной валидации без реальных данных, противоречивых статус-отчётов и разовой (двухдневной) модели разработки. Честный статус проекта — «продвинутый прототип-исследование», а не «Production Ready 95%».
