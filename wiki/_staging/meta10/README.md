# meta10 — аналитический разбор grep-ast и проект пайплайна «grep-ast → ast-grep»

## Обзор

**meta10** — это не программный проект, а репозиторий-контейнер для одного большого аналитического документа. Всё содержимое — файл `review-habr-ecom-article.md` (841 строка, ~64 КБ): глубокий, критический разбор статьи на Хабре «Grep-AST или как мы заменили векторный поиск всего одной библиотекой» (команда LLM-приложений ecom.tech, март 2026). Описание репозитория на GitHub — «info, grep-ast → ast-grep — естественный двухстадийный пайплайн» — отражает главный собственный вклад документа: спроектированный автором двухстадийный пайплайн поиска по коду, где grep-ast работает широким «ситом» первой стадии, а ast-grep — точным структурным фильтром второй.

Кода в репозитории нет. README состоит из двух строк («# meta10» и «info») и не выполняет никакой роли. Вся ценность сосредоточена в одном документе, который, однако, заметно превосходит по глубине саму рецензируемую статью: автор разбора самостоятельно проанализировал исходный код библиотеки grep-ast (версия 0.9.0) и выявил ключевое расхождение между тем, что статья подразумевает, и тем, как инструмент устроен на самом деле.

## Назначение и идея

Документ решает три задачи по нарастающей:

1. **Рецензия статьи.** Подробный пересказ и структурирование материала ecom.tech: задача reverse engineering документации (извлечение REST-эндпоинтов и Kafka-продюсеров/консьюмеров из кода сотен микросервисов на Go, Kotlin, Ruby, Elixir, PHP), три «тупиковых» подхода (tree-sitter напрямую, RAG-пайплайн с точностью 85%, regex+grep) и итоговое решение — grep-ast как tool call для LLM-агента.

2. **Независимая перепроверка по исходникам.** Автор разбора прочитал код grep-ast и показал: метод `grep()` в `TreeContext` — это чистый построчный `re.search()`; AST используется **только** для контекстуализации результата (родительские скоупы, дочерние блоки), но **не** для фильтрации. Следовательно, grep-ast не решает проблему ложных срабатываний (`@GetMapping` в Javadoc он найдёт так же, как настоящую аннотацию) — вопреки впечатлению, которое создаёт статья. Всего сформулировано **8 критических проблем** статьи: от асимметрии измерений (85% у RAG против «стало лучше» без цифры) до ложных отрицаний при метапрограммировании (Rails `resources`, Elixir-макросы) и непоказанного промпта агента. *Наш аудит перепроверил это утверждение по актуальному исходнику `Aider-AI/grep-ast` — оно верно (см. assessment.md).*

3. **Собственное архитектурное предложение.** Раздел 11 проектирует двухстадийный пайплайн: grep-ast обрабатывает весь репозиторий широким regex и даёт LLM-friendly структурный контекст; ast-grep валидирует кандидатов структурными YAML-паттернами (отличает код от комментариев, захватывает переменные `$PATH`, `$HANDLER`). Приведены конкретные пары паттернов для всех пяти языков задачи, схема tool calls для LLM-агента, таблицы плюсов/минусов и рисков (каскад ошибок стадии 1, удвоение поддержки паттернов). Завершается всё 12 практическими выводами.

## Как устроено (архитектура)

Репозиторий плоский: два markdown-файла в корне, папок нет. «Архитектура» — это структура самого документа: 12 пронумерованных разделов, идущих от пересказа (разделы 1–7) через критику (8–10) к собственному проектному предложению (11) и выводам (12). Подробное оглавление — на странице [Структура](structure.md).

Документ создавался итеративно через Claude Code: 9 коммитов за один день (5 марта 2026), три пул-реквеста (#1–#3) из ветки `claude/review-habr-ecom-article-MjaMf`, смёрженных владельцем. Эволюция по сообщениям коммитов: первичный англоязычный черновик → переписывание на русский → расширение деталей и таблиц → «глубокий разбор: анализ исходного кода grep-ast, 8 критических проблем» → «анализ двухстадийного пайплайна grep-ast → ast-grep». То есть репозиторий — типичный для профиля svend4 «info»-контейнер, где артефакт наращивался в несколько проходов агентом под контролем владельца.
