# Характеристика и оценка ingit

## Что есть

- **Отличная проектная документация** (~4 300 строк, 7 файлов в docs/): методология с честным сравнительным анализом конкурентов (Git, GitLab CE, Gitea, Fossil), спецификация БД на 933 строки, план реализации с фазами и оценками сроков (10–16 месяцев до v1.0), спецификация API, ASCII-wireframes UI, гайд по деплою, каталог инновационных идей. Это уровень полноценного design document.
- **Каркас FastAPI-бэкенда**: рабочая точка входа (`backend/ingit/main.py`), конфигурация через pydantic-settings, роутеры с корректными Pydantic-схемами запросов/ответов, эндпоинты `/api/health` и `/api/ping`.
- **6 ORM-моделей** (`backend/ingit/db/models.py`, 351 строка): User (с полями 2FA), Project, Repository, Task (иерархия, epics), Document (YAML-метаданные, checksum), FinancialRecord, Commit — с CheckConstraint'ами и индексами, аккуратно по DATABASE_SPEC.
- **CLI-инструмент** (`backend/ingit/cli/main.py`, 349 строк, click): `ingit init` создаёт структуру папок 00–90 с YAML-профилем и git init; `task create/list` работают с YAML-файлами напрямую. Не зависит от сломанных моделей БД — концептуально самая живая часть кода.
- **Git-хуки на Python** (`scripts/hooks/pre-commit` 186 строк, `post-commit` 80 строк): валидация YAML-метаданных, запрет коммитов из `00_inbox/`, контроль размера файлов, автозакрытие задач; плюс `install-hooks.sh` и генератор отчётов `generate-report.py` (222 строки).
- **Демо-проект** `examples/demo-project/` («E-Commerce Platform MVP») — наглядный пример структуры InGit с реальными YAML-задачами, финансами, договором, таймлайном.
- **Инфраструктура**: два docker-compose (стек + мониторинг), Dockerfile'ы backend/frontend, CI/CD workflows, Makefile на ~35 целей, pre-commit-конфиг, alembic, monitoring/prometheus.yml + alerts.
- **LICENSE MIT**, CONTRIBUTING.md, CHANGELOG.md, QUICKSTART.md.

## Чего нет

- **Работающей функциональности API**: все CRUD-эндпоинты projects/tasks/documents — стабы `# TODO: Implement with database`, возвращают пустые списки, 501 или 404.
- **Проходящих тестов**: файлы тестов есть (5 файлов, ~20+ кейсов), но не выполняются (см. «Минусы»). Coverage-отчёты и «26+ test cases ✅» из CHANGELOG — фикция в смысле прохождения.
- **Git-интеграции**: `pygit2` заявлен в README/CHANGELOG и закреплён в requirements.txt (`pygit2==1.14.0`), но **ни один файл кода его не импортирует**. «Git-платформа» пока не работает с Git через API вообще.
- **Реального фронтенда**: одна статическая страница «Coming Soon»; antd, redux, monaco, recharts из package.json не используются; Electron-приложение заявлено, но `src/electron/main.js` отсутствует (404) — `npm run electron:*` сломаны.
- **Аутентификации/шифрования**: SECRET_KEY и JWT-настройки в конфиге есть, эндпоинтов auth нет; заявленное шифрование (age/SQLCipher) не реализовано.
- **Заявленного стека мониторинга целиком**: в `monitoring/` видны только prometheus.yml и alerts/; Grafana-дашборды и Loki из CHANGELOG не обнаружены (не проверено глубже листинга папки).
- **Зелёного CI**: workflow есть, но backend-джоба падает на pytest (импорт models). Фактические прогоны Actions не проверялись.
- **Упаковки как продукта**: setup.py указывает на несуществующие URL (github.com/ingit/ingit, ingit.readthedocs.io); публикации в PyPI нет.

## Плюсы

1. Редкая для профиля глубина проработки концепции: документация тянет на серьёзный design doc, идеи (Metadata as Code, гибрид Git+SQL, offline-first PM) внятные и оригинальные.
2. Целостная структура монорепозитория: docs → backend → frontend → infra → examples; всё названо и разложено правильно.
3. Файловый контур (CLI + git-хуки + YAML-структура 00–90 + демо-проект) самодостаточен и близок к работоспособности без БД и сервера.
4. Хорошие практики «на бумаге»: Pydantic-схемы, CheckConstraint'ы и индексы в моделях, pre-commit, Makefile, multi-stage Docker, Keep a Changelog.
5. README честен о стадии («Проектирование и документирование») и содержит трезвый раздел «Не подходит для».

## Минусы

1. **Критический баг, блокирующий весь бэкенд**: во всех 6 моделях объявлена колонка `metadata = Column(Text)`, а имя `metadata` зарезервировано в Declarative API SQLAlchemy. Проверено локально на закреплённой версии sqlalchemy==2.0.25: `InvalidRequestError: Attribute name 'metadata' is reserved when using the Declarative API`. Следствия: `ingit.db.models` не импортируется → `create_tables()` из QUICKSTART падает, все тесты падают на этапе сбора, CI красный. Код очевидно ни разу не запускался.
2. **Тесты написаны не по коду**: `test_api_health.py` ожидает `{"status": "ok"}` и эндпоинт `/api/health/db`, тогда как `health.py` возвращает `"healthy"` и `/db`-эндпоинта не имеет. Даже после исправления бага №1 тесты не пройдут.
3. **CHANGELOG систематически выдаёт план за сделанное**: «✅ Git integration via pygit2» (нет ни одного импорта), «✅ 26+ test cases» (не проходят), «✅ Grafana dashboards / Loki» (в репо не видны), «✅ CLI `ingit doctor`» (не подтверждено чтением). Это главный вывод аудита-перепроверки.
4. Расхождения мелочей: README пишет «лицензия будет определена позже», хотя LICENSE MIT уже лежит в корне; setup.py ссылается на чужие/несуществующие URL; `App.tsx` импортирует неиспользуемый `useState` (упадёт на eslint `--max-warnings 0`).
5. Один день реальной работы (все контент-коммиты 01.02.2026, авторство `claude`), затем только merge в апреле — проект не развивается.
6. Инфраструктура (мониторинг, CD, PostgreSQL, Electron) на порядок опережает приложение — сопровождать её нечем.

## Качество кода и документации

- **Документация: 4.5/5.** Структурирована, конкретна, на русском, с таблицами сравнения, roadmap и спецификациями. Небольшой минус — маркетинговый тон и дублирование между файлами.
- **Код: 2/5.** Стиль чистый (типизация, docstrings, схемы), но код не верифицирован исполнением: блокирующий баг в моделях, тесты не соответствуют реализации, мёртвые зависимости (pygit2, age, antd и др.), битые ссылки в setup.py/package.json. Это типичный артефакт одной генерационной сессии без запуска.
- **Перепроверка самоотчётов**: README-статус («проектирование») — соответствует реальности; CHANGELOG 0.1.0 — существенно завышен (см. Минусы, п. 3); QUICKSTART — шаг «Создать БД» невыполним из-за бага №1.

## Зрелость: 2/5

Обоснование: репозиторий — качественный концепт с полной проектной документацией (это тянуло бы на 2.5–3 для «проекта-спецификации»), но заявленная реализация не работает: бэкенд не импортируется, тесты не проходят, CI красный, фронтенд — заглушка, Git-интеграции нет. От «1» спасают документация, автономный CLI/хуки-контур и продуманная структура; до «3» не дотягивает отсутствие хотя бы одного проверяемо работающего сквозного сценария.

*Ограничение покрытия*: прочитано ~20 ключевых файлов кода и конфигов; docs/ — выборочно; `cd.yml`, migrations/, monitoring/alerts/, YAML демо-проекта, хвост CLI (report/doctor) — не читались. Запуск проекта не производился (только точечная верификация бага SQLAlchemy на закреплённой версии).
