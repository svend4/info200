# Рекомендации по ingit

## Быстрые улучшения

1. **Исправить блокирующий баг моделей**: переименовать колонку `metadata` во всех 6 моделях `backend/ingit/db/models.py` (например, в `meta_json = Column("metadata", Text)` или просто `extra_metadata`) — имя `metadata` зарезервировано в Declarative API SQLAlchemy. Без этого не работает вообще ничего в бэкенде.
2. **Синхронизировать тесты с кодом**: привести `test_api_health.py` в соответствие с `health.py` (сейчас тест ждёт `"status": "ok"` и `/api/health/db`, код возвращает `"healthy"` и такого эндпоинта не имеет) — либо, наоборот, доработать health-эндпоинты под тесты.
3. **Прогнать pytest и CI хотя бы один раз** и добиться зелёного статуса; добавить бейдж CI в README.
4. **Честный CHANGELOG**: перевести невыполненные пункты (pygit2, Grafana/Loki, «26+ tests») из «Added ✅» в «Planned» — сейчас файл вводит в заблуждение.
5. **Убрать/поправить битые артефакты**: несуществующий `src/electron/main.js` в package.json (или добавить файл), URL `github.com/ingit/ingit` и `ingit.readthedocs.io` в setup.py, неиспользуемый `useState` в App.tsx, фразу «лицензия будет определена позже» в README (LICENSE MIT уже есть).
6. **Подчистить requirements.txt** от неиспользуемых зависимостей (pygit2, age, pyotp, python-jose) или пометить их как «для будущих фаз» в комментариях.
7. Добавить в README прямые команды запуска единственного работоспособного контура: `ingit init` + git-хуки + `generate-report.py` на демо-проекте.

## Серьёзные доработки

1. **Реализовать хотя бы один сквозной сценарий**: например, Tasks API поверх SQLite — создание/список/смена статуса задачи из БД, с реальными проходящими тестами. Это переведёт проект из «концепта» в «прототип».
2. **Настоящая Git-интеграция**: подключить pygit2 (или обёртку над git CLI) — индексация коммитов в таблицу Commit, связывание коммитов с задачами по сообщению (это уже делает post-commit-хук на файловом уровне — перенести в API).
3. **Выбрать ядро и отсечь лишнее**: инфраструктура (PostgreSQL, Prometheus, CD, Electron) сильно опережает приложение. Для offline-first продукта логичнее «SQLite + один бинарь/CLI», а весь monitoring/compose отложить до фазы Beta, как и предусматривает собственный IMPLEMENTATION_PLAN.md.
4. **Синхронизация файлового и БД-контуров**: сейчас CLI пишет YAML, а API «должен» писать в БД — нужен индексатор YAML→SQLite (watcher или команда `ingit sync`), это и есть заявленная инновация «Hybrid Storage», пока не реализованная.
5. **MVP фронтенда**: заменить «Coming Soon» на простейший Kanban по данным Tasks API (antd уже в зависимостях), Electron отложить.
6. Реализовать заявленное шифрование папки `40_finance/` через age (зависимость уже закреплена) как отдельную CLI-команду.

## Варианты продолжения

**Сценарий 1: «Файловый минимализм» — InGit как CLI-инструмент без сервера.**
Отказаться (временно) от FastAPI/React/Docker и довести до блеска то, что почти работает: `ingit init`, YAML-задачи, git-хуки, отчёты, шифрование финансов через age. Получится устанавливаемый через pipx консольный продукт «Git-органайзер жизни и проектов» в духе вдохновившей статьи с Хабра. Это достижимо за недели, даёт реальных пользователей и обратную связь по методологии 00–90, а сервер/GUI можно наращивать потом поверх проверенной файловой модели.

**Сценарий 2: «Прототип платформы» — довести бэкенд до рабочего MVP по собственному плану.**
Следовать docs/IMPLEMENTATION_PLAN.md: починить модели, реализовать CRUD поверх SQLite, добавить индексацию YAML→БД и простую Kanban-страницу. Цель — самостоятельно хостящаяся локальная веб-платформа для одного пользователя/малой команды (аналог «локальной Jira поверх Git»). Дороже сценария 1, но именно это обещает README; критерий успеха — зелёный CI и работающий docker-compose up с реальными задачами.

**Сценарий 3: «Спецификация как продукт» — оформить InGit как открытый стандарт.**
Признать, что ценность репозитория — методология и спецификации, и развивать их: выделить «InGit Project Layout» (структура 00–90 + YAML-схемы метаданных + соглашения о хуках) в версионируемый стандарт с JSON Schema для валидации, референсными хуками и каталогом совместимых инструментов. Реализации могут делать другие (или другие репозитории профиля). Это дёшево, честно относительно текущего состояния и хорошо сочетается с «инфо-системными» репозиториями профиля svend4.

**Сценарий 4 (дополнительный): архивировать с честным статусом.**
Если возврата к проекту не планируется — пометить в README «концепт, разработка не ведётся», исправить CHANGELOG и оставить как качественный design doc в портфолио.

## Сочетания с другими репозиториями профиля

1. **ingit + daten20 (Document Management System) = локальная DMS поверх Git.**
   У ingit есть модель Document с YAML-метаданными (стороны, суммы, сроки действия, checksum), папочная структура `30_documents/` и pre-commit-валидация; daten20 — система управления документами. Объединение даёт офлайн-DMS, где каждый документ версионируется Git'ом, метаданные валидируются хуками, а поиск идёт через SQLite-индекс — «Paperless-ngx без сервера», уникальная ниша для домашнего архива и малого бизнеса.

2. **ingit + info40 (AI Agent Orchestration Platform) = агентная фабрика, доводящая скелет до MVP.**
   ingit — идеальный полигон для оркестрации ИИ-агентов: есть полные спецификации (DATABASE_SPEC, API_SPEC, IMPLEMENTATION_PLAN) и пустые стабы с TODO. Оркестратор из info40 может раздавать агентам задачи «реализовать эндпоинт по спецификации + добиться зелёного теста», а InGit-структура задач (YAML в `70_tasks/`) станет нативным форматом очереди работ для агентов. Инновация: замкнутый цикл «спецификация → агент → код → тест → задача закрыта коммитом» на реальном проекте.

3. **ingit + daten22 (offline search app, SQLite FTS4) / data20 (offline app, embedded backend) = полнотекстовый офлайн-поиск по InGit-архиву.**
   Гибрид «Git + SQL» из методологии ingit не реализован; daten22 уже умеет офлайн-поиск на SQLite FTS. Скрестив их, получаем индексатор, который складывает YAML-задачи, документы, вики и сообщения коммитов в FTS-таблицы — мгновенный поиск по всему личному архиву без сервера. Это закрывает главное практическое обещание InGit («быстрый поиск по локальным данным») минимальными средствами.

4. **ingit + data4 (перс. бюджет) = офлайн-финансы, версионируемые Git'ом.**
   Модель FinancialRecord и папка `40_finance/` из ingit плюс логика персонального бюджета из data4 дают «бюджет как код»: каждая транзакция — YAML-файл в Git с историей изменений, отчёты генерируются generate-report.py, критичные данные шифруются age. Уникально: аудируемая история личных финансов средствами системы контроля версий.
