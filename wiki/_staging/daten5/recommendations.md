# Рекомендации по daten5

## Быстрые улучшения

1. **Починить docker-compose.yml**: удалить первый (устаревший) блок `api-gateway` (~стр. 252) — оставить второй, с BLUEPRINT_ENGINE_URL; убрать или закомментировать монтирования `./infrastructure/prometheus/...` и `./infrastructure/grafana/...` (либо создать эти конфиги). Без этого `docker-compose up` не воспроизводим.
2. **Синхронизировать README с реальностью**: убрать из дерева несуществующие `frontend/cli`, `infrastructure/`, `docs/api`, `docs/guides`, `scripts/`, `compatibility-engine` или пометить их как «планируется».
3. **Добавить файл LICENSE** (MIT уже заявлена в package.json) и удалить ссылку на несуществующий CONTRIBUTING.md.
4. **Создать `scripts/migrate.js` и `scripts/seed.js`** (или убрать команды из package.json/GETTING_STARTED); сид с 20–50 приложениями сразу оживит каталог и демо.
5. **Дописать страницу `/blueprints`** или убрать ссылку с главной; подключить `/applications` и `/chat` к уже существующим API (lib/api.ts готов).
6. **Один smoke-тест**: GitHub Action, который делает `docker compose config` (поймал бы дубликат ключа) и `npm ci && node --check` по сервисам — полчаса работы, резкий рост доверия.
7. Заменить дефолтные `changeme123` на обязательные переменные без значений по умолчанию.

## Серьёзные доработки

- **Один подтверждённый end-to-end сценарий**: поднять компоуз → прогнать github-crawler на 50 репозиториях → увидеть их в каталоге через REST/GraphQL → отобразить на странице /applications. Это переведёт проект из «скелета» в «прототип» (зрелость 3/5).
- **Решить судьбу Elasticsearch и RabbitMQ**: либо реализовать индексацию в ES и перевести поиск с ILIKE, либо выкинуть оба сервиса из compose (Bull на Redis уже покрывает очереди) — минус 2 тяжёлых контейнера.
- **Тесты ядра**: unit-тесты на резолверы catalog-api и WorkflowExecutor (шаги, отмена, прогресс), интеграционные — на schema.sql через testcontainers.
- **Реализовать хотя бы 3 настоящих blueprint'а** (например, «магазин», «мониторинг», «контент-пайплайн») и прогнать их через WorkflowExecutor — сейчас концепция макросов существует только в тексте.
- **Обновить ИИ-слой**: код использует устаревшие openai-вызовы (`openai.api_key`, gpt-3.5-turbo, ada-002); мигрировать на актуальный SDK и модели, вынести LLM-клиент в общий модуль.
- **Compatibility-engine** из манифеста так и не создан — либо реализовать минимальную проверку совместимости по графу Neo4j, либо вычеркнуть из архитектурных документов.

## Варианты продолжения

**1. «Каталог-для-профиля»: рационализация собственных 61 репозиториев.**
Самый прагматичный путь: направить github-crawler не на весь GitHub, а на профиль svend4. Каталог заполнится реальными данными (61 приложение, их языки, зависимости, README), Neo4j-граф покажет фактические пересечения между daten*/info*/data*-проектами, а nl-interface станет чат-навигатором по собственному портфелю. Это одновременно демо платформы и рабочий инструмент для хаба info200 — идея «рационализации» проверяется на собственной экосистеме, где проблема фрагментации стоит буквально.

**2. «Минимальный вертикальный продукт»: AI-подбор стека по описанию задачи.**
Сжать амбиции до одного сценария из манифеста: пользователь описывает задачу текстом → solution-composer подбирает 3–5 компонентов из каталога → выдаёт blueprint с оценкой стоимости. Для этого достаточно catalog-api + ai-classifier + solution-composer + одна страница фронтенда; gateway, Neo4j, ES, RabbitMQ на время убрать. Узкий, но работающий продукт ценнее широкого скелета, и его можно показать как proof-of-concept манифеста.

**3. «Манифест-первым»: развить документ, заморозить код.**
Признать, что главная ценность — концепция. Вынести rationalization-proposal.md в отдельную публикацию (статью/серию), добавить обзор существующих аналогов 2026 года (MCP-экосистема, каталоги агентских инструментов, awesome-списки с ИИ-индексацией — мир заметно сдвинулся в эту сторону), а код оставить как приложение-иллюстрацию с честной пометкой «прототип». Дешёво, честно и сохраняет идею живой до появления ресурсов на реализацию.

**4. «Слияние с daten12»: единая линия «рационал инфо программ».**
daten12 имеет идентичное описание («Info рационал инфо программ») — проверить пересечение и либо слить, либо явно разграничить роли (например, daten12 — теория/документы, daten5 — платформа), чтобы убрать дублирование в профиле. (Содержимое daten12 в этом аудите не проверялось — см. вопросы.)

## Сочетания с другими репозиториями профиля

1. **daten5 + meta10 (grep-ast → ast-grep) = краулер с глубоким анализом кода.**
   Сейчас github-crawler извлекает только метаданные и списки зависимостей. Прикрутив ast-grep/tree-sitter-анализ из meta10, краулер сможет извлекать реальные capabilities из кода (какие API экспортирует библиотека, какие паттерны использует), а не угадывать их LLM-ом по README. Получится уникальный «семантический индексатор функциональности» — ровно тот компонент, которого манифесту не хватает для «Периодической таблицы софта», и которого нет у обычных каталогов типа libraries.io.

2. **daten5 + infom (ГрафРАГ) = GraphRAG-навигатор по каталогу решений.**
   У daten5 уже есть Neo4j-граф приложений и pgvector-эмбеддинги, у infom — методика графового RAG. Соединение даёт nl-interface, который отвечает не по одному документу, а обходом графа: «что заменит X», «какой стек собрать под задачу Y и почему», с объяснимым путём по рёбрам DEPENDS_ON/SIMILAR_TO. Это инновационнее классического векторного поиска: рекомендации становятся проверяемыми (путь в графе — это доказательство).

3. **daten5 + info40 (AI Agent Orchestration Platform) = агенты, исполняющие blueprints.**
   Blueprint-engine умеет исполнять декларативные шаги (api_call/validate/wait), но настоящие интеграции требуют адаптивности. Если шаги blueprint'ов исполнять агентами оркестратора info40 (агент сам разбирается с формой API, ошибками, ретраями), получится «self-healing макрос уровня интернета» — практическая реализация главного обещания манифеста, недостижимая для жёстких Zapier-подобных сценариев.

4. **daten5 + info2 (Тезаурус-Хаб программного кода) = единая онтология capabilities.**
   Таблица capabilities в daten5 сейчас пуста и без источника таксономии. Тезаурус кода из info2 может стать её словарём: категории, синонимы, иерархия parent_id. Двусторонняя выгода: info2 получает живое применение и данные краулера, daten5 — контролируемый словарь вместо свободных LLM-тегов.
