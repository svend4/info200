# Вопросы к info150

## 1. Почему три новых сиблинга (coast, desk, stroll) не включены в CI-матрицу, а их README/STATUS остались копиями чужих доменов?

Это единственное место, где проект нарушает собственный стандарт («broken demo fails CI, not silently rots»).

**Варианты ответов:**
- А. Недосмотр в спешке спринта начала мая — забыли обновить qa.yml и переписать README после copy-форка.
- Б. Сознательно: новые сиблинги — черновики-эксперименты, их «официальное» включение в каталог (docs/adaptations 15–17, CI) планировалось следующим шагом, который не состоялся из-за паузы.
- В. Они создавались как временные пробы и, возможно, будут удалены/слиты с crowd и fit.

**Варианты дальнейших действий:**
- При А: механическая правка — 3 строки в матрице qa.yml + переписать 3 документа; добавить корневой линтер целостности монорепо (см. recommendations.md), чтобы класс ошибки не повторялся.
- При Б: завести в корне TODO/ROADMAP монорепо с чек-листом «что делает сиблинга официальным», провести coast/desk/stroll по нему.
- При В: удалить или пометить каталоги как experimental в корневом README, чтобы дерево не противоречило документации.

## 2. Каков реальный статус проекта после паузы с 4 мая 2026 — это завершённый спринт или остановка?

181 коммит за апрель–май, затем два месяца тишины. От ответа зависит, что делать со всем остальным.

**Варианты ответов:**
- А. Пауза временная, работа продолжится (например, Phase 10/11 из ROADMAP).
- Б. Проект достиг задуманной консолидированной точки и заморожен намеренно.
- В. Фокус ушёл в другой репозиторий профиля (например, идеи продолжаются в info40/nautilus).

**Варианты дальнейших действий:**
- При А: начать с быстрых улучшений из recommendations.md и первого mutation-baseline — дешёвые победы для разгона.
- При Б: закрыть репозиторий «начисто»: LICENSE, CI для всех пакетов, дрейф документации, тег v0.1.0 — и явная пометка «research archive, см. STATUS.md».
- При В: перенести переиспользуемое (portal-протокол, biocore, score_fusion) в активный репозиторий, а в info150 оставить указатели.

## 3. Планируется ли валидация на реальных данных (PhysioNet, реальное видео), или проект сознательно остаётся simulation-first?

STATUS.md называет отсутствие реальных данных «единственным самым большим разрывом между Alpha и убедительной Beta» (RISK CAL-001).

**Варианты ответов:**
- А. Да, PhysioNet-ингест — следующий этап; нужны только время/ресурсы.
- Б. Нет: без клинического партнёра и IRB реальные данные не имеют смысла, стек остаётся симуляционным до появления партнёра.
- В. Реальные данные появятся не у флагмана, а у «неклинического» сиблинга (farm/fish/fit), где нет регуляторных барьеров.

**Варианты дальнейших действий:**
- При А: выбрать конкретный открытый датасет, прогнать через готовый адаптер, обновить CALIBRATION.md результатами — это сразу поднимает достоверность всех цифр бенчмарка.
- При Б: усилить грантовую упаковку (ONE_PAGER + STATUS) и искать партнёра; в README честно вынести «simulation-first» в первый абзац.
- При В: сфокусировать сценарий «продукт из сиблинга» (recommendations, вариант 2): реальное видео + MediaPipe в fit/desk дешевле всего.

## 4. Какова стратегия по 17 Web UI — их реально сопровождать?

Каждый сиблинг получил React/Vite/TS-фронт; это ~18 отдельных фронтендов на одного мейнтейнера, и коммиты последних дней спринта — как раз UI-фиксы (темы, цвета в coast).

**Варианты ответов:**
- А. UI генерируются по шаблону, сопровождение дёшево — правки тиражируются скриптом/агентом.
- Б. UI — витрины для демонстраций, сопровождать их всерьёз не планируется.
- В. Останутся только UI флагмана и 1–2 пилотов, остальные будут удалены.

**Варианты дальнейших действий:**
- При А: оформить шаблон как явный инструмент (каталог-эталон + скрипт раскатки), задокументировать в CONTRIBUTING.
- При Б: пометить в DEMOS.md статус «demo-grade UI», исключить UI из ожиданий qa.
- При В: провести чистку и сократить поверхность — заодно уменьшится и TypeScript-доля поддержки.

## 5. Считать ли монорепо конечной формой, или сиблинги будут выделяться в отдельные репозитории?

DEMOS.md прямо говорит, что каждый сиблинг «intended to spin out into its own repository», но ни один пока не выделен.

**Варианты ответов:**
- А. Spin-out планируется для зрелых сиблингов (кандидаты — rescue с multiuser или fish с multi-modal пайплайном).
- Б. Монорепо — постоянная форма: единый CI и перекрёстные документы ценнее автономии.
- В. Решение отложено до появления внешнего интереса к конкретному домену.

**Варианты дальнейших действий:**
- При А: определить чек-лист выпуска (свой зелёный CI, собственный README/адаптационный док, LICENSE) и выделить первый пилот; в info150 оставить указатель.
- При Б: убрать обещание spin-out из DEMOS.md и вместо этого закрепить правила монорепо в корневом CONTRIBUTING.
- При В: ничего не делать, но зафиксировать критерий «когда выделяем» письменно.
