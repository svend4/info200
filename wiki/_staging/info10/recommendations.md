## Серьёзные доработки

- **Сделать pro-шлюз действительно OpenAI-совместимым**: вернуть схему chat.completion (как в medium-варианте), поддержать стриминг и настоящий tool calling (`search`, `download`, `git_write` как tools) — тогда любой OpenAI-клиент подключится без адаптеров.
- **Безопасная запись в GitHub**: заменить subprocess-git на GitHub REST API (Contents API) с точечными правами токена, whitelist путей, ветка-песочница + PR вместо прямого push в main.
- **Реальная MCP-интеграция**: заявленная «активация 13 MCP-серверов» — оформить шлюз как MCP-сервер (tools: search/download/write), чтобы Claude и другие клиенты подключались нативно; сейчас это самое большое расхождение слова и дела.
- **Тесты и CI**: pytest с TestClient FastAPI (health, ask с замоканным `docstoolkit.rag.ask`, отказ git_write без токена, отказ path traversal), GitHub Actions на push.
- **Данные**: определить, откуда контейнер берёт корпус lorenzo (git clone при старте / volume / submodule) — сейчас `/api/download` и RAG указывают на пустой `/app`.
- Общий модуль для трёх вариантов шлюза вместо трёх независимых скриптов; конфигурация через pydantic-settings.

## Варианты продолжения (минимум 3 сценария)

**Сценарий 1 — «Довести до работающего сервиса над lorenzo».**
Цель прежняя: живой шлюз к корпусу lorenzo. Шаги: вендорить/подключить docstoolkit, при старте контейнера клонировать lorenzo в volume, включить API-ключ, закрыть traversal, задеплоить на Render.com по уже написанной инструкции, добавить смоук-тест. Результат: реальный публичный RAG-эндпоинт для 2815 md-файлов Svyazi 2.0 — то, что документация уже обещает. Это самый короткий путь превратить «полностью готово» из декларации в факт.

**Сценарий 2 — «Влить в lorenzo и закрыть info10».**
daf-gateway по смыслу — модуль docs-toolkit (он его и импортирует). Перенести папку в lorenzo (`lorenzo/daf-gateway/` или `docs-toolkit/gateway/`), где зависимость разрешается локально, а корпус лежит рядом; info10 заархивировать с указателем. Плюс: исчезает проблема расщеплённой зависимости и лишний репозиторий в профиле из 61; минус: lorenzo ещё больше разрастается.

**Сценарий 3 — «Обобщить в универсальный DAF для любого репозитория».**
Убрать привязку к lorenzo: шлюз получает `REPO_URL` в конфиге, при старте индексирует любой md-корпус (или использует infom/ГрафРАГ как движок) и даёт стандартный набор инструментов: search / download / git_write / health. Тогда DAF становится продуктом: «поставь контейнер — получи API к своему репозиторию знаний». Это оправдало бы имя Dynamic Activation Fabric и пригодилось бы для info150, data70, soz150 и других info-репозиториев профиля.

**Сценарий 4 — «Заморозить как артефакт сессии».**
Честно пометить в README: «прототип из чат-сессии Grok, не запускается без docstoolkit», исправить только статус в документации и заархивировать. Минимальные усилия, устраняется дезинформация — приемлемо, если развитие ушло в nautilus/info40.

## Сочетания с другими репозиториями профиля (минимум 2 идеи)

1. **info10 + lorenzo = живой корпус Svyazi 2.0.** lorenzo даёт docstoolkit (RAG) и ~2815 md-документов, info10 — HTTP/Docker-обёртку с записью в GitHub. Вместе: самообновляющаяся база знаний, которую любая нейросеть читает через `/v1/chat/completions` и пополняет через `/api/git/write` — «википедия с API для агентов». Это прямое завершение исходного замысла, инновация — двусторонний (чтение+запись) доступ моделей к корпусу.

2. **info10 + infom (ГрафРАГ) = граф-шлюз знаний.** Заменить в шлюзе `docstoolkit.rag.ask` на граф-RAG из infom: ответы приходят не как плоский топ-k, а с путями по графу сущностей. Получится редкий продукт — OpenAI-совместимый эндпоинт над GraphRAG для произвольного md-корпуса, где `/api/download` отдаёт ещё и подграф контекста.

3. **info10 + universal-file-storage-mcp = двухпротокольный доступ к файлам.** У universal-file-storage-mcp уже есть MCP-сервер файлового хранилища; DAF добавляет HTTP/REST-фасад и git-запись. Объединение даёт один сервис с двумя интерфейсами (MCP для Claude, REST для остальных моделей) — и заявленная в доках info10 «активация MCP» наконец станет правдой.

4. **info10 + info40 (AI Agent Orchestration Platform) + daten8 (мониторинг объявлений) = агентный конвейер с памятью.** info40 оркестрирует агентов, daten8 собирает данные из интернета, DAF-шлюз служит общей «внешней памятью»: агенты пишут находки через `/api/git/write` в версионируемый корпус и ищут по нему через RAG. Инновация: журнал работы мультиагентной системы как git-история, доступная для аудита и отката.
