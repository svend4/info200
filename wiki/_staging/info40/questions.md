# Вопросы к info40

## 1. Каков реальный статус проекта: это витрина-концепт или заготовка продукта, который планируется доводить?

README называет платформу «production-ready», но всё хранение — in-memory, auth — заглушка, агенты имитируют работу. От ответа зависит вся стратегия работы с репозиторием.

**Варианты ответов:**
- А. Это осознанная витрина/учебный образец, доводить не планирую.
- Б. Это заготовка: планирую довести до работающего MVP.
- В. Проект заморожен, решение не принято.

**Варианты дальнейших действий:**
- При А: выполнить «быстрые улучшения» из recommendations.md (честный README, дисклеймеры в use-cases, исправление цифр), пометить как concept/showcase в хабе info200 — и больше не вкладываться.
- При Б: начать со сквозного happy path (Registry на PostgreSQL + один реальный агент + очередь), отложив marketplace; починить CI и тесты до начала новой функциональности.
- При В: минимальный порядок (пункты 1–2 быстрых улучшений) и статус «архив», чтобы аудиторская вики не расходилась с README.

## 2. Почему заявленные метрики (40 000+ строк, 15 000 строк концепт-дока, ~1 400 строк schema.sql) в разы превышают фактические (~26 600, 1 040, 576)?

Это ключевая находка перепроверки: PROJECT_SUMMARY и README описывают несуществующие объёмы и структуру каталогов.

**Варианты ответов:**
- А. Цифры сгенерированы ИИ вместе с проектом и не проверялись.
- Б. Часть материалов существовала локально и не была закоммичена (например, полный AI_AGENT_ORCHESTRATION.md, values-production.yaml).
- В. Цифры считались иначе (символы, включая сгенерированные файлы и т.п.).

**Варианты дальнейших действий:**
- При А: ввести правило — статистику в README генерировать скриптом (`cloc`/`wc`) и обновлять в CI; исправить текущие цифры.
- При Б: докоммитить недостающее (в первую очередь values-production.yaml, полную версию концепт-дока) — тогда вики нужно будет обновить.
- При В: указать методику подсчёта прямо в PROJECT_SUMMARY, чтобы будущие аудиты не фиксировали расхождение.

## 3. Должны ли сервисы работать с реальными PostgreSQL/Redis/RabbitMQ, и в каком порядке их подключать?

Схема на 9 таблиц и вся инфраструктура готовы, но код с ними не связан — это самый большой разрыв между заявленным и фактическим.

**Варианты ответов:**
- А. Да, начать с PostgreSQL в Registry Service (минимальный шаг).
- Б. Да, но сразу весь контур: БД + очередь + воркеры (полный E2E).
- В. Нет, in-memory достаточно — репозиторий демонстрационный.

**Варианты дальнейших действий:**
- При А: добавить слой asyncpg/SQLAlchemy в registry_service, поднять PG из docker-compose, переписать unit-тесты на testcontainers; остальные сервисы — по мере надобности.
- При Б: спланировать 3–4 итерации (БД → RabbitMQ → воркер с реальным LLM → агрегация результатов), фиксируя каждую зелёным CI.
- При В: явно пометить в README «in-memory by design» и удалить из документации утверждения о подключённой БД.
