# Вопросы к daten5

## 1. Запускалась ли платформа хотя бы один раз целиком (`docker-compose up`)?

В docker-compose.yml дублируется ключ `api-gateway` и монтируются несуществующие конфиги Prometheus/Grafana — это признаки того, что компоуз в текущем виде не поднимался.

**Варианты ответов:**
- А. Да, поднималась частично (отдельные сервисы).
- Б. Нет, код сгенерирован и не запускался.
- В. Запускалась старая версия до коммита «Phases 2-4».

**Варианты дальнейших действий:**
- При А: зафиксировать в README, какие сервисы проверены; починить компоуз для остальных (см. быстрые улучшения 1).
- При Б: первым шагом сделать smoke-запуск ядра (postgres + catalog-api + crawler), остальное временно закомментировать; только потом развивать функциональность.
- При В: восстановить работавшую конфигурацию из истории коммитов и оформить её как «минимальный профиль» compose.

## 2. Какова роль daten5 относительно daten12 («Info рационал инфо программ» — описание совпадает дословно) и data30 («info ос рационал программ»)?

В профиле минимум три репозитория с «рационал»-тематикой; непонятно, где каноническая версия концепции.

**Варианты ответов:**
- А. daten5 — основной, остальные — черновики/копии.
- Б. Разные грани: daten5 — платформа, daten12/data30 — документы/ОС-направление.
- В. Исторические дубли, судьба не решена.

**Варианты дальнейших действий:**
- При А: пометить daten12/data30 как архивные с ссылкой на daten5; манифест держать в одном месте.
- При Б: прописать разграничение в README всех трёх репо и в хабе info200, добавить перекрёстные ссылки.
- При В: провести сверку содержимого (аудит-страницы соседних агентов роя), слить лучшее в один репозиторий, остальные архивировать.

## 3. Что было целью PR #1 «fix-api-data-refresh», который на деле принёс всю платформу (+10 582 строки)?

Название ветки говорит о фиксе обновления данных API, содержимое — полная реализация фаз 1–4.

**Варианты ответов:**
- А. Автоназвание ветки Claude Code, смысловой нагрузки нет.
- Б. Изначально задумывался фикс, но сессия переросла в полную генерацию.
- В. Название осознанное: «refresh» = наполнение каталога данными.

**Варианты дальнейших действий:**
- При А/Б: в будущем разбивать такие сессии на тематические PR — это единственный репозиторий-механизм самоаудита; при следующем спринте описывать в PR, что реально проверено.
- При В: тогда механизм «data refresh» (периодический прогон краулера) стоит доделать явно: cron/scheduler для github-crawler уже напрашивается (node-cron в зависимостях blueprint-engine есть, но не используется).

## 4. Концепция предполагает каталог «всего интернета» — есть ли намерение сузить домен до обозримого (например, до собственных 61 репозиториев или одной экосистемы вроде WordPress/MCP)?

Roadmap манифеста (100 000+ приложений к Q4 2026) при 5 коммитах и нуле данных нереалистичен.

**Варианты ответов:**
- А. Да, сузить до профиля svend4 / одной экосистемы.
- Б. Нет, цель принципиально глобальная, это долгосрочная ставка.
- В. Проект был экспериментом «что сгенерирует Claude по манифесту», продолжение не планировалось.

**Варианты дальнейших действий:**
- При А: сценарий «Каталог-для-профиля» из рекомендаций — 1–2 спринта до работающего демо.
- При Б: скорректировать roadmap на реальные даты, начать с ниши (top-1000 npm) и искать соратников/финансирование — в одиночку объём неподъёмный.
- При В: зафиксировать выводы эксперимента в README (что получилось/нет), репозиторий пометить как experimental и хранить как референс.

## 5. Нужны ли в стеке Elasticsearch и RabbitMQ, которые подняты в compose, но кодом фактически не используются?

Поиск работает на PostgreSQL ILIKE (плюс pgvector для семантики), очереди — на Bull/Redis; ES и RabbitMQ лишь потребляют ресурсы и усложняют запуск.

**Варианты ответов:**
- А. Убрать оба, упростить стек.
- Б. Оставить ES (планируется полнотекст), убрать RabbitMQ.
- В. Оставить оба — задел на масштаб.

**Варианты дальнейших действий:**
- При А: удалить из compose и db/init.js, поиск задокументировать как PG-only; это сократит время старта и память вдвое.
- При Б: реализовать индексацию приложений в ES в момент upsert краулера и перевести /api/search на ES; RabbitMQ удалить (Bull уже покрывает).
- При В: тогда написать интеграционный код (публикация задач краулера в RabbitMQ, консьюмер в ai-classifier) — иначе «задел» останется мёртвым грузом.

## 6. Каков источник таксономии capabilities — LLM-теги или контролируемый словарь?

Таблица capabilities с иерархией parent_id есть, но пуста; ai-classifier генерирует capabilities свободным текстом GPT — без словаря каталог быстро засорится синонимами.

**Варианты ответов:**
- А. Планировался контролируемый словарь (вручную/из внешней таксономии).
- Б. Свободные LLM-теги с последующей кластеризацией по эмбеддингам.
- В. Не продумано.

**Варианты дальнейших действий:**
- При А: завести seed-словарь из 50–100 категорий (можно опереться на тезаурус info2), в ai-classifier заменить свободную генерацию на выбор из словаря.
- При Б: добавить джоб дедупликации capabilities по косинусной близости эмбеддингов и слияния синонимов; поле confidence в application_capabilities уже готово под это.
- При В: начать с варианта А как более дешёвого; словарь — это и есть «рационализация» в миниатюре.
