# Вопросы к daten14

## 1. Планируется ли реализация, или BIOS-I задуман как чистый концепт-документ?

С 3 января 2026 в репозитории нет активности; дорожная карта (`docs/08-roadmap/`) расписана до Фазы 5, но даже Фаза 0 (WordPress-краулер + MVP каталога) не начата.

**Варианты ответов:**
- А. Да, реализация планируется, руки не дошли.
- Б. Нет, это осознанный концепт/манифест — реализация не предполагалась.
- В. Реализация ожидается не здесь, а через ИИ-агентов / в другом репозитории.

**Варианты дальнейших действий:**
- При А: начать с урезанной Фазы 0 (краулер одной экосистемы + SQLite + простой поиск), перенести milestone M0.x в GitHub Issues; зафиксировать дедлайн go/no-go, который сама дорожная карта предусматривает.
- При Б: пометить репозиторий как «design study / concept», довести документ до публикуемого вида (сценарий C из рекомендаций) и закрыть вопрос реализации явно.
- При В: переупаковать YAML-спецификации макросов и кластеров как машиночитаемый корпус для агентов (сценарий B), связать с info40.

**Варианты дальнейших действий:**

- При Б: допушить недостающее и проверить, нет ли других расхождений между локальной и опубликованной версией.
- При В: удалить упоминание из README, чтобы описание соответствовало реальности.

## 4. Какая экосистема — точка входа, и почему именно она?

Дорожная карта выбирает WordPress («начинаем с малого, доказываем ценность»), но диагностика в `docs/02-diagnostics/` показывает, что у Make.com выше баллы по интеграции и стандартизации, то есть там идея кластеров ближе к реализуемости.

**Варианты ответов:**
- А. WordPress — самая большая и болезненная экосистема, эффект заметнее.
- Б. Make.com/Zapier — там уже есть коннекторы, остаётся слой кластеров и макросов.
- В. npm/GitHub — ближе к разработчикам, проще собрать данные через открытые API.

**Варианты дальнейших действий:**
- При А: реализовать WordPress-краулер по готовой спецификации из `docs/03-architecture/` (открытый API, без скрейпинга) и собрать первые 10 000 плагинов.
- При Б: строить не краулер, а библиотеку «кластеров» поверх готовых коннекторов Make.com — это тестирует главную гипотезу (ценность проверенных комбинаций) без инфраструктуры.
- При В: начать с npm (registry API + deps уже структурированы) — граф зависимостей почти бесплатен, останется слой «совместимости/качества».

## 5. Откуда возьмутся данные для графа совместимости — самой уникальной части концепции?

Каталог и метрики можно собрать краулером, но факты «X конфликтует с Y» нигде в API не лежат. В документации предложены производные источники (анализ отзывов, co-installation), но методика не проверена.

**Варианты ответов:**
- А. Извлечение из отзывов/форумов с помощью LLM.
- Б. Ручная разметка небольшого ядра экспертами (top-100 компонентов).
- В. Телеметрия/краудсорсинг от пользователей будущей системы.
- Г. Пока нет ответа — это открытый риск.

**Варианты дальнейших действий:**
- При А: сделать пилот — прогнать отзывы 50 популярных WordPress-плагинов через LLM-извлечение пар «конфликт/совместимость» и оценить точность вручную.
- При Б: разметить ядро вручную и опубликовать как открытый датасет — само по себе ценный артефакт, даже без платформы.
- При В: отложить граф до появления пользователей; начать с каталога и метрик здоровья.
- При Г: честно пометить граф совместимости в документации как research question и вынести в отдельный раздел рисков.
