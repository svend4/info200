# Вопросы к info2

## 1. Запускался ли прототип хоть раз целиком (docker-compose up + npm test)?

В репозитории нет lock-файлов, поле `main` в package.json указывает на несуществующий файл, а CI требует отсутствующий package-lock.json — признаки того, что код никогда не исполнялся.

**Варианты ответов:**
- А. Нет, это одно-проходная генерация без запуска.
- Б. Запускались отдельные части (например, ядро дедупликации), но не весь стек.
- В. Запускалось локально целиком, просто артефакты (lock-файлы) не закоммичены.

**Варианты дальнейших действий:**
- При А: начать со «смоук-запуска» — docker-compose, миграции, тесты; составить список реальных ошибок и чинить их по одной (см. «Серьёзные доработки» в recommendations.md).
- При Б: зафиксировать в README, какие части проверены, а какие нет; добить непроверенные или вырезать их.
- При В: закоммитить lock-файлы, включить CI, добавить badge — тогда заявление «работает» станет проверяемым.

## 2. Какова реальная цель проекта: продукт, исследование или упражнение?

Документация написана как инвесторский питч ($1M ARR, тарифы, маркетплейс), но контакты и организация thub-io — вымышленные.

**Варианты ответов:**
- А. Серьёзная продуктовая амбиция, питч писался «на вырост».
- Б. Исследование идеи content-addressed кода; бизнес-часть — антураж.
- В. Упражнение/демонстрация возможностей AI-генерации проекта.

**Варианты дальнейших действий:**
- При А: убрать фикцию, определить нишу против существующих решений (npm workspaces, Nix, unpkg, Bit.dev, jsDelivr) и написать честный анализ конкурентов — его в 06-ROADMAP.md нет.
- При Б: развивать сценарий 3 из рекомендаций (бенчмарк дублирования на реальном корпусе) и почистить документацию от бизнес-слоя.
- При В: пометить статус в README («AI-generated concept study»), заархивировать — и перенести ценные идеи в вики info200.

## 3. Почему семантическая дедупликация заявлена как «AST analysis», а реализована как Jaccard по токенам?

`core/deduplication.js:calculateSimilarity` — это разбиение по пробелам и пересечение множеств; PROJECT-SUMMARY.md при этом упоминает AST.

**Варианты ответов:**
- А. Jaccard — сознательная временная заглушка, AST планировался позже.
- Б. Разница не осознавалась; «semantic match» казался достаточным.
- В. AST-вариант считается ненужным для MVP.

**Варианты дальнейших действий:**
- При А: реализовать AST-нормализацию (например, на базе наработок meta10 / ast-grep) — это самое ценное возможное усиление ядра.
- При Б: провести тест на ложные срабатывания (два разных шаблонных Express-роута дадут высокий Jaccard) и решить, приемлемо ли это.
- При В: тогда убрать слова «AST analysis» из документации и честно описать ограничения метода.

## 4. Проверялся ли центральный тезис «80–90% кода приложений дублируется» на каких-либо данных?

Цифра повторяется во всех документах (README, 02-COMMON-FUNCTIONS.md, PROJECT-SUMMARY.md), но источника или замера нет.

**Варианты ответов:**
- А. Это экспертная оценка/интуиция, замеров не было.
- Б. Есть внешние источники (исследования code clone detection), просто не процитированы.
- В. Планировался собственный замер, не дошли руки.

**Варианты дальнейших действий:**
- При А или В: использовать сам прототип для замера — прогнать дедупликатор по 61 репозиторию профиля svend4 или по выборке npm-пакетов; полученная реальная цифра станет главным активом проекта.
- При Б: добавить раздел «Источники» со ссылками (работы по клон-детекции: Roy & Cordy и др.) — документация сразу станет цитируемой.

## 5. Как info2 соотносится с соседними «реестровыми» проектами профиля — info1 (шаблоны, алгоритмы), info4 (база скиллов), daten40/IFOS (блоки)?

В профиле несколько проектов строят «реестр переиспользуемых единиц» (шаблонов, скиллов, блоков) — T-Hub концептуально их обобщает.

**Варианты ответов:**
- А. Это независимые эксперименты, связи не задумывались.
- Б. T-Hub задумывался как обобщающая платформа для них.
- В. Планируется консолидация, но не решено, вокруг какого репо.

**Варианты дальнейших действий:**
- При А: хотя бы задокументировать в вики info200 сопоставление подходов, чтобы новые проекты не изобретали реестр заново.
- При Б: сделать info2 ядром — определить общий формат «компонента» (код/шаблон/скилл/блок) и мигрировать содержимое остальных реестров в единую схему БД T-Hub.
- При В: провести сравнительный аудит трёх реестров по зрелости и выбрать носителя; остальные пометить как источники контента.

## 6. Нужен ли фронтенд, и если да — почему он остановлен на одной странице?

`frontend/` содержит одну страницу, 3 компонента и 1 хук при заявленном полном стеке (Next.js, MUI, recharts, zustand, swr и react-query одновременно).

**Варианты ответов:**
- А. Фронтенд нужен, просто генерация оборвалась на скелете.
- Б. Фронтенд был «для полноты картины», реальный интерфейс — CLI.
- В. Ещё не решено.

**Варианты дальнейших действий:**
- При А: достроить 3–4 ключевые страницы (карточка компонента, публикация, поиск дублей) и убрать дублирующие библиотеки данных (оставить одну из swr/react-query).
- При Б: удалить frontend/ или перенести в отдельную ветку — это уменьшит поверхность поддержки и сделает заявления README честными.
- При В: отложить решение до первого реального пользователя CLI/API; фронтенд без работающего бэкенда смысла не имеет.
