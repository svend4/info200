# Рекомендации по info150

## Быстрые улучшения

1. **Добавить LICENSE (MIT) в корень репозитория** — сейчас лицензия заявлена только в pyproject и фразой в README; GitHub её не детектирует, а формально монорепо не лицензирован.
2. **Включить `triage4-coast`, `triage4-desk`, `triage4-stroll` в матрицу `qa.yml`** — три пакета живут без CI-гейта, что противоречит собственной политике проекта «broken demo fails CI».
3. **Починить README/STATUS новых сиблингов:** coast/README (сейчас — текст crowd про стадионы), stroll/README (сейчас — фитнес-текст про приседания), desk/README (тоже фитнес-копия) и desk/STATUS («No UI/API» при существующем web_ui/) — дрейф README затрагивает все три новых сиблинга.
4. **Синхронизировать счётчики:** «17 пакетов» в корневом README → фактические ~20; «759 vs 609 тестов» в STATUS.md; убрать упоминание конкретной рабочей ветки из INSTALL.md.
5. **Дописать `docs/adaptations/15–17`** (coast, desk, stroll) — каталог адаптаций должен покрывать все сиблинги, это его смысл.
6. **Обновить описание репозитория на GitHub:** «info med» ничего не говорит; одной строки «triage4 monorepo: stand-off triage decision-support + 17 domain adaptations» достаточно.
7. Прогнать первый полный mutation-run (`make mutation`) и зафиксировать baseline выживаемости мутантов — инфраструктура уже готова, не хватает только запуска.

## Серьёзные доработки

- **Валидация на реальных данных.** Собственный STATUS.md называет это главным разрывом: загрузить хотя бы один архив PhysioNet через готовый адаптер и откалибровать пороги на нём; для сиблингов — хотя бы по одному реальному видео на домен.
- **Реальная перцепция.** `build_ultralytics_detector` существует, но не тестируется в CI; нужен hardware-in-the-loop прогон webcam-пути (Phase 10 Stage 2 демо уже есть — довести до регулярной проверки на реальном кадре).
- **Автоматический контроль дрейфа монорепо.** Скрипт-линтер уровня корня: каждый каталог `triage4-*` обязан присутствовать в qa.yml, иметь непустой README с упоминанием собственного домена (сверка с description из pyproject), STATUS.md и запись в docs/adaptations. Это системно закрывает класс найденных при аудите проблем.
- **Стратегия сопровождения 17 Web UI.** Либо генератор/шаблон (UI-скелет как копируемый пакет с чек-листом обновления), либо честная деградация: UI только у флагмана и 2–3 пилотов.
- **Разделение судьбы сиблингов.** DEMOS.md говорит, что каждый сиблинг «intended to spin out into its own repository» — стоит определить критерии выпуска (свой CI зелёный, README свой, адаптационный док есть) и начать с самого зрелого.
- Выпуск тегов/релизов и, при амбициях, публикация flagship-пакета на PyPI (имя triage4, вероятно, свободно — не проверено).

## Варианты продолжения

**1. Курс на DARPA/грант: флагман как исследовательская заявка.** Сконцентрироваться на triage4: реальные данные (PhysioNet), первый mutation-baseline, полевые прогоны webcam/Tello-демо, оформление ONE_PAGER + STATUS в грантовую заявку или демонстрацию для партнёра с IRB. Сиблинги замораживаются как «каталог потенциала» — они уже сыграли роль доказательства переносимости архитектуры. Это самый честный путь к «Phase 11» из ROADMAP, требующий внешнего партнёра.

**2. Курс на продукт: один сиблинг — в отдельный репозиторий и до пользователей.** Выбрать наименее регуляторно-нагруженный домен с готовой аудиторией (triage4-fit/desk — wellness, или triage4-farm/fish — agtech, где уже есть multi-modal пайплайн и Web UI) и выделить его в самостоятельный репозиторий с реальной перцепцией (MediaPipe/MoveNet), мобильным/веб-клиентом и обратной связью первых пользователей. Монорепо остаётся фабрикой, спин-офф — витриной. Механика spin-out прямо предусмотрена философией проекта.

**3. Курс на платформу: развить portal до межрепозиторного протокола.** Портал сейчас видит 3 пилотов и 6 типов мостов (у референсного nautilus — 33). Довести адаптеры до всех 17 сиблингов, обогатить типологию мостов, добавить постоянное хранилище и дашборд «межсиблинговой обстановки» — получится общая шина ситуационной осведомлённости, а протокол PortalEntry/Bridge можно вынести в отдельный пакет и применять к любым репозиториям профиля (см. сочетания ниже).

**4. Курс на консервацию (минимальный).** Если приоритеты сместились: закрыть быстрые улучшения (лицензия, CI, README-дрейф), пометить репозиторий как research-archive со ссылкой на STATUS.md — проект и в таком виде является сильным портфолио-артефактом.

## Сочетания с другими репозиториями профиля

1. **info150 (portal) + nautilus = универсальный протокол совместимости репозиториев.** nautilus — «мета инфопортал протокол» с 33 типами мостов; portal в info150 — его работающая, протестированная реализация на 6 типах с живыми адаптерами и CI. Слить наработки: вынести PortalEntry/Bridge/discovery в отдельный пакет, принять таксономию мостов nautilus как расширяемый реестр — получится первый в профиле production-качества инструмент «Не слияние — совместимость», применимый к любым источникам отчётов (не только triage-сиблингам). Инновация: межпроектная федерация данных без общей схемы.

2. **info150 + info40 (AI Agent Orchestration Platform) = мультидоменный ситуационный центр на агентах.** 17 движков сиблингов (VenueMonitorEngine, DriverMonitoringEngine, WelfareCheckEngine…) — готовые детерминированные «инструменты» для агентов; info40 даёт оркестрацию. Агент-диспетчер получает потоки из нескольких доменов (пляж + толпа + медпункт на фестивале), запускает соответствующие сиблинги, а portal-мосты (эскалация, географическое соседство) служат правилами маршрутизации внимания агентов. Инновация: оркестрация не LLM-фантазий, а сертифицируемых decision-support пайплайнов с explainable-выходами.

3. **info150 (triage4-rescue) + daten22/data20 (offline-приложения с SQLite FTS) = полевой офлайн-комплект спасателя.** У rescue уже есть CRDT-синхронизация без связи, офлайн-маркеры и multiuser (RBAC + аудит); daten22/data20 дают отработанный паттерн полностью офлайнового приложения с полнотекстовым поиском. Комбинация: планшетный комплект «triage + поиск по протоколам/справочникам без сети», где отчёты о пострадавших и справочная база живут в одном SQLite и сходятся при появлении связи. Инновация: денied-comms система поддержки решений «в одном ящике».

4. **info150 + data7 (задача коммивояжёра, оптимизация) = оптимизация маршрута обхода пострадавших.** `mission_coordination` флагмана назначает платформы (UAV/Spot) на пострадавших; data7 — движок TSP/маршрутной оптимизации. Скрестить: маршрут дообхода N пострадавших с весами из triage-приоритетов и прогнозов ухудшения (ForecastLayer) — «приоритетный коммивояжёр», где стоимость ребра зависит от времени деградации пациента. Инновация: классическая комбинаторика, управляемая медицинской моделью времени.

5. **info150 + meta2/infom/in4n = замыкание круга происхождения.** Флагман уже несёт verbatim-порты из meta2 (24 модуля). Обратный перенос: вынести обкатанные в triage4 версии (score_combiner, DTW/Fréchet-матчинг, conflict resolver) обратно в meta2 как «проверенные боем» релизы, а граф знаний infom подключить к portal как ещё один «сиблинг»-источник записей. Инновация: профиль перестаёт быть набором черновиков — появляется цикл «идея → полевой стек → возврат зрелого кода».
