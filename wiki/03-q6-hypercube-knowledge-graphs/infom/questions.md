# Вопросы к infom

## 1. Планируется ли наконец подключение реального LLM, и какого?

CLAUDE.md называет это «следующим шагом» ещё с марта 2026, все метрики получены на mock/semantic-адаптерах, а `config.py` уже поддерживает 10 провайдеров — но ни одного результата с реальным LLM в репо нет.

**Варианты ответов:**
- А. Да, локальный Ollama (qwen2.5 + bge-m3) — приватность важнее скорости.
- Б. Да, облачный бесплатный тир (Groq/Cohere/Gemini) — быстрее получить результат.
- В. Нет, SemanticAdapter достаточен для текущих задач.
- Г. Проект на паузе, решение отложено.

**Варианты дальнейших действий:**
- При А: прогнать индексацию data70 через Ollama, сравнить Q и число рёбер с semantic-режимом, обновить «ключевые числа» в CLAUDE.md; проверить, что average-pool 1024→6 действительно работает как заявлено.
- При Б: то же, но начать с Groq (chat) + Jina (embed) — конфиг уже готов; добавить учёт rate-limit в indexer.
- При В: тогда приоритет — расширение словаря `semantic_sim.py` и честная фиксация ограничения в README («система работает в пределах словаря ~N понятий»).
- При Г: зафиксировать в README статус «прототип, заморожен», чтобы репозиторий не выглядел заброшенным молча.

## 2. Почему в реальном отчёте по data70 всего 8 рёбер на 46 нод — известна ли причина?

Граф почти без связей — GraphRAG без рёбер вырождается в обычный поиск по эмбеддингам. Это баг парсинга relations, слабость промпта или свойство mock-режима?

**Варианты ответов:**
- А. Известно: mock/semantic-адаптер не умеет извлекать relations, с реальным LLM будет плотнее.
- Б. Известно: JSON-парсер отбрасывает relations при малейшей ошибке формата.
- В. Не исследовалось.

**Варианты дальнейших действий:**
- При А: подтвердить экспериментом на реальном LLM (см. вопрос 1) и записать в отчёт честную сноску.
- При Б: добавить tolerant-парсинг (json-repair), логирование отброшенных relations, метрику edges/nodes в infom_stats.
- При В: добавить в `test_semantic.py` тест «на этом эталонном тексте должно извлечься ≥ K связей» — это самый дешёвый детектор проблемы.

**Варианты ответов:**
- А. Гипотеза, проверка планируется бенчмарками.

- В. Это в первую очередь язык описания/визуализации, а не оптимизация.

**Варианты дальнейших действий:**
- При А: собрать бенчмарк на базе `search/benchmark.py`: recall@k и латентность Q6-LSH vs полный перебор при 100/1k/10k нод; опубликовать таблицу.
- При Б: формализовать наблюдения — хотя бы на демо-данных `main.py` зафиксировать, какие выводы дают тангрэм/фрактал, которых не даёт modularity.
- При В: переориентировать доки — продавать геометрию как объяснимость (визуальные сигнатуры сообществ), убрать перформанс-обещания из CLAUDE.md.
