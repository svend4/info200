## Серьёзные доработки (недели)

1. **Один честный масштабный бенчмарк.** Самоаудит сам называет главный разрыв: всё измерено при d=128, 800 шагов, <100 K токенов. Один прогон YiJingGPT vs VanillaGPT на WikiText-103 (хотя бы d=256–384, 20–50 M токенов, равный бюджет FLOPs) либо подтвердит идею, либо закроет вопрос. Это важнее любых новых архитектур v70+.
2. **Проверить заявление «LCI → π».** Это самое сильное и самое рискованное утверждение проекта. Нужен отдельный документ с формальным определением LCI, нулевой гипотезой (не является ли π артефактом нормировки) и абляциями. Если подтвердится — это ядро будущей статьи.
3. **Прополка корня**: 24 скрипта → подпапки `training_scripts/`, `agents/`; 45+ JSON-логов → `logs/` или артефакты CI. Убрать дубли между `yijing_transformer/scripts/` и корнем.
4. **Оформить paper_draft.md в препринт** (arXiv). Материала — эволюция v53–v69, честные абляции, воспроизводимость R²>0.998 — уже больше, чем во многих workshop-статьях. Внешняя критика даст то, чего проекту не хватает: независимую валидацию.
5. **Опубликовать пакет на PyPI** (после LICENSE и CI): `pip install yijing-transformer` резко снижает порог для внешних экспериментов.
6. **Довести interlingua_fixed до «production»**: баг общего trit_proj исправлен и PROVEN (PPL 1.17), но фикс, по самоаудиту, не активирован в основных моделях (флаг `interlingua_use_fixed`). Включить по умолчанию и перегнать бенчмарки v60–v61.

## Варианты продолжения

**Сценарий A — «Научная валидация» (исследовательский путь).**
Заморозить добавление новых архитектур (их уже 11 классов моделей) и потратить 4–6 недель на верификацию трёх ключевых заявлений: (1) геометрическое смещение Q6 даёт выигрыш при равном бюджете параметров/FLOPs на реальном корпусе; (2) факторизация 8×8 действительно ускоряет на 3.75× на реальном железе (микробенчмарк); (3) LCI→π не артефакт. Результат — препринт + чистый reproducibility-репозиторий. Это превращает pro2 из «личной лаборатории» в цитируемый артефакт, и это единственный сценарий, при котором тысячи часов работы получают внешнюю ценность.

**Сценарий B — «Инженерный продукт: малые интерпретируемые модели».**
Ниша pro2 — не конкуренция с GPT, а **крошечные (1–3 M параметров) интерпретируемые модели** для офлайн-устройств: маршрутизация объяснима (токен «указывает» на ось куба Касаткина), домены читаемы, чекпоинты по 19 МБ. Упаковать NautilusMoME как «микро-LLM для локальных знаний»: обучение на корпусе пользователя одной командой, инференс на CPU, экспорт в ONNX (уже реализован). Целевая аудитория — офлайн-приложения самого профиля svend4 (daten22, data20).

**Сценарий C — «Семантическое ядро экосистемы svend4».**
Развивать линию, которая уже начата в nautilus/ и corpus_loader.py: pro2 становится общим эмбеддинг-слоем профиля. Q6-эмбеддинги (`e2_inference.py --embed/--similar/--map`) дают каждому документу из 61 репозитория адрес в 64-ячеечной карте гиперкуба, поиск похожего — по Хэммингу. Портал nautilus уже умеет читать info1/meta/data2/data7 — довести адаптеры до всех ключевых репо и отдать API хабу info200. Это самый синергичный сценарий для профиля, даже если научная ценность Q6 не подтвердится: как «дешёвый локальный семантический индекс» система полезна независимо от этого.

**Сценарий D — «Архивация с достоинством» (если приоритеты сместились).**
Если продолжения не будет: добавить LICENSE, склеить README, вынести чекпоинты в один Release «v0.50.0 final», в шапке честно указать «исследование заморожено, результаты — в REPORT-v60-v61-status.md». Проект и так задокументирован лучше 95 % исследовательского кода — зафиксировать это состояние дёшево.

## Сочетания с другими репозиториями профиля

1. **pro2 + lorenzo (docs Svyazi 2.0, ~2815 md-файлов) = семантическая карта корпуса знаний.** Прогнать весь md-корпус lorenzo через `e2_inference.py --embed` и Q6-квантизацию: каждый документ получает гексаграмму-адрес (одну из 64 ячеек) и 6-доменный профиль (CODE/RECON/SYSTEM/MATH/HUMAN/INFO). Получится инновационная вещь: **дискретная навигационная карта огромного корпуса**, где «похожие документы» = соседние вершины гиперкуба (Хэмминг ≤ 1), а docs-toolkit из lorenzo рендерит карту. Ни один обычный поиск такого представления не даёт; это одновременно и реальный (не синтетический!) бенчмарк для Q6-эмбеддингов.

2. **pro2 + infom (ГрафРАГ) = ГрафРАГ с дискретным геометрическим индексом.** Классический GraphRAG строит граф сущностей с дорогими эмбеддингами; pro2 предлагает готовый дешёвый дискретный индекс: узлы графа квантуются в 64 архетипа, рёбра типизируются по графу Бян-Гуа (переход = флип бита = «минимальная смысловая мутация»). Retrieval становится walk'ом по гиперкубу вместо ANN-поиска — работает офлайн на CPU, объясним («документ найден, потому что отличается одной линией гексаграммы»). Уникальный гибрид символьного и векторного поиска.

3. **pro2 + info40 (AI Agent Orchestration Platform) = геометрическая маршрутизация агентов.** В pro2 уже есть мультиагентные тренировочные схемы (nautilus_4agent, nautilus_15agent, multi_salesman) и KasatkinQ6Router с объяснимым выбором из 6 доменов. Перенести этот роутер в оркестратор info40: входящая задача проецируется в Q6, каждая ось = тип агента (код/анализ/система/математика/человек/инфо), маршрутизация объяснима и не требует LLM-вызова. Получится редкая вещь — **детерминированный, интерпретируемый и бесплатный диспетчер агентов**.

4. **pro2 + daten22/data20 (офлайн-приложения с SQLite FTS) = офлайн-поиск с семантикой без сервера.** FTS4 ищет по словам; добавить колонку с 6-битной гексаграммой документа (одно число 0–63 от NautilusMoME, инференс на CPU, модель 19 МБ) — и офлайн-приложение получает «семантические соседи» через простой SQL (`WHERE hamming(hex, ?) <= 1` через таблицу предвычисленных соседей). Семантический поиск в приложении без эмбеддинг-базы, без сети и почти без места.
