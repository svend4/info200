# Вопросы к nautilus

## 1. Почему остановился еженедельный sync-бот после 2026-04-27 — это сознательная пауза или GitHub автоматически отключил cron-воркфлоу?

Последний коммит — `chore: weekly ecosystem sync 2026-04-27` от `nautilus-sync-bot`; с тех пор ~9 недель тишины, хотя `sync.yml` требует запуск каждый понедельник.

**Варианты ответов:**
- А. GitHub отключил schedule из-за 60 дней неактивности, владелец не заметил.
- Б. Воркфлоу падает (например, на scan_repo.py), и падения игнорируются.
- В. Пауза сознательная: проект «доведён до v1.2», синк не нужен.

**Варианты дальнейших действий:**
- При А: включить воркфлоу в Actions; добавить в конец sync.yml шаг «создать issue при неуспехе» и лёгкий keep-alive (бот сам является активностью, но нужен первый ручной запуск).
- При Б: разобрать логи Actions, починить упавший шаг, добавить `--strict`-режимы и алертинг.
- При В: отключить schedule явно (закомментировать cron), зафиксировать в README «snapshot-режим, данные апреля 2026», чтобы витрина не врала.

## 2. Планируется ли подключение живых данных вместо fallback-слепков?

Собственный health-отчёт показывает: 7 из 14 адаптеров возвращают только вшитые статические записи, реальный консенсус 36 %. Портал работает, но показывает «музейный слепок» экосистемы.

**Варианты ответов:**
- А. Да, план — клонировать репо-источники в sync-боте и запускать адаптеры по живым файлам.
- Б. Да, но через сеть: перевести адаптеры на raw.githubusercontent (как AutoAdapter) либо разложить `nautilus.json`-индексы по репо-источникам.
- В. Нет, fallback — осознанный дизайн: слепки обновляются вручную при больших релизах.

**Варианты дальнейших действий:**
- При А: добавить шаг shallow-clone всех репо реестра в sync.yml, прогонять адаптеры, складывать результат в cache/ и коммитить; цель — health 90+.
- При Б: сделать сетевое чтение общим миксином (кэш уже есть в adapters/cache.py), покрыть тестами offline-путь.
- При В: пометить в README и в `describe()` каждого адаптера дату слепка, добавить в health_check метрику «возраст fallback-данных».

## 3. Под какой лицензией распространяется код?

LICENSE отсутствует (проверено), при этом проект явно рассчитан на внешнее использование: авторегистрация чужих репо, INTEGRATION.md, «подключи свой репозиторий за 5 минут». CC BY 4.0 упомянута только для текста протокола.

**Варианты ответов:**
- А. MIT/Apache-2.0 для кода + CC BY 4.0 для спецификации.
- Б. Пока «all rights reserved» — внешнее использование не приоритет.
- В. Не задумывался.

**Варианты дальнейших действий:**
- При А: добавить LICENSE и LICENSE-docs (или раздел в README), в PORTAL-PROTOCOL.md — ссылку на файл.
- При Б: явно написать это в README, убрать призывы к интеграции или пометить их «по договорённости».
- При В: рекомендация — MIT для кода (максимальная совместимость с целями протокола-стандарта).

## 4. Как назначаются Q6-координаты и мосты — есть ли процедура проверки, или это авторская интуиция?

Q6-метки вшиты таблицей в adapters/pro2.py и проставлены в паспортах вручную; confidence мостов (0.70–0.95) ничем не выводится. При этом вся математика проекта (Хэмминг, соседи, кластеры, gap-анализ, конфликты) стоит на этих координатах.

**Варианты ответов:**
- А. Интуиция автора, и это осознанно: Q6 — символическая онтология (И-Цзин/Вольфрам), а не измеримая величина.
- Б. Есть неформальная методика (в pro2/info1), но она не записана.
- В. Хочу автоматизировать выведение координат.

**Варианты дальнейших действий:**
- При А: задокументировать это ограничение в PORTAL-PROTOCOL.md (раздел Q6) — «координаты декларативны»; конфликт-детектор становится главным механизмом контроля.
- При Б: оформить методику отдельным docs/Q6_ASSIGNMENT.md с примерами, добавить чек в generate_passport.py.
- При В: прототип — классификатор на основе tfidf_search-профилей или LLM с обязательным логом обоснования; сверять с ручными метками, расхождения — во флаги needs_review.

## 5. Какова судьба GitHub Pages (svend4.github.io/nautilus) — это будущая публичная витрина?

В nautilus.json прописан адрес Pages, есть index.html, snapshot.py генерирует docs/ для Pages, но работоспособность страницы в аудите не проверялась.

**Варианты ответов:**
- А. Pages включены и должны показывать живой снапшот.
- Б. Задел на будущее, Pages не настроены.
- В. Витриной должен стать не Pages, а сам портал (--serve) в контейнере.

**Варианты дальнейших действий:**
- При А: проверить публикацию, добавить бейдж-ссылку в README, обновлять через sync-бот.
- При Б: включить Pages из папки docs/ — почти всё уже готово (snapshot.md, ecosystem.mmd, q6_map/graph.html можно копировать в docs/).
- При В: описать деплой (docker compose up) в README c реальным хостом; Pages оставить как статическую копию снапшота.

**Варианты ответов:**
- А. Технический долг спринта v1.2 — планировалось, не успелось.
- Б. Считаю их косвенно покрытыми через test_portal/health_check.
- В. Эти подсистемы экспериментальные, API нестабилен.

**Варианты дальнейших действий:**

- При Б: минимум — smoke-тест каждого эндпоинта и один тест конфликт-детекции, косвенное покрытие тут иллюзорно.
- При В: пометить в openapi.yaml статус beta у нестабильных эндпоинтов и заморозить контракт стабильных, покрыв только их.
