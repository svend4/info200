# nautilus — мета-портал и протокол федерации репозиториев экосистемы svend4

## Обзор

**Nautilus Portal** (v1.2) — самый инженерно зрелый «связующий» проект профиля svend4: единая точка входа в экосистему из ~13 репозиториев знаний. Девиз проекта: **«Не слияние — совместимость»** — как офисный пакет читает `.docx`, `.pdf`, `.xlsx`, не сливая их в один формат, так Nautilus читает все репозитории экосистемы через адаптеры, находит связи между ними и строит общий вид.

Проект написан на Python 3.10+ **без единой внешней зависимости** (только stdlib; опционально `torch` для экспериментального glyph-компонента). Включает: движок портала с 14 адаптерами, REST API на 12 эндпоинтов, формальную спецификацию протокола (PORTAL-PROTOCOL.md, ~1000 строк, в стиле RFC с BCP 14), OpenAPI 3.1, 60 тестов, CI, Docker, Python SDK и автоматический еженедельный sync-бот.

## Назначение и идея

Проблема: у каждого репозитория экосистемы (info1, pro2, meta, data2, data7, infom, daten22, soz150, meta1, info3/4/30/100) — свой формат данных, своя онтология и своя точка зрения на одни и те же концепты. Без портала нужно знать формат каждого репо и искать вручную.

Решение — три кита:

1. **Адаптерный паттерн.** Любой репозиторий реализует два метода (`fetch(query)` / `describe()`) и становится частью единого поискового пространства. Записи приводятся к универсальному `PortalEntry`. Для быстрого подключения достаточно положить `nautilus.json` в корень репо — его подхватит `AutoAdapter` («вариант на 5 минут»).
2. **Q6-пространство.** Каждый концепт получает координату в бинарном гиперкубе {0,1}⁶ (64 вершины). Расстояние Хэмминга = семантическая близость. Вершины сопоставлены 64 гексаграммам И-Цзин и классам клеточных автоматов Вольфрама — это сквозная онтология всей экосистемы svend4.
3. **Bridge-граф и консенсус.** 33 типизированных моста (analogy / derivation / projection / embedding / isomorphism) между репозиториями, описанные в machine-readable паспортах; алгебра мостов v2.0 (`invert`, `compose`, `transitive_closure`, `detect_conflicts`). При запросе портал опрашивает все адаптеры и вычисляет консенсус — в скольких репо концепт подтверждён «реальными» записями.

Поверх этого — система аннотаций (Protocol 3 / «Double-Triangle»): любой участник или агент-адаптер может аннотировать любую запись, конфликты автоматически получают флаг `needs_review`.

## Как устроено (архитектура)

```
info1  pro2  meta  data2  data7  graphrag  daten22  legal  continuum  ai_research
  └──────┴─────┴─────┴─────┴────────┴────────┴──────┴────────┴──────────┘
                                     │
                        ⬡ Nautilus Portal v1.2
                 BaseAdapter · PortalEntry · BridgeRegistry
                                     │
          ┌──────────────────────────┼──────────────────────────┐
   текстовый вывод            REST API / JSON               HTML SPA
   portal.py --query          api.py :8080                  --serve :8000
```

- `portal.py` (668 строк) — оркестратор: регистрирует 14 адаптеров, считает релевантность и консенсус, отдаёт текст/HTML; автоматически подгружает `auto`/`jsonl` адаптеры из реестра `nautilus.json`.
- `api.py` (394) — REST API на чистом `http.server` (12 эндпоинтов + `/metrics` для Prometheus).
- `adapters/` — 22 файла: протокол `base.py` (BaseAdapter + PortalEntry + fuzzy_match), дисковый кэш с TTL 24 ч, адаптеры для конкретных репо и универсальные (AutoAdapter, JSONLAdapter, ObsidianAdapter, ArxivAdapter, GitHubTopicAdapter, ConversationAdapter). Есть `py.typed` — код типизирован, заявлен mypy clean.
- `passports/` — 12 паспортов репозиториев с секциями «Bridges (machine-readable)» (JSON внутри markdown); `bridge_registry.py` парсит их и строит граф мостов.
- `annotations.py` — хранилище аннотаций (SQLite или in-memory).
- Инструменты анализа: `health_check.py` (score 0–100), `validate_links.py` (317 кросс-ссылок), `gap_detection.py` (пробелы Q6-покрытия, BFS), `tfidf_search.py` (семантический поиск, 207 документов), `cluster.py`, `diff_report.py`, `timeline.py`, `snapshot.py`, интерактивные `q6_map.html` и `graph.html` (D3.js).
- Автоматизация: 4 GitHub Actions воркфлоу — CI (pytest + validate_links --strict + health_check), еженедельный `sync.yml` (бот `nautilus-sync-bot` пересканирует репо, обновляет снапшоты и коммитит), `auto_update.yml` (самореистрация чужого репо через `repository_dispatch`), `register_nautilus.yml`.
- Развёртывание: `Dockerfile` + `docker-compose.yml` (сервисы portal, api, health, snapshot), `openapi.yaml`, `nautilus_sdk.py` — Python-клиент.

Подробнее — в [structure.md](structure.md).

## Статус и активность

- **54 коммита**: Initial commit 2026-03-14, основная разработка — интенсивный спринт 19–27 апреля 2026 (v1.1 → v1.2, авторы `claude` и `svend4`), последний коммит — `chore: weekly ecosystem sync 2026-04-27` от бота.
- После 2026-04-27 еженедельный sync-бот **перестал коммитить** (на дату аудита 2026-07-02 прошло ~9 недель) — вероятно, GitHub отключил cron-воркфлоу из-за неактивности репо, либо он падает. Проект в паузе.
- 1 звезда, 0 issues, 0 **открытых** PR — но **16 PR уже смёржено**: разработка v1.1→v1.2 шла через pull-request'ы с ревью (ветки `claude/review-*`, напр. PR #16 от 2026-04-21), ветка `main`. Это плюс к инженерной культуре, а не отсутствие процесса.
- Важный нюанс из собственного отчёта проекта (`health_report.txt`, 2026-04-27): **оценка экосистемы 66/100**, 7 из 14 адаптеров возвращают только **fallback-записи** (статические данные, вшитые в код адаптеров), потому что реальные соседние репозитории не доступны в окружении запуска. Подробнее — в [assessment.md](assessment.md).
