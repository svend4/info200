# daten2 — учебный «магазин цветов» в 7 уровнях сложности (на main остался только уровень 5)

## Обзор

**daten2** — учебный проект «7 flowersshops — 7 level programm»: одно и то же приложение (интернет-магазин цветов с каталогом, корзиной и оформлением заказа) реализуется на семи уровнях технологической сложности — от PHP-файла с SQLite до микросервисов уровня «Enterprise». Однако **текущее содержимое ветки `main` — только уровень 5** (React + Vite на фронтенде, Flask API + SQLite на бэкенде): в ходе экспериментов с деплоем на Render уровни вливались в main по одному, каждый *заменяя* предыдущее содержимое, и последним оказался уровень 5. **Важно: остальные уровни не потеряны.** Каждый из семи уровней сохранён в собственной ветке — `claude/level1-php-GBpVR`, `claude/level2-flask-GBpVR`, `claude/level3-django-GBpVR`, `claude/level4-express-GBpVR`, `claude/level5-react-flask-GBpVR`, `claude/level6-nextjs-GBpVR`, `claude/level7-enterprise-GBpVR`. Более того, консолидированное дерево со всеми семью уровнями в подпапках существует в ветке `claude/flower-shop-seven-levels-GBpVR` (`flower_shop_levels/levels/level1_flower_shop … level7_flower_shop_enterprise`). На `main` уровни просто не собраны в одно дерево — там виден только уровень 5.

Код почти полностью сгенерирован Claude (автор коммитов уровней — `claude`, владелец сливал PR). Проект маленький: на main около 10 файлов и ~300 строк кода.

## Назначение и идея

Идея — «лестница сложности»: показать одну и ту же предметную задачу (магазин цветов) на разных технологических ступенях. По истории коммитов и README веток восстанавливается такая лестница:

1. **Уровень 1** — PHP + SQLite, весь сайт в одном `index.php` (ветка `claude/level1-php-GBpVR`);
2. **Уровень 2** — Flask + SQLite + серверные шаблоны (ветка `claude/level2-flask-GBpVR`);
3. **Уровень 3** — Django + админка (ветка `claude/level3-django-GBpVR`, PR #8);
4. **Уровень 4** — Node.js Express + EJS (ветка `claude/level4-express-GBpVR`, PR #9);
5. **Уровень 5** — React (Vite) + Flask API + SQLite — **текущий main** (ветка `claude/level5-react-flask-GBpVR`, PR #10);
6. **Уровень 6** — Next.js (App Router) + TypeScript + PostgreSQL + Prisma + Tailwind (ветка `claude/level6-nextjs-GBpVR`; на main не выносился);
7. **Уровень 7** — «Enterprise»: микросервисы (Docker + nginx-шлюз + Postgres + RabbitMQ) для деплоя на Render (ветка `claude/level7-enterprise-GBpVR`; на main не выносился).

README на main честно описывает только уровень 5 и ссылается на «структуру как в чате 14.12.2025» — проект вырос из переписки/чата.

## Как устроено (архитектура)

Текущий main (уровень 5) — классическая двухзвенная связка:

- **backend/** — Flask-приложение `api.py` (~47 строк): два эндпоинта — `GET /api/products` (активные товары из SQLite) и `POST /api/orders` (создание заказа с позициями; цена берётся из БД, не от клиента). База `flowers.db` (28 КБ) закоммичена в репозиторий уже заполненной; скрипта инициализации на main нет.
- **frontend/** — React 18 + Vite 5 + axios: весь UI в одном компоненте `App.jsx` (каталог карточками, корзина с +/−, форма имя/телефон, alert с номером заказа). Интерфейс на русском, цены в евро.
- **Dockerfile** — multi-stage: Node 20 собирает фронтенд → Python 3.12-slim + gunicorn отдаёт API на порту 10000 (конфигурация под Render; в `vite.config.js` разрешён хост `.onrender.com`).

**Важный найденный дефект:** Dockerfile копирует собранный фронтенд в `./static`, но `api.py` на main статику **не отдаёт**, а `App.jsx` жёстко зашивает `API = 'http://127.0.0.1:5001'` — то есть Docker-образ с main в продакшене отдаёт только API, без UI. Оба дефекта исправлены в **открытом, но не слитом PR #11** (ветка `claude/level5-react-flask-GBpVR`: раздача статики через Flask + `VITE_API_URL`/относительные пути). Также открыт PR #12 с починкой уровня 4, которого на main нет (сам уровень 4 жив в ветке `claude/level4-express-GBpVR`).
