# Рекомендации по in4

## Быстрые улучшения

1. **Добавить LICENSE** (для текстов уместна CC BY-SA 4.0 или CC BY 4.0) — сейчас переиспользование контента юридически не определено.
2. **Включить GitHub Pages** и добавить `index.html` (можно сгенерировать из README) — серия мгновенно станет читаемым сайтом; сейчас svend4.github.io/in4 возвращает 404.
3. **Свести два Vulkan-гайда в один**: `prima-cpp-vulkan-porting-guide.html` и `prima-vulkan-port.html` дублируют тему (~219 КБ); оставить канонический, второй пометить как архив или удалить.
4. **Добавить сквозную навигацию**: единый хедер/футер «← предыдущая | оглавление | следующая →» на все 15 страниц (сейчас внутренние перекрёстные ссылки разбросаны неравномерно — от 10 в калькуляторе и 7 в favorites до нуля; 4 страницы — comparison, clustering и оба Vulkan-гайда — вообще без навигации, единого меню нет).
5. **Проставить гиперссылки на источники** в тексте страниц — сейчас arXiv, Jeff Geerling, ServeTheHome упомянуты только текстом в README; без ссылок цифры непроверяемы.
6. **Вынести дату и «срок годности» на каждую страницу** (баннер «данные на 02.2026, цены могли измениться»), а не только в README.
7. **Вынести общий CSS в один файл** (или хотя бы зафиксировать тему), чтобы правки стиля не требовали 15 синхронных правок.

## Серьёзные доработки

1. **Сделать калькулятор настоящим калькулятором**: часть 11 содержит все формулы и данные 15 конфигураций, но статична. Добавить JS-форму (бюджет, страна/тариф на электричество, целевая модель) → расчёт TCO, $/tok/s и рекомендация конфигурации. Данные вынести в JSON — это заодно откроет их для переиспользования.
2. **Извлечь данные из HTML в машиночитаемый слой**: таблицы (железо, сети, квантизации, цены) конвертировать в JSON/CSV в папку `data/`; HTML генерировать из них. Это превратит «замороженные статьи» в обновляемую базу данных.
3. **Реализовать Vulkan-порт по собственному плану**: гайд содержит 7 фаз, словарь CUDA→Vulkan и почасовой чеклист — логичный шаг сделать форк prima.cpp и довести хотя бы фазу 1–2 до PR в upstream, приложив бенчмарки из главы 9.
4. **Процесс актуализации**: раз в квартал обновлять цены/модели (можно полуавтоматически: скрипт тянет цены и прайс-агрегаторы, человек валидирует), вести CHANGELOG.
5. **Перевод ядра серии на английский** — тема востребована, англоязычная версия резко расширит аудиторию и шанс на вклад сообщества.

## Варианты продолжения

**Сценарий 1 — «Живой справочник» (сайт-энциклопедия).** Включить Pages, добавить index, навигацию, поиск (например, клиентский lunr.js или Pagefind), баннеры актуальности и квартальные обновления цен. Репозиторий превращается из архива февральского исследования в поддерживаемый русскоязычный справочник по домашнему LLM-инференсу — ниша, где конкуренции почти нет. Трудозатраты умеренные, основной актив (контент) уже готов.

**Сценарий 2 — «Инструмент» (интерактивный конфигуратор кластера).** Развить часть 11 в полноценное веб-приложение: пользователь задаёт бюджет, страну (тариф на электричество), желаемую модель/квантизацию — приложение из JSON-базы конфигураций считает TCO, tok/s, срок окупаемости против облачных API и выдаёт спецификацию закупки (вплоть до б/у рынка из tesla-zluda-гайда). Это самый «продуктовый» путь: серия становится источником данных, а ценность смещается в инструмент.

**Сценарий 3 — «Инженерный вклад» (реальный Vulkan-порт prima.cpp).** Использовать два porting-гайда как ТЗ: форкнуть prima.cpp, пройти 7 фаз, воспроизвести бенчмарки Vulkan vs CUDA vs CPU из главы 9 на реальном железе, оформить PR в upstream и статью-отчёт как часть 12 серии. Даже частичный результат (фазы 1–3) превратит in4 из «исследования о чужом коде» в проект с собственным кодом и репутацией в сообществе llama.cpp/prima.cpp.

**Сценарий 4 — «База знаний для ИИ» (RAG/MCP-слой).** Конвертировать серию в Markdown/JSON и поднять над ней RAG-индекс или MCP-сервер «домашний AI-архитектор»: ассистент отвечает на вопросы «какой кластер собрать под 70B за $2000 в Германии?» с опорой на данные серии. Симметрия красивая: база знаний о локальном инференсе обслуживается локальным инференсом.

## Сочетания с другими репозиториями профиля

1. **in4 + daten22 / data20 (offline search app, SQLite FTS4, embedded backend) = офлайн-энциклопедия домашнего AI.** Контент in4 конвертируется в записи FTS4-базы, а офлайн-приложения из daten22/data20 дают полнотекстовый поиск без интернета. Получается уникальный артефакт: полностью автономный справочник по построению автономного AI — идеологически цельный продукт для тех, кто принципиально работает офлайн (это же и целевая аудитория in4).

2. **in4 + infom (ГрафРАГ) + info100 (лаборатория агентов) = локальный «AI-архитектор железа».** Из таблиц in4 строится граф знаний (железо → интерфейсы → фреймворки → модели → цены), infom даёт GraphRAG-механику, а агентная обвязка из info100 — диалогового консультанта, который проектирует кластер под бюджет и валидирует конфигурацию по графу (совместимость RoCE/Thunderbolt, лимиты памяти под квантизацию). Инновация: рекомендации не из «мнения LLM», а из проверяемого графа с расчётными формулами серии.

3. **in4 + info40 (AI Agent Orchestration Platform, Production) = самодостаточная агентная платформа на своём железе.** in4 отвечает на вопрос «на чём запускать» (конфигурации, продакшн-развёртывание, мониторинг из части 10), info40 — «что запускать» (оркестрация агентов). Объединение даёт reference-архитектуру «агентная платформа on-premises под ключ»: от закупки б/у Tesla P40 до Grafana-дашбордов и OpenAI-совместимого API, на который садится оркестратор. Такой end-to-end гайд — редкость.

4. **in4 + lorenzo (docs-toolkit, Python-пакет для документации) = конвейер публикации.** docs-toolkit из lorenzo применить для конвертации HTML-монолитов in4 в структурированный Markdown-корпус с автогенерацией оглавлений, проверкой ссылок и сборкой сайта — одновременно решаются проблемы навигации, дублирования CSS и машиночитаемости, а lorenzo получает крупный реальный кейс.
