# Вопросы к meta10

## 1. Планируется ли превращать спроектированный пайплайн grep-ast → ast-grep в работающий код?

Раздел 11 документа — фактически готовое ТЗ (архитектура, паттерны для 5 языков, схема tool calls), но ни строчки реализации в репозитории нет.

**Варианты ответов:**
- А. Да, реализация планируется (здесь или в отдельном репо).
- Б. Нет, meta10 задуман как чисто аналитический документ.
- В. Реализация уже есть/начата в другом репозитории профиля (например, info40/info100).

**Варианты дальнейших действий:**
- При А: начать с минимального прототипа (обёртка `TreeContext` + CLI ast-grep, 200–400 строк), сразу заложить бенчмарк точности — это закроет и «проблему 2» самого документа; вести код в отдельной папке `pipeline/` или новом репо со ссылкой из meta10.
- При Б: зафиксировать это в README («спецификация, реализация не планируется») и опубликовать выжимку наружу (комментарий к статье Хабра, issue в Aider-AI/grep-ast), чтобы анализ принёс пользу.
- При В: добавить перекрёстные ссылки meta10 ↔ репозиторий с реализацией; в вики-хабе info200 отразить связь «спецификация → код».

## 2. Что означает «meta10» и какова стратегия размещения таких разборов — почему отдельный репозиторий, а не хаб?

Имя репозитория не связано с содержанием; в профиле есть info200 (будущий вики-хаб) и lorenzo (монорепо документации ~2815 md-файлов), куда подобный разбор ложится естественно.

**Варианты ответов:**
- А. `meta*` — серия репозиториев под мета-анализы инструментов; нумерация техническая.
- Б. Репозиторий создан ситуативно под одну задачу Claude Code, без стратегии.
- В. Планируется миграция подобных документов в единый хаб (info200/lorenzo).

**Варианты дальнейших действий:**
- При А: описать соглашение об именовании в info200 и добавить в README каждого `meta*` строку «серия: мета-анализы, №10»; сделать индекс серии.
- При Б: ничего не мигрировать срочно, но добавить в README тему и тег, чтобы документ был находим; учесть в будущем правиле «новые разборы — в хаб».
- При В: перенести файл в хаб с сохранением истории (git mv/subtree), в meta10 оставить README-указатель или заархивировать репозиторий.

## 3. Будут ли ещё разборы статей в этом стиле (серия рецензий), и если да — нужен ли шаблон?

Документ демонстрирует сильную воспроизводимую методику: пересказ → верификация по исходникам → нумерованные проблемы → конструктивная альтернатива → выводы.

**Варианты ответов:**
- А. Да, планируется серия регулярных разборов.
- Б. Возможно, эпизодически — когда попадётся достойная статья.
- В. Нет, это разовый эксперимент.

**Варианты дальнейших действий:**
- При А: выделить шаблон разбора (структура разделов + чек-лист верификации) в отдельный файл; вести индекс рецензий в README; рассмотреть связку с docs-toolkit из lorenzo для автоматизации (оглавления, проверка ссылок).
- При Б: минимально — сохранить в README meta10 пометку «формат открыт для новых разборов» и шаблон-черновик.
- При В: закрыть репозиторий как завершённый (заметка в README, archive), ценность зафиксировать ссылкой из info200.

## 4. Проверялись ли YAML-правила ast-grep из раздела 11 реальным запуском?

Правила для Kotlin/Go/PHP/Elixir приведены в документе, но признаков их верификации нет; имена типов узлов различаются между tree-sitter-грамматиками, и часть правил может не сработать как написано.

**Варианты ответов:**
- А. Да, проверялись локально, просто результаты не закоммичены.
- Б. Нет, правила написаны «на бумаге» как иллюстрация.

**Варианты дальнейших действий:**
- При А: добавить в репозиторий каталог `patterns/` с проверенными правилами и мини-фикстурами кода + команду запуска; одна строка в документе «правила проверены на ast-grep vX.Y».
- При Б: пометить правила в тексте как непроверенные иллюстрации (честность к читателю) или провести проверку — это быстрый способ поднять достоверность главного раздела.

## 5. Планируется ли актуализация анализа при выходе новых версий grep-ast?

Анализ жёстко привязан к grep-ast 0.9.0; библиотека живая, и, например, добавление фильтрации по типу узла обесценит центральный вывод документа.

**Варианты ответов:**
- А. Да, документ будет обновляться.
- Б. Нет, это снимок на дату анализа.

**Варианты дальнейших действий:**
- При А: добавить в шапку раздел «История версий анализа» и подписаться на релизы Aider-AI/grep-ast; обновления вносить отдельными коммитами с датой.
- При Б: явно зафиксировать в шапке «анализ действителен для grep-ast 0.9.0, март 2026» — минимальная защита от введения будущих читателей в заблуждение.

## 6. Отправлялась ли обратная связь авторам статьи или в репозиторий grep-ast?

Главное открытие разбора (grep-ast не фильтрует false positives, вопреки впечатлению от статьи) полезно и авторам ecom.tech, и пользователям grep-ast, но следов публикации вовне нет.

**Варианты ответов:**
- А. Да, комментарий/issue отправлены.
- Б. Нет, разбор делался для внутреннего пользования.
- В. Планировалось, но не дошли руки.

**Варианты дальнейших действий:**
- При А: добавить ссылки на комментарий/issue в документ — это внешнее подтверждение ценности работы.
- При Б: осознанно оставить как есть; рассмотреть хотя бы публикацию выжимки (10 строк) в профильном канале.
- При В: подготовить короткую версию (3 абзаца: находка в коде + предложение двух стадий) для комментария на Хабре — усилия минимальны, отдача репутационная.
