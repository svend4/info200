# Структура meta10

## Дерево репозитория

Репозиторий предельно плоский — две единицы контента в корне, папок нет:

```
meta10/
├── README.md                     # 2 строки: «# meta10» + «info» — заглушка без содержания
└── review-habr-ecom-article.md   # 841 строка, ~64 КБ — ВЕСЬ контент репозитория:
                                  #   разбор статьи Habr (ecom.tech, март 2026) о grep-ast,
                                  #   независимый анализ исходного кода grep-ast 0.9.0,
                                  #   8 критических проблем статьи,
                                  #   проект двухстадийного пайплайна grep-ast → ast-grep
```

Отсутствуют: LICENSE, CLAUDE.md, .github/ (CI), какие-либо папки, код, примеры.

## Ключевые файлы

| Файл | Объём | Что делает |
|---|---|---|
| `README.md` | 2 строки | Формальная заглушка («meta10», «info»); не описывает содержимое репозитория |
| `review-habr-ecom-article.md` | 841 строка / ~64 КБ | Единственный содержательный артефакт — трёхслойный аналитический документ: рецензия + перепроверка по исходникам + собственное архитектурное предложение |

## Внутренняя структура документа `review-habr-ecom-article.md`

Фактическая «архитектура» репозитория — это композиция документа. 12 разделов образуют три смысловых слоя:

### Слой 1 — пересказ и систематизация статьи (разделы 1–7)

| Раздел | Содержание |
|---|---|
| 1. Постановка задачи | Reverse engineering документации в ecom.tech: извлечение REST-эндпоинтов и Kafka-паттернов из сотен микросервисов на Go, Kotlin, Ruby, Elixir, PHP; таблица паттернов по языкам |
| 2. Эволюция подходов: три тупика | Tree-sitter напрямую (AST без семантики фреймворка), RAG-пайплайн (эмбеддинги `gte-multilingual-base`, точность 85%), regex+grep («костыльные регулярки») |
| 3. Что такое grep-ast | Библиотека Aider-AI (Пол Готье), Python поверх tree-sitter, v0.9.0; таблица CLI-флагов; 100+ расширений файлов |
| 4. Внутренняя механика grep-ast | Собственный анализ исходников: три фазы (`walk_tree` → `grep` → `add_context`), устройство `enumerate_files`, ограничение одного `.gitignore`, карта языков |
| 5. Конкретные примеры | grep vs grep-ast на поиске метода и на поиске по проекту; формула «где текст?» vs «какие части программы за этим стоят?» |
| 6. grep-ast vs ast-grep | Таблица разграничения (Python/Rust, regex/структурные паттерны, поиск/поиск+замена+линтинг) и критика отказа ecom.tech от ast-grep |
| 7. Интеграция в LLM-агент | RAG vs tool call: таблица из 6 свойств, трассируемость как системное свойство, параллели с Aider, Claude Code, Cursor |

### Слой 2 — критика и контекст (разделы 8–10)

| Раздел | Содержание |
|---|---|
| 8. Критический анализ | 5 сильных сторон статьи и **8 критических проблем**: (1) grep-ast НЕ фильтрует ложные срабатывания — поиск это чистый `re.search()`; (2) асимметрия измерений — 85% у RAG, нет цифры у решения; (3) ложные отрицания при метапрограммировании (Rails `resources`, Elixir-макросы, роуты из конфига в Go); (4) управление паттернами не раскрыто; (5) промпт агента не показан; (6) производительность: нет параллелизма/кеширования, GIL; (7) только один `.gitignore`; (8) отказ от ast-grep недообоснован |
| 9. Более широкий контекст | Паттерн «детерминированный инструмент как tool call»; таблица «AST-поиск vs эмбеддинги» по 6 сценариям; эскиз гибридной архитектуры |
| 10. grep-ast в экосистеме Aider | Зачем Готье создал grep-ast (repo map), как это объясняет дизайн-решения (текстовый поиск, отсутствие фильтрации по типу узла) |

## Особенности организации

- **Один артефакт — один репозиторий.** meta10 следует паттерну профиля svend4: маленькие «info»-репозитории под отдельные темы. Имя `meta10` никак не связано с содержанием; связь тема↔репозиторий видна только из описания на GitHub.
- **Итеративная сборка через Claude Code.** 9 коммитов за один день (5 марта 2026), три последовательно смёрженных PR из ветки `claude/review-habr-ecom-article-MjaMf`; каждый PR добавлял слой (перевод/расширение → анализ исходников и 8 проблем → двухстадийный пайплайн).
- **Документ богат структурой:** ~15 markdown-таблиц, код-блоки с Python/YAML/Go/Bash, ASCII-схемы пайплайнов, псевдо-JSON примеров tool calls. Внутреннего оглавления при этом нет — при 841 строке навигация только скроллом.
- **README не выполняет роль входной точки** — читатель, открывший репозиторий, не узнает из README ни темы, ни того, что смотреть.
