# Рекомендации по universal-file-storage-mcp

## Быстрые улучшения

1. **Починить компиляцию (39 ошибок tsc)** — три механические правки:
   - в `registerTool` передавать `inputSchema` как «сырую» zod-форму (`{ query: z.string(), ... }`), а не `z.object({...})` — уберёт ~30 ошибок и вернёт типизацию параметров;
   - в catch-блоках заменить `error.message` на `error instanceof Error ? error.message : String(error)` (5 ошибок TS18046);
   - переписать создание `StreamableHTTPServerTransport` под реальный API SDK (`sessionIdGenerator` и т.д.) и добавить Express-роут `app.post('/mcp', (req,res) => transport.handleRequest(req,res,req.body))`.
2. Добавить файл **LICENSE** (MIT уже заявлен в package.json) и **package-lock.json**.
3. Убрать jest из скрипта `npm test` или добавить jest в devDependencies (сейчас команда падает).
4. Заменить плейсхолдер `YOUR_USERNAME` в `install-termux.sh` на `svend4`.
5. Вынести массив `STORAGES` из исходника в `storages.json`/`.env` — README и так обещает конфигурацию, но заставляет править код.
6. Синхронизировать доки с кодом: убрать из README/ARCHITECTURE заявления про S3, кэширование, индексацию и path-traversal-защиту либо пометить их как «планируется»; исправить пример Anthropic API (localhost недостижим для MCP-коннектора — нужен публичный URL/туннель).
7. Реализовать или удалить мёртвые параметры `recursive` (list_files) и `include_images` (search_files).

## Серьёзные доработки

1. **Безопасность NAS-монтирования**: не собирать shell-строку с паролем (инъекция + утечка через список процессов) — использовать credentials-файл для `mount.cifs` или библиотеку SMB на чистом JS (`@marsaud/smb2` и т.п.), создать точку монтирования перед mount, убрать требование sudo из рантайма.
2. **Защита путей и аутентификация**: нормализация и проверка `path.resolve` внутри корня хранилища (сейчас `../` выводит за пределы), токен/ключ для HTTP-эндпоинта, режим read-only по умолчанию.
3. **Рекурсивный обход + индексация**: сейчас поиск видит только файлы верхнего уровня и на каждый запрос читает всё подряд. Нужен рекурсивный walker с лимитами и индекс (SQLite FTS5 — он и так заявлен в roadmap; см. также идею сочетания с daten22 ниже), OCR-результаты кэшировать.
4. **Честные адаптеры**: разнести `StorageAdapter` на подклассы (как уже нарисовано в ARCHITECTURE.md), реализовать S3 (зависимость уже стоит) или удалить её; для Android OCR — сначала скачивать файл (`adb pull`) во временную папку.
5. **Тесты и CI**: unit-тесты адаптеров на mock-FS, smoke-тест «сервер поднялся и отвечает на initialize», GitHub Actions с `tsc --noEmit` — одна эта проверка не дала бы залить некомпилирующийся код.
6. Извлечение текста из PDF/DOCX (pdf-parse, mammoth) — иначе заявленный поиск по документам фиктивен.

## Варианты продолжения

**Сценарий A — «Довести до рабочего MCP-сервера для себя» (минимальный, 1–2 дня).** Ограничить амбиции: только локальные папки + Termux на телефоне, выбросить NAS/cloud/S3-ветки. Починить компиляцию и транспорт, проверить подключение из Claude Desktop/Claude Code, зафиксировать рабочий сценарий «поиск по заметкам и скриншотам телефона». Это самый короткий путь превратить 5 700 строк заготовки в ежедневно используемый инструмент, а Termux-документация — уже готовая половина продукта.

**Сценарий B — «Универсальный файловый шлюз» (полная реализация замысла).** Реализовать адаптеры как плагины (local, SMB, WebDAV, S3, ADB), добавить индексатор с SQLite FTS5 и фоновым обходом, кэш OCR, аутентификацию и конфиг-файл. Результат — публикуемый в npm/каталогах MCP-серверов пакет с реальной нишей: существующие filesystem-MCP работают только с локальными путями, а «локальные+NAS+телефон+облако в одном сервере с OCR» — отличительная особенность именно этого проекта.

**Сценарий C — «Термукс-первый продукт: телефон как файловый сервер для Claude».** Сузить проект до самой проработанной части: MCP-сервер, живущий на Android в Termux, дающий Claude доступ к фото/скриншотам/загрузкам телефона с OCR. install-termux.sh, boot-автозапуск и 848-строчный гайд уже написаны — осталось заставить работать код. Ниша практически пустая, и это единственный сценарий, где 41 % Shell-кода репозитория работает на продукт.

**Сценарий D — «Разобрать на запчасти».** Если возвращаться к проекту не планируется — честно пометить его в README как concept/unmaintained и перенести ценное: описания инструментов (образцовые для LLM) — в другие MCP-проекты профиля, Termux-гайды — в вики-хаб info200 как самостоятельную инструкцию «Node.js-сервисы на Android».

## Сочетания с другими репозиториями профиля

1. **universal-file-storage-mcp + daten22 (Offline search app, SQLite FTS4) = «Индексированный офлайн-поиск для Claude по всем устройствам».** daten22 уже решает ровно ту проблему, которая объявлена главным узким местом этого сервера (roadmap v1.5: «индексация для быстрого поиска», SQLite FTS): взять из daten22 схему FTS-индекса и офлайн-подход, встроить как слой индексации в MCP-сервер. Получается уникальная вещь: полнотекстовый (и OCR-) поиск по ноутбуку, NAS и телефону за миллисекунды, целиком офлайн, с Claude в роли интерфейса — ни один публичный filesystem-MCP такого не даёт. Родственный опыт есть и в data20 (offline app, embedded back end).

2. **universal-file-storage-mcp + meta2 (восстановление разорванных документов) = «MCP-реставратор документов по всем хранилищам».** У meta2 — логика склейки/восстановления фрагментированных документов, у этого репо — унифицированный доступ к файлам на всех носителях. Вместе: Claude ищет фрагменты одного документа по локальному диску, NAS и телефону (включая скриншоты через OCR), а meta2-алгоритмы собирают из них целый документ. Инновация — «кросс-устройственная реконструкция»: половина договора в PDF на NAS, вторая — фотографией в галерее телефона; ни поиск, ни восстановление по отдельности этого не умеют.

3. **universal-file-storage-mcp + info40 (AI Agent Orchestration Platform) + daten20 (Document Management System) = «агентный документооборот поверх реальных файлов».** Оркестратор info40 получает через этот MCP «руки» до файлов на всех устройствах, а модель документооборота daten20 — правила классификации и маршрутизации. Агенты сами инвентаризируют файловый хаос пользователя (дубликаты, версии, «где последний вариант?») — превращение трёх info-прототипов в один осязаемый продукт.
