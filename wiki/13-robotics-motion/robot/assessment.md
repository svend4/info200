# Характеристика и оценка robot

## Что есть

- **Работоспособный proof-of-concept** (внутри архивов). В рамках аудита код из `etd_proto_repo (1).zip` был распакован и запущен (Python 3.11, PyYAML): 
  - `validate_examples.py` — все 4 пакета `valid=True, level=A, score=1.0`;
  - `sim/failure_scenarios.py` — негативный сценарий отрабатывает (при отсутствии сервисов пакет получает level=D);
  - `sim/report_runner.py` — отчёт генерируется, `overall_pass: true`;
  - `sim/marketplace_demo.py` — магазин корректно различает open-source/commercial пакеты и требует entitlement.
- **Перепроверка заявленных статусов: ПОДТВЕРЖДЕНО.** Корневой `report_summary.json`/`report_summary.md` («overall_pass: True», 4 пакета level=A, блокировки human_too_close / payload_out_of_range / station_incompatible) — байт-в-байт копия отчёта из архива 6, и эти результаты воспроизводятся живым запуском кода.
- **Продуманная модель безопасности**: списки forbidden capabilities (запрет переопределения E-stop, торков, коллизионной защиты, баланса), декларативные capabilities read/write/forbidden, профили станций с ограничением семейств скилов и payload, уровни совместимости A–D, уровни ревью магазина 0–3, принцип «маркетплейс не может обходить safety».
- **Проработанная экономика**: 6 категорий дистрибуции (open-source reference / open model-dataset / free proprietary / paid commercial / enterprise-certified / private OEM-factory), разделение осей «лицензия / доступность исходников / сертификация / монетизация», entitlement-модель, черновики политик в JSON.
- **Богатая документация** (40 файлов в архиве 1): архитектура, формат пакета, интеграция в стиле Atlas, автомобильные use-cases, roadmap v0.2, due-diligence-чеклист, питч для инвесторов.
- **Зафиксировано происхождение идеи**: экспорт диалога с ChatGPT (Hyundai/Boston Dynamics → разбор `data2`/ЕТД Крюкова → концепция скил-пакетов) — редкий случай, когда «генезис» проекта задокументирован полностью.
- Внутри архива: CI-workflow (`validate-examples.yml`), CHANGELOG, requirements.txt, LICENSE (MIT).

## Чего нет

- **Распакованного кода в git** — весь прототип заперт в трёх zip; история изменений, диффы, поиск по коду, запуск CI невозможны.
- **Лицензии на уровне репозитория** — LICENSE есть только внутри архивов, и его текст усечён («...» вместо полного текста MIT) → юридически лицензия фактически не оформлена.
- **Настоящих тестов** — `tests/acceptance_tests.yaml` в пакетах (~95 байт) — заглушки; unit-тестов нет; единственная проверка — smoke-прогон валидатора.
- **Работающего CI** — workflow лежит внутри zip и не исполняется.
- **Настоящих JSON-схем** — файлы в `schemas/` — пустышки `{"type": "object"}` без properties; вся валидация захардкожена в Python (в `docs/roadmap-v0.2.md` это честно признано: «Add real JSON Schema execution»).
- **Осмысленного README репозитория** — 2 строки «robot / info»; посетитель не поймёт, что внутри.
- **Реальной интеграции с роботом** — ни ROS, ни SDK Unitree/Boston Dynamics; «симуляция» — это валидация JSON/YAML и печать словарей, физики нет.
- **Подписи пакетов** — модель подписания подробно описана в документах, но в коде подписи нигде не проверяются.
- Issues/веток с задачами, releases, тегов — нет.

## Плюсы

1. Идея своевременная и цельная: индустриальный skill-store с governance строже потребительского — прямой ответ на анонс Unitree и стратегию Hyundai/Atlas (CES 2026).
2. Код действительно работает и воспроизводит заявленный отчёт — редкость для «инфо-дампов» этого профиля.
3. Безопасность заложена в структуру данных (forbidden capabilities, packageCanNotOverride), а не в комментарии.
4. Связка с ЕТД Крюкова (`etdMapping: MVS/SVS/BVS/CHS` в манифестах) даёт проекту оригинальный теоретический каркас, а не просто копию app-store.
5. Минимальные зависимости (только PyYAML) — прототип запускается за минуту.

## Минусы

1. Форма хранения обесценивает содержание: zip-архивы с суффиксами «(1) (5) (6)» вместо дерева исходников; непонятно, какая версия каноническая (апрельская 6 местами богаче майской 1).
2. Документация сильно избыточна: ~15 из 40 доков — вариации одной темы лицензирования/защиты IP, следствие итеративной чат-генерации; CHANGELOG с пересекающимися версиями (0.1.0, 0.1.4, 0.1.1-docs, 0.2.0-docs-marketplace) не по порядку.
3. Глубина кода не соответствует глубине документов: описаны подписи, ревокация, entitlement-серверы, симуляция отказов — в коде ~680 строк Python, где «симуляция» сводится к повторной валидации манифестов.
4. Мусор в артефактах: `__pycache__/*.pyc` в архиве 1, три формата одного и того же чата (421 КБ), сырой JSON-экспорт с идентификаторами сессии ChatGPT.
5. Кириллические имена файлов с пробелами и скобками ломают скрипты и ссылки.

## Качество кода и документации

**Код** (внутри архивов): компактный, идиоматичный Python (dataclasses, pathlib, type hints), читается легко; однако плотный стиль «всё в одну строку» (`if not pkg.is_dir(): continue`), нет ни одного unit-теста, нет обработки ошибок за пределами happy-path, схемы-пустышки. Оценка: приличный черновик уровня «сгенерировано и один раз проверено».

**Документация**: верхний слой (архитектура, губернанс, экономика) — содержательный и внутренне непротиворечивый; но 40% объёма — самоповторы, и ни один документ не собран в связную книгу. Корневой README репозитория информации не несёт.

**Ограничение покрытия аудита**: прочитаны все 17 корневых файлов (Hyundai-экспорты — выборочно, это 420 КБ диалога), полный листинг всех трёх архивов и ~15 ключевых файлов кода/конфигов из архива 1 с контрольным запуском; 40 документов в `docs/` прочитаны выборочно (около трети), их полное содержание не проверялось.

## Зрелость: 2/5

Обоснование: работоспособный и концептуально сильный PoC (это больше, чем 1/5 «свалка заметок»), но: код не в git, лицензия не оформлена, тесты и CI фактически отсутствуют, схемы — заглушки, версия каноническая не выбрана, активность — один день (11 мая 2026), после чего проект законсервирован. До 3/5 не хватает как минимум распаковки кода в репозиторий, работающего CI и наведения порядка в документации.
