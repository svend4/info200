# Вопросы к data4

## 1. Что именно означает «Soz соц апп»: в чём социальный компонент бюджета?

Описание обещает «соц апп», но внутри нет ни строчки пояснений. От ответа зависит вся архитектура.

**Варианты ответов:**
- А. Совместные бюджеты: семья/группа ведут общий журнал, взаимные долги.
- Б. Социальные функции вокруг личного бюджета: обмен шаблонами категорий, сравнение с другими, челленджи экономии.
- В. «Соц» = принадлежность к линейке soz-проектов (как soz150), а не социальные функции.
- Г. Идея ещё не оформилась.

**Варианты дальнейших действий:**
- При А: проектировать модель с несколькими участниками и механикой взаимных расчётов (splitwise-подобной) с самого начала — её трудно прикрутить потом.
- При Б: сначала одиночный трекер (MVP), социальный слой как поверх-функция второй очереди.
- При В: рассмотреть слияние с soz150 как модуль; data4 закрыть или переименовать.
- При Г: провести короткую сессию фиксации замысла и записать результат в docs/idea.md, прежде чем писать код.

## 2. Проект ещё планируется или репозиторий можно считать отменённым?

Единственный коммит 28.12.2025, полгода тишины.

**Варианты ответов:**
- А. Да, планируется — просто руки не дошли.
- Б. Идея жива, но будет реализована в другом репозитории/сервисе.
- В. Отменён.

**Варианты дальнейших действий:**
- При А: выполнить «Быстрые улучшения» из recommendations.md (README, idea.md, issues с планом MVP) — 1–2 часа, чтобы проект перестал быть немой заготовкой.
- При Б: добавить в README ссылку «идея переехала в X» и заархивировать data4.
- При В: заархивировать репозиторий, чтобы описание «соц апп» не создавало ложных ожиданий при обзоре профиля.

## 3. Какой стек и форм-фактор предполагается: офлайн-приложение, веб-сервис, бот?

В профиле есть все три традиции: офлайн-first (daten22, data20), веб/магазины (data40), боты и агенты (info7, info40).

**Варианты ответов:**
- А. Офлайн-first одностраничник (HTML+JS+SQLite/localStorage).
- Б. Веб-сервис с бэкендом и аккаунтами.
- В. Telegram-бот / чат-интерфейс поверх журнала трат.
- Г. Не решено.

**Варианты дальнейших действий:**
- При А: переиспользовать наработки daten22/data20 (SQLite FTS, embedded backend) — быстрый старт.
- При Б: сначала оценить, оправдан ли сервер для персонального бюджета; спроектировать API и модель пользователей.
- При В: начать с бота-регистратора трат («потратил 300 еда») + еженедельная сводка; связать с оркестратором info7.
- При Г: сделать прототип по пути А как самому дешёвому, решение о стеке принять после первых пользователей (себя).

## 4. Финансовые данные чувствительны: какие требования к приватности и хранению?

Для бюджетного приложения это ключевое проектное решение.

**Варианты ответов:**
- А. Только локально, никакого облака (приватность по умолчанию).
- Б. Синхронизация через собственные файлы/git пользователя.
- В. Облачный бэкенд с аккаунтами допустим.

**Варианты дальнейших действий:**
- При А: офлайн-стек (см. вопрос 3А), экспорт/импорт вместо синхронизации; это же снимает вопросы о защите данных.
- При Б: определить формат журнала (JSON/CSV со схемой) и правила слияния — заодно это основа «социального» обмена.
- При В: заложить шифрование и разграничение доступа с первого дня; для группового бюджета — модель ролей.

## 5. Как data4 соотносится с денежной тематикой других репо (data40/daten23 — магазины, daten3 — tourist hub с партнёрками)?

Есть шанс на общую «финансовую» подсистему профиля.

**Варианты ответов:**
- А. Никак, независимый проект.
- Б. Планировалась связка: покупки в магазинах/поездки — источники расходов для бюджета.
- В. data4 задумывался как общий финансовый модуль для нескольких проектов.

**Варианты дальнейших действий:**
- При А: развивать автономно, но выдержать формат экспорта операций, чтобы связка осталась возможной.
- При Б: определить формат «чека» (заказ магазина → операция бюджета) и добавить импорт в MVP.
- При В: оформить ядро как библиотеку/пакет (модель операций + расчёты), а приложения-потребители держать отдельно.
